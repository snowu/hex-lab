Command: actions as data

Turn "do this" into an object you can store, send, undo and replay. Input mapping, undo/redo and replays.

The problem

The straightforward input code is a pile of ifs inside the player: if Input.is_pressed("jump"): jump(). It works until you want to rebind keys, let an AI drive the same character, replay a run, add undo, or send the player's actions over the network. All of those need the same thing: the action must exist as a value, separate from who decides it and when it runs.

The pattern

A command is an object (or just a piece of data) that represents "do this action". The code that produces commands (keyboard, gamepad, AI, network, replay file) is decoupled from the code that executes them.

# GDScript: input becomes commands, the actor executes them
class_name MoveCommand extends RefCounted
var dir: Vector2
func execute(actor): actor.move(dir)

# the player controller only produces commands
func _unhandled_input(event):
    if event.is_action_pressed("jump"):
        queue.push_back(JumpCommand.new())

Because the AI now emits the same commands, an enemy and a player can drive the very same character class, and a "possess this unit" feature is a one-line change of who produces the commands.

Undo and redo

Add an undo() to each command. The cheap and robust way is to store what the command changed (the previous value) rather than computing the reverse action: moving a unit back by "-1 tile" fails if the move was blocked, but restoring the saved old position always works. Keep a stack of executed commands; undo pops and reverses, redo re-applies, and executing a new command clears the redo stack (the old future no longer exists). You write exactly this in the drill below.

Replay and networking

If commands are plain data and the simulation is deterministic (fixed timestep, seeded RNG, see the game loop and procgen lessons), then a replay is just (seed, list of (frame, command)): a few kilobytes for a whole match. Deterministic lockstep networking sends only the commands too. Both rely on the same rule: the only way to change the world is through commands. One direct write that bypasses them silently breaks every replay.

Commands as data in Zig

In a language with tagged unions a command is naturally a union and executing it is one switch (no virtual calls, trivially serialisable):

const std = @import("std");

const Command = union(enum) {
    move: struct { dx: i32, dy: i32 },
    set_hp: i32,
    heal: i32,
};

const Actor = struct {
    x: i32 = 0,
    y: i32 = 0,
    hp: i32 = 10,

    fn execute(self: *Actor, c: Command) void {
        switch (c) {
            .move => |m| {
                self.x += m.dx;
                self.y += m.dy;
            },
            .set_hp => |v| self.hp = v,
            .heal => |v| self.hp = @min(self.hp + v, 10),
        }
    }
};

test "a recorded list of commands replays to the same state" {
    const log = [_]Command{ .{ .move = .{ .dx = 2, .dy = 0 } }, .{ .set_hp = 4 }, .{ .heal = 3 }, .{ .move = .{ .dx = 0, .dy = -1 } } };
    var a = Actor{};
    var b = Actor{};
    for (log) |c| a.execute(c);
    for (log) |c| b.execute(c);
    try std.testing.expectEqual(a, b);
    try std.testing.expectEqual(@as(i32, 7), a.hp);
}

Costs and variants

  • Memory for history: cap the stack (the drill keeps the last 4) or store compact deltas.
  • Closures can replace command classes (func(): actor.move(dir)) when you do not need to inspect or serialise them. Data commands (unions) can be saved to disk and sent over a network; closures cannot.
  • Compound commands: one user gesture (drag-select and move 20 units) should be one undo step, so a command can hold a list of sub-commands.
  • The pattern is overkill for a game with one input mapping and no undo. Add it when the first of the needs above appears.

Drill: Command pattern: undo and redo

An editor has 8 integer cells. Every change is a command object that remembers how to reverse itself: the index, the new value and the previous value. A history keeps the last 4 commands.

  • exec(index, value): set the cell and push a command on the undo stack (when the stack already holds 4, the oldest is forgotten). An out-of-range index does nothing and records nothing. A new change clears the redo stack.
  • undo(): reverse the latest command and move it to the redo stack. false if there is nothing to undo.
  • redo(): re-apply the latest undone command and move it back to the undo stack. false if there is nothing to redo.

Starter (Zig):

const std = @import("std");

pub const Command = struct { index: usize, value: i32, prev: i32 = 0 };

pub const History = struct {
    cells: [8]i32 = @splat(0),
    undo_buf: [4]Command = undefined,
    undo_len: usize = 0,
    redo_buf: [4]Command = undefined,
    redo_len: usize = 0,

    /// Set cells[index] = value and remember how to undo it.
    pub fn exec(self: *History, index: usize, value: i32) void {
        _ = self;
        _ = index;
        _ = value;
    }

    pub fn undo(self: *History) bool {
        _ = self;
        return false;
    }

    pub fn redo(self: *History) bool {
        _ = self;
        return false;
    }
};

Design exercise: turn-based strategy undo

Units move, attack, and a unit can be killed by an attack. Players want to undo their whole turn, step by step.

  • What does the AttackCommand need to store so undo can bring a dead unit back? (HP before, the unit itself kept in a graveyard list rather than freed, its tile.)
  • How do you make "move 5 units, then attack" undo as one step or as six? (compound command vs one per action: decide with the player's mental model.)
  • What if the attack rolled a random number? (Store the result in the command, or the RNG state, so redo gives the same outcome.)
  • What must not be in the history? (animations, sounds, UI state: derive those from state changes.)

Answer key

1. Command pattern: undo and redo back ↑

Hint: Capture prev = cells[index] before you overwrite it. undo writes prev back; redo writes value again. Write one helper that pushes onto a bounded stack (drop the oldest by shifting) and use it for both stacks. Clearing redo is just redo_len = 0.

This is the Command pattern: an action turned into data. The same object powers undo/redo, input replay (record commands with their frame number), network play (send commands, not state), AI (an enemy emits the same commands a player does) and macros. The trick that makes undo cheap is storing the previous value in the command instead of snapshotting the whole world. For large changes (move 500 selected tiles) one command holds a list of per-tile changes so one Ctrl+Z reverts the whole gesture.

2. Quick check back ↑

B. The reverse of an action is not always well defined (a blocked move, a clamped heal), restoring the saved value always is

"Heal by 3" at full health changed nothing, so "damage by 3" would be wrong. Restoring the old value is exact.

3. Quick check back ↑

B. The simulation is not deterministic: wall-clock time, unseeded or shared RNG, a variable timestep, or a direct state change that bypasses commands

Replays assume the same inputs give the same results. Any hidden input (time, random, uninitialised memory) or hidden writer breaks that.

4. Check 1 back ↑

D. Clear it, because the old future no longer exists once a new command is executed

Redo re-applies an undone past. A new command replaces that future, so the stack must be discarded.

5. Check 2 back ↑

B. Closures cannot be inspected or serialised; switch to data commands such as a tagged union so a replay is just seed plus a list of frame and command

Commands as data are trivially serialisable and sendable. Closures capture code that cannot be stored or transmitted.
