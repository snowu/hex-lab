Putting it together: architecture of a small game

Design the architecture of Breakout from scratch, choosing patterns for reasons, and learn to read a codebase you did not write.

Patterns are tools, and the skill is knowing which problem calls for which. We design a game small enough to hold in your head: Breakout (paddle, ball, bricks, lives, levels from files, a pause menu, high scores), and decide at each step whether a pattern pays for itself.

1. The loop and the update order

Fixed-timestep simulation, variable-rate rendering (game loop lesson). Per step, a written order: read input commands → move paddle → move ball → collisions → apply consequences (score, destroy bricks) → check win/lose. Comment the order in one place. Because the ball depends on the paddle's new position, order matters here; do not rely on node ordering by accident.

2. Input: commands, but only as much as needed

Keyboard, gamepad and touch all produce the same two intents: MovePaddle(dir) and Launch. Making these commands costs almost nothing and buys rebinding, an attract-mode AI that plays the game, and replays for bug reports. Undo is not needed in Breakout: skip it.

3. States: the game flow

Title → Playing → Paused → GameOver → HighScores. This is a pushdown stack: Pause pushes onto Playing and pop resumes. Ball-in-play vs ball-on-paddle is a small enum state machine inside the gameplay state. Do not make the ball a pushdown automaton; the pattern follows the problem.

4. Entities: data, not classes

The bricks (up to a few hundred) are plain data in arrays: position, hit points, type id. A type object defines brick kinds (normal, two-hit, indestructible, explosive) from a data file. The level is data too: a text grid where each character is a brick type id. Adding a new brick kind or level must not need a programmer. Because there are hundreds of bricks and the update touches few fields, struct-of-arrays is fine but unnecessary at this scale: write the clear version and measure before optimising.

5. Collisions: do not build a broadphase

One ball, a paddle and 200 bricks: brute force is trivial. The interesting part is tunneling: a fast ball can pass through a thin brick, so use a swept test (collision lesson) and resolve the first hit by time of impact. A grid would help only with thousands of objects: the "do I need this?" question again.

6. Events: how consequences spread

When the ball destroys a brick: add score, play a sound, spawn particles, maybe drop a power-up, check if the level is clear. The collision code emits brick_destroyed(brick, position) and the scoring, audio, particle and power-up systems each subscribe (observer). Audio requests go through a small event queue so ten bricks breaking in one frame play a limited number of sounds. The level-complete check reacts to the event instead of the collision code knowing about levels.

7. Services and data

Audio, settings, and save/high-score storage are services behind small interfaces, injected into the places that need them (audio into the event listener; the save service into the high-score screen). No Game.instance. The high-score file has a version number from the first release (data lesson).

8. What you deliberately skip

ECS, bytecode scripting, a scene graph with dirty-flag transforms, object pooling for particles (maybe later, after profiling shows allocation). Knowing what not to use is half of the design.

How the pieces talk

Input (keyboard/gamepad/AI) --commands--> Gameplay state
Gameplay: paddle, ball, bricks (data) --swept collision--> hit results
hit results --events (brick_destroyed, ball_lost)--> Score, Audio queue, Particles, PowerUps, LevelFlow
LevelFlow --push/pop/replace--> State stack (Title / Playing / Paused / GameOver)
Services (Audio, Save, Settings) injected at construction

Reading a codebase you did not write

  1. Find the loop. Every game has one place that runs each frame. Start there and read down.
  2. Find the data. Where do kinds of things come from (resources, JSON, tables)? That tells you how content is made.
  3. Follow one event end to end. Pick "the player shoots" and trace input → command → spawn → collision → damage → UI. You will meet every system.
  4. Draw the ownership tree: who creates whom, who frees whom.
  5. Look for the global state (singletons, autoloads, statics): that is where the surprises live.
  6. Run it with a profiler and a debugger before forming opinions.

Design challenge: apply this to your own game

Take a game you want to build (or one you love) and write, in one page:

  1. The loop and the written update order (6 to 10 steps).
  2. The commands the input produces.
  3. The game-flow stack and which transitions push, pop and replace.
  4. What is data (type objects, level files) and what is code.
  5. The 3 to 5 events that cross system boundaries.
  6. The services, and who owns each.
  7. Three patterns you deliberately skipped, with a one-line reason each.

Then check it against the antipatterns lesson: is there any global the design cannot live without?
