Data-driven design and save files

Keep tuning numbers out of code, and write saves that survive updates and corruption.

Data-driven design

Enemy HP, weapon damage, loot tables and level layouts are data. Put them in files (Godot Resource files, JSON, CSV) and load them, instead of hard-coding constants across scripts. Benefits: designers (or you at 2 am) tweak without recompiling, hot reload speeds iteration, mod support gets easier, and the numbers can be balanced in a spreadsheet. The rule: code defines behaviour, data defines instances.

  • Validate data on load and fail loudly, with the file and field name in the error.
  • Reference things by stable string ids ("iron_sword"), never by array index, or reordering breaks saves.
  • Keep derived values (DPS, total cost) computed, not stored.

Save files

  • Version everything with a number from the first release, and keep one migration function per version step. Never edit an old step.
  • Save the state, not the objects: ids, positions, counters, so the format is independent from your class layout.
  • Atomic writes: write to a temp file, flush, then rename over the real save. A crash mid-write then leaves the previous save intact. Keep one backup.
  • Never trust the file: validate lengths, ranges and checksums. A corrupt or hand-edited file must produce a friendly error, not a crash or an out-of-bounds read.
  • Text (JSON) saves are debuggable and easy to migrate; binary saves are compact and fast but need explicit layout, endianness and versioning, as in the drill.
  • Cloud saves add conflict handling: compare timestamps or play time, or ask the player when both changed.

Determinism and replays

If simulation is deterministic (fixed step, seeded RNG, no wall-clock reads), a replay is just seed + inputs per frame. That powers demos, bug reports (“attach the replay”), speedrun verification and rollback netcode.

Drill: A versioned binary save format

Saves outlive your code. Implement encode and decode for this layout (all multi-byte integers little-endian):

versionbytes
2 (current, 9 bytes)'S' (0x53), 2, coins u32, level u16, checksum
1 (old, 6 bytes)'S', 1, coins u16, level u8, checksum

The checksum is the sum of all the bytes before it, modulo 256. encode always writes version 2. decode accepts both versions (migrating v1 to the current Save struct) and returns "nothing" for a wrong length, bad magic byte, unknown version or bad checksum. It must never read out of bounds.

Starter (Zig):

const std = @import("std");

pub const Save = struct { coins: u32, level: u16 };
pub const size = 9;

pub fn encode(s: Save) [size]u8 {
    _ = s;
    return @splat(0);
}

pub fn decode(bytes: []const u8) ?Save {
    _ = bytes;
    return null;
}

Answer key

1. A versioned binary save format back ↑

Hint: Check the length first, then the magic byte, then the version, then the checksum. Zig: std.mem.writeInt(u32, buf[2..6], value, .little) and std.mem.readInt(u32, bytes[2..6], .little). C++: shift and mask yourself.

Always write a version number from day one. Never edit an old migration step, only append new ones, and keep a test fixture per historical version. Write saves to a temp file and rename it over the old one so a crash mid-write cannot destroy the player's progress. Never trust the bytes: a corrupt or hand-edited save must fail cleanly, not crash or read past the buffer (this is also how most real-world game exploits start).

2. Quick check back ↑

B. Write to a temporary file and atomically rename it over the old save (keeping a backup)

Write-then-rename means the old file is never half-overwritten.

3. Quick check back ↑

B. Reordering or inserting items in the data would silently change what every saved index means

Stable ids survive content changes. Indices turn a harmless data edit into corrupted saves.

4. Check 1 back ↑

A. Keep a version number from the first release plus one migration function per version step, never editing an old step

Immutable per-step migrations chain any old save forward without breaking saves that already migrated.
