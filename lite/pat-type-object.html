Type object, prototype and data-driven design

Make "kinds of thing" into data, let designers add content without code, and resolve inheritance once.

The class explosion

The first instinct for a game with many monsters is a class per monster: Goblin, Orc, GoblinChief, FireGoblin... Every new variant needs code, a recompile, and a programmer. Most of those classes differ only in numbers and references (hp 10 vs 25, which sprite, which attack). That is data, not behaviour.

Type object

Create one Monster class and a separate MonsterType object that holds the shared definition. Each monster instance has a reference to its type. "Goblin" and "Orc" become rows of data that designers can add without touching code.

# GDScript: a type is a Resource, edited in the inspector, saved as a .tres file
class_name EnemyType extends Resource
@export var display_name := "Goblin"
@export var max_hp := 10
@export var speed := 3.0
@export var sprite: Texture2D
@export var parent: EnemyType            # inherit anything not set here

# the one Monster class
class_name Enemy extends CharacterBody2D
var type: EnemyType
func setup(t: EnemyType): type = t; hp = t.max_hp

This is also how you separate engine code from game content. The same pattern drives weapons, items, spells, tiles, quests and levels. Godot Resource files and Unity ScriptableObject assets are this pattern with an editor.

Prototype and inheritance between types

"Elite goblin chief" is the goblin with a few overrides. Let a type name a parent and only store what differs. To read a stat, walk up the chain until a type sets it (you implement exactly this in the drill). The older name for the idea is prototype (JavaScript's prototype chain is the same mechanism). Two design points:

  • Resolve once, not per frame. Flatten the chain into a final table at load time. Looking up the chain inside the update loop wastes time.
  • Make the source visible. When a goblin has 25 hp, designers must be able to see which ancestor said so. Tooling that shows the inherited value in a different colour prevents hours of confusion.
  • Reject cycles and missing parents at load time with a clear error that names the file.

Data-driven design: how far to go

You can push more and more into data: stats, then spawn tables and wave definitions, then ability parameters, then whole behaviours expressed as data (a list of effects, or bytecode, see the bytecode lesson). The trade-off is that the more behaviour lives in data, the more you need a data language, validation and tooling, and the harder debugging gets. A good boundary: if a designer will want to change it weekly, it is data; if it changes how the engine works, it is code.

Practical rules: reference other things by stable string ids ("iron_sword"), never by array index; validate data on load and report the file and field; keep derived values (damage per second) computed, not stored; version your data files (see the save-file lesson).

Drill: Type object: data-driven monsters with inheritance

Instead of a C++/Zig class per monster kind (Goblin, GoblinChief, EliteGoblinChief...), make "monster type" data. A type has a name, an optional parent type, and stats that may be set or left unset. Designers add types without recompiling.

  • define(name, parent, stats): add a type. Returns false if the name already exists or the parent has not been defined yet.
  • resolve(name): the final stats. Walk from the type up through its parents: each stat comes from the closest type that sets it. Returns nothing if the type is unknown or a stat is never set anywhere on the chain.

Example: goblin sets hp 10, attack 2, speed 3. chief (parent goblin) sets hp 25 and attack 4. elite (parent chief) sets speed 5. Resolving elite gives hp 25, attack 4, speed 5.

Starter (Zig):

const std = @import("std");

pub const Stats = struct { hp: ?i32 = null, attack: ?i32 = null, speed: ?i32 = null };
pub const Resolved = struct { hp: i32, attack: i32, speed: i32 };

pub const Registry = struct {
    const max = 8;

    names: [max][]const u8 = undefined,
    parents: [max]?usize = @splat(null),
    stats: [max]Stats = undefined,
    n: usize = 0,

    /// false if the name exists already or the parent is not defined yet
    pub fn define(self: *Registry, name: []const u8, parent: ?[]const u8, stats: Stats) bool {
        _ = self;
        _ = name;
        _ = parent;
        _ = stats;
        return false;
    }

    /// each stat comes from the closest type on the chain that sets it; null if unknown or incomplete
    pub fn resolve(self: *const Registry, name: []const u8) ?Resolved {
        _ = self;
        _ = name;
        return null;
    }
};

Answer key

1. Type object: data-driven monsters with inheritance back ↑

Hint: Keep parallel arrays (names, parent indices, stats) and a find(name) helper. define: reject duplicates, translate the parent name to an index (failing if missing), store. resolve: start with three empty optionals, loop cur = idx; while cur: fill any still-empty stat from stats[cur]; cur = parents[cur].

Type Object (and its close relative Prototype) is why games are mostly data: weapons, enemies, items, spells. The runtime has one Monster class that holds a pointer/index to its type. Resolving inheritance once at load time, not per frame, is the usual optimisation (flatten the chain into a final table). Godot Resources and Unity ScriptableObjects are this pattern with an editor on top. Watch for cycles (reject parents that are not defined yet, as here) and for "inheritance depth creep" where nobody knows where a stat comes from: show the source in tooling.
