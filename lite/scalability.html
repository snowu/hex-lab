Scalability fundamentals

Find the bottleneck, scale statelessly, shed load, and do the maths.

The scaling playbook (in the order you should reach for it)

  1. Measure first. Profile, find the real bottleneck (CPU, DB, network, a lock, one hot partition). Scaling the wrong tier wastes money.
  2. Make services stateless (state in DB/cache/queue) so you can add instances behind a load balancer.
  3. Cache reads, batch writes, add indexes, fix N+1 queries.
  4. Go async: move slow or bursty work behind a queue; absorb spikes instead of provisioning for them.
  5. Scale data: read replicas → partition/shard → purpose-built stores (search, time series, KV).
  6. Protect yourself: rate limits, backpressure, load shedding, timeouts, bulkheads.

Useful laws

  • Little’s Law: concurrency = arrival rate × latency. 200 req/s at 0.5 s average needs ~100 requests in flight. If latency doubles, so does the concurrency you need, which is how a slow dependency exhausts your pool.
  • Amdahl’s Law: the serial fraction caps speed-up. If 10% is serial, the maximum speed-up is 10× however many nodes you add.
  • Tail latency: with fan-out to N backends, the chance at least one is slow rises fast. Watch p99, use hedged requests and timeouts.
  • Utilisation vs queueing: latency explodes as utilisation nears 100%. Keep headroom (about 60-70% target) and autoscale on a leading signal.
Say this in interviews: “What is the bottleneck, how will we know, what is the cheapest change that moves it, and what breaks next?”

4. Autoscaling calculation back ↑

Hint: need = math.ceil(lag / (rate * drain)). Then clamp: max with the minimum first, min with the partition count last.

Reference solution:

import math

def desired_replicas(lag, rate_per_consumer, drain_seconds, partitions, min_replicas=1):
    needed = math.ceil(lag / (rate_per_consumer * drain_seconds))
    return min(partitions, max(min_replicas, needed))

The cap by partitions is the key insight: in Kafka, parallelism within a group is bounded by the partition count, so plan partitions for peak parallelism up front (increasing them later breaks key ordering).
