Edge and serverless: Cloudflare Workers, KV, Durable Objects

What runs where, which storage to pick, and how to protect an upstream with caching and coalescing.

How Workers run

A Cloudflare Worker is JavaScript/WASM running in a lightweight V8 isolate in a data centre near the user: very small cold starts, no servers to manage, billed per request and CPU time. The trade-offs: tight CPU-time and memory limits (check the plan's numbers), no guarantee that in-memory state survives between requests, and you reach everything else through bindings.

Patterns you can name in an interview

  • Shared cache with explicit TTLs per payload: seconds for live data (arrivals), minutes for a whole-city feed, days for data that barely changes. Put a version in the cache key and bump it when the parsed shape changes.
  • Fan-in polling: instead of N users each calling an upstream API, route them to one Durable Object per resource that polls once and shares the result (single-flight at global scale). The upstream sees one caller.
  • Per-user background jobs as a Durable Object with an alarm (for example “check every two minutes and push a notification”). Alarms are best effort, not exact clocks: design for late or retried runs and expire stale pushes.
  • Credentials in KV with an expiry shorter than the token’s (login expiry minus a minute) plus isolate memory, so one login serves everyone.
  • JWT passthrough: verify nothing yourself where the database can do it; forward the user’s token so row-level security applies.
  • Keep-alive cron for free-tier databases that pause when idle.
  • Budget and quota awareness: an upstream with a daily quota is protected by caching and coalescing, and a plan that rejects instead of billing at the limit caps cost.
Interview framing: “The Worker exists because a public page cannot hold credentials and cannot call the upstream directly (CORS). It stays thin: auth check, cache lookup, upstream call, shape the response. State that must be correct lives in Postgres or a Durable Object, not in the isolate’s memory.”

Challenge (Python): Single-flight: coalesce duplicate requests

Fifty phones ask for the same stop's arrivals in the same second. Calling the upstream 50 times wastes quota. Write class SingleFlight with async do(key, fn): if a call for key is already running, wait for it and share its result; otherwise run await fn() (an async function with no arguments). When the call finishes the key is forgotten, so a later call runs again. Errors propagate to every waiter and are not cached. Different keys run independently.

Challenge (Python): Stale-while-revalidate cache

Write class SWRCache with __init__(ttl, swr, now) (now() returns seconds), async get(key, loader) and async idle(). For each key:

  • Fresh (age < ttl): return the cached value, no load.
  • Stale (ttl ≤ age < ttl + swr): return the cached value immediately and refresh it in the background. Many readers must trigger only one refresh.
  • Missing or expired: await loader(), cache the result, return it. Concurrent callers share one load.
  • A failed background refresh keeps the old value (the next get tries again). A failed foreground load raises and caches nothing.
  • idle() waits for any background refreshes to finish (so tests are deterministic).

Answer key

1. Single-flight: coalesce duplicate requests back ↑

Hint: Keep a dict of key → task. If there is none, create one with asyncio.ensure_future(run()) where run() awaits fn() and removes the key in a finally block. Every caller awaits the same task, wrapped in asyncio.shield so one cancelled waiter cannot cancel it for everybody.

Reference solution:

import asyncio

class SingleFlight:
    def __init__(self):
        self.inflight = {}

    async def do(self, key, fn):
        task = self.inflight.get(key)
        if task is None:
            async def run():
                try:
                    return await fn()
                finally:
                    self.inflight.pop(key, None)
            task = self.inflight[key] = asyncio.ensure_future(run())
        return await asyncio.shield(task)

This is the pattern behind a shared poller: N clients, one upstream call. In a Cloudflare Worker the same idea is a Durable Object (one instance per key) that all requests are routed to. Go ships it as golang.org/x/sync/singleflight.

2. Stale-while-revalidate cache back ↑

Hint: Store (value, fetched_at) per key and a dict of in-flight tasks per key (the single-flight idea). Decide by age: fresh → return; stale → return the old value and start (or join) a background task you track in a set; otherwise await the shared load task. Entries are written only when a load succeeds, so failures leave the old value alone. Retrieve the background task’s exception so asyncio does not warn.

Reference solution:

import asyncio

class SWRCache:
    def __init__(self, ttl, swr, now):
        self.ttl, self.swr, self.now = ttl, swr, now
        self.entries = {}      # key -> (value, fetched_at)
        self.inflight = {}     # key -> task
        self.background = set()

    def _load(self, key, loader):
        task = self.inflight.get(key)
        if task is None:
            async def run():
                try:
                    value = await loader()
                    self.entries[key] = (value, self.now())
                    return value
                finally:
                    self.inflight.pop(key, None)
            task = self.inflight[key] = asyncio.ensure_future(run())
        return task

    async def get(self, key, loader):
        entry = self.entries.get(key)
        if entry is not None:
            age = self.now() - entry[1]
            if age < self.ttl:
                return entry[0]
            if age < self.ttl + self.swr:
                task = self._load(key, loader)
                self.background.add(task)
                task.add_done_callback(self.background.discard)
                task.add_done_callback(lambda t: t.cancelled() or t.exception())
                return entry[0]
        return await asyncio.shield(self._load(key, loader))

    async def idle(self):
        await asyncio.gather(*list(self.background), return_exceptions=True)

This is Cache-Control: max-age=ttl, stale-while-revalidate=swr implemented in-process. It hides latency from users, absorbs upstream slowness, and (with the single-flight behaviour) prevents a stampede when a hot key expires. Add stale-if-error to serve old data during an upstream outage.

3. Quick check back ↑

B. A Durable Object per API key: one single-threaded, strongly consistent counter all requests are routed through

KV is eventually consistent, so concurrent requests would each read a stale count. A Durable Object serialises access to one instance per key, giving a correct counter at the cost of routing to that object.

Scheduling guarantees are “at least once, roughly on time”. Alert content that is stale after a couple of minutes should carry a short expiry, and repeated runs must not duplicate effects.
