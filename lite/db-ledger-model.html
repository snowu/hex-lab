Modelling money in a relational database

Accounts, transactions, entries: invariants as constraints.

For money you want a database that enforces rules for you: ACID transactions, constraints and joins. The classic model is a double-entry ledger:

accounts      (id, owner, currency, ...)
transactions  (id, idempotency_key UNIQUE, created_at, memo)
entries       (id, transaction_id → transactions, account_id → accounts, amount_minor BIGINT, currency)
              -- every transaction's entries sum to zero; entries are never updated or deleted

Rules a senior engineer states unprompted

  • Integer minor units (BIGINT cents) or NUMERIC(19,4), never FLOAT/DOUBLE. Avoid Postgres's money type (locale-dependent). Store the currency next to the amount.
  • Append-only. A mistake is corrected with a reversing transaction, never an UPDATE. History stays auditable.
  • Idempotency key with a UNIQUE constraint, so a retried request cannot post twice.
  • Constraints over application checks: NOT NULL, foreign keys (ON DELETE RESTRICT), CHECK (amount_minor <> 0), CHECK (length(currency) = 3).
  • Timestamps: timestamptz stored in UTC. Never store local times.
  • The balance is derived (SUM(entries)). If you keep a cached balance column, update it in the same transaction and reconcile against the sum regularly.
  • NULL means unknown, not zero. Prefer NOT NULL DEFAULT 0 where zero is what you mean.

Challenge (SQL): Balance per account

The ledger stores every money movement as entries (positive or negative amount_minor, in cents). Write a query returning one row per account: owner and balance_minor, the sum of that account's entries. Accounts with no entries must still appear, with a balance of 0.

Why do payments systems store amounts as integer minor units (or NUMERIC) rather than FLOAT?
  1. A. Integers are smaller on disk
  2. B. Binary floating point cannot represent most decimal fractions exactly, so sums drift and equality checks fail
  3. C. Floats are slower to index
  4. D. SQL does not support FLOAT arithmetic

answer 4 ↓

Interview prompt: “model payments with refunds and partial captures”

  • A payments table with a state machine (created, authorised, captured, refunded, failed) and an append-only payment_events history.
  • Money movement lives in the ledger. A capture posts entries; a refund posts new entries, linked by original_payment_id, never editing the capture.
  • Partial capture and refund amounts are constrained: SUM(captures) <= authorised and SUM(refunds) <= SUM(captures), checked in the same transaction under a row lock on the payment.
  • Idempotency keys on every write endpoint, with unique indexes.

Answer key

1. Balance per account back ↑

Hint: You need every account, so start from accounts and LEFT JOIN entries. SUM over zero rows is NULL, not 0: wrap it in COALESCE.

Reference solution:

SELECT a.owner, COALESCE(SUM(e.amount_minor), 0) AS balance_minor
FROM accounts a
LEFT JOIN entries e ON e.account_id = a.id
GROUP BY a.id, a.owner

An INNER JOIN silently drops accounts without entries, a classic reporting bug. In production the balance is usually a maintained column checked against SUM(entries), never recomputed on every read of a hot account.

2. Find unbalanced transactions back ↑

Hint: Filtering on an aggregate needs HAVING, not WHERE (WHERE runs before grouping).

Reference solution:

SELECT transaction_id AS id, SUM(amount_minor) AS imbalance
FROM entries
GROUP BY transaction_id
HAVING SUM(amount_minor) <> 0

Enforcing this inside the database is hard: a CHECK constraint sees one row at a time. Options are a deferred constraint trigger, posting through one function that validates, or a reconciliation job that runs this exact query and alerts on any row.

3. Quick check back ↑

B. Post a new reversing transaction (and then the corrected one), leaving the original entries untouched

Entries are immutable so that any past state can be reconstructed and audited. Corrections are new, visible transactions.

4. Quick check back ↑

B. Binary floating point cannot represent most decimal fractions exactly, so sums drift and equality checks fail

0.1 + 0.2 is not 0.3 in binary floating point. Integer cents (or an exact decimal type) make sums exact, and the invariant "entries sum to zero" is only checkable if arithmetic is exact.

5. Check 1 back ↑

B. Store an idempotency key with a UNIQUE constraint so a retried request fails to insert twice

Only a UNIQUE constraint enforced inside the transaction makes retries safe under concurrency; application checks race.

6. Check 2 back ↑

A. Derive the balance as SUM of entries, and if a cached balance column exists update it in the same transaction and reconcile against the sum

The entries sum is the truth; a cached balance is only safe when written atomically with its entries and reconciled regularly.
