Input, buffering and state machines

How games read input, why they forgive players, and how to stop booleans multiplying into bugs.

Input is a sampled signal

The game does not receive "a press", it samples the keyboard or pad once per frame. Two models:

  • Polling: ask "is jump held right now?" every frame. Simple, perfect for continuous things (moving left, holding a charge).
  • Events: the engine tells you "jump was pressed" or "released". Better for one-shot actions (the press itself matters, not the state).

Most engines give you both (Input.is_action_pressed versus Input.is_action_just_pressed, or the _input(event) callback). Always bind actions ("jump", "attack") rather than physical keys so rebinding and gamepads are free.

Forgive the player

Humans press buttons a few frames early or late and a game that checks the exact frame feels broken. Cheap, invisible tricks fix that:

  • Coyote time: keep allowing the jump for ~100 ms after leaving a ledge.
  • Jump buffering: remember a jump pressed ~100 ms before landing and fire it on touchdown.
  • Input buffering in action games: queue the next attack during the current animation.
  • Corner correction: nudge the player around a block's corner instead of bonking the head.

Implement the first two in the drill: it is a small problem and the code is short.

Drill: Coyote time and jump buffering

Two tricks make platformers feel fair. Coyote time: you may still jump for a few ms after walking off a ledge. Jump buffering: a jump pressed a few ms before landing still fires on landing. Times are in ms.

  • leave_ground(t): the player walked off a ledge at time t.
  • press(t, grounded): jump pressed. Return true if the jump happens now (grounded, or within coyote ms of leaving the ground). Otherwise remember the press and return false. A coyote jump uses up the coyote window (no double jump).
  • land(t): the player touched the ground. Return true if a press happened within buffer ms before t (the buffered jump fires). Clear the buffer and coyote state either way.

Both windows default to 100 ms.

Starter (Zig):

const std = @import("std");

pub const Jumper = struct {
    coyote: i64 = 100,
    buffer: i64 = 100,
    left_at: ?i64 = null,
    pressed_at: ?i64 = null,

    pub fn leaveGround(self: *Jumper, t: i64) void {
        _ = self;
        _ = t;
    }

    /// true if the jump happens right now
    pub fn press(self: *Jumper, t: i64, grounded: bool) bool {
        _ = self;
        _ = t;
        _ = grounded;
        return false;
    }

    /// true if a buffered jump fires on landing
    pub fn land(self: *Jumper, t: i64) bool {
        _ = self;
        _ = t;
        return false;
    }
};

State machines

A player can idle, run, jump, fall, dash, attack, take damage and die. The tempting implementation is a pile of booleans: is_jumping, is_attacking, is_hurt... With 6 booleans there are 64 combinations and most are nonsense ("hurt and dashing and dead"). Each new feature multiplies the bug surface.

A finite state machine allows exactly one state at a time, and only listed transitions. Impossible combinations are unrepresentable. The usual shapes:

  • Enum + match: the smallest thing that works. Good for 3 to 8 states.
  • State objects (or child nodes in Godot): each state owns its enter, update, exit. Scales to big characters and keeps code per state together.
  • Hierarchical: "airborne" contains "jumping" and "falling" and shares their gravity logic.
  • Pushdown (stack): hit-stun pushes on top of running, and popping returns to what you were doing. Menus and dialogue use the same idea.
enum State { IDLE, RUN, AIR }
var state = State.IDLE

func _physics_process(delta):
    match state:
        State.IDLE: if Input.get_axis("left", "right") != 0: state = State.RUN
        State.RUN:  if not is_on_floor(): state = State.AIR
        State.AIR:  if is_on_floor(): state = State.IDLE

In Zig or C++ an exhaustive switch over an enum is checked by the compiler: add a state and every switch that forgets it stops compiling. That is the real win over a pile of if statements.

Drill: A state machine you cannot misuse

Model a player with three states idle, running, air and five events run, stop, jump, land, wait. The valid transitions:

fromeventto
idlerunrunning
idlejumpair
idlewaitidle
runningstopidle
runningjumpair
airlandidle

Everything else is invalid. transition(state, event) returns the next state or "nothing". Machine::send applies an event: it returns true when the event was valid. It increments enter_count only when the state actually changes (so idle + wait is valid but does not count as entering a state).

Starter (Zig):

const std = @import("std");

pub const State = enum { idle, running, air };
pub const Event = enum { run, stop, jump, land, wait };

/// The next state, or null if the event is not valid in this state.
pub fn transition(s: State, e: Event) ?State {
    _ = s;
    _ = e;
    return null;
}

pub const Machine = struct {
    state: State = .idle,
    enter_count: u32 = 0,

    /// true if the event was valid. enter_count only grows when the state changes.
    pub fn send(self: *Machine, e: Event) bool {
        _ = self;
        _ = e;
        return false;
    }
};

Answer key

1. Coyote time and jump buffering back ↑

Hint: Keep two optionals: left_at and pressed_at. press: if grounded or (left_at set and t - left_at <= coyote) then clear both and return true, else pressed_at = t. land: clear left_at, fire if pressed_at is set and within buffer, then clear pressed_at.

Celeste uses roughly 5 frames of coyote time and a similar jump buffer. Players never notice these, only their absence ("the game ate my jump"). The same idea (input forgiveness) applies to attack buffering in action and fighting games.

2. A state machine you cannot misuse back ↑

Hint: A nested switch on state, then event. Let the compiler check you covered every state: do not use a default branch on the outer switch.

Explicit states beat a pile of booleans (is_jumping, is_attacking, can_dash...) because impossible combinations cannot exist. In Godot you would write this as an enum plus match, or as child nodes per state. A pushdown automaton (a stack of states) handles "go back to what I was doing", like hit-stun interrupting a run. In Zig and C++ an exhaustive switch over an enum is a compile error when you add a state and forget a branch.

3. Quick check back ↑

C. Use a hierarchical or parameterised machine: the enraged flag selects a different set of timings and transitions, while the states stay the same

Keep the state set small and put the variation in data (timings, damage) or a parent state. A boolean sprinkled through every state is exactly the pile-of-flags problem again, only one level up.

4. Quick check back ↑

B. Jump buffering

Buffering stores the press and fires it on landing. Coyote time is the mirror image: jumping shortly after leaving the ground.

5. Check 1 back ↑

A. Poll the held state for running, use a press event or just-pressed check for the jump

Polling suits continuous held input; one-shot actions need the press itself, so events or just-pressed checks fit the jump.

6. Check 2 back ↑

C. Replace the flags with one state machine state plus listed transitions, so impossible combinations cannot be represented

One state at a time with explicit transitions removes the combinatorial bug surface that piles of flags create.
