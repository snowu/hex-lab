Worked design: webhook delivery platform

At-least-once delivery, retries, signing, ordering, and customer pain.

Prompt: “Design a system that notifies customers’ HTTP endpoints when events happen (e.g. a payment status changes).” It is a favourite because it is small but full of real trade-offs, and it is exactly what a payments / open-banking platform ships.

1. Requirements

  • Customers register endpoint URLs and event types.
  • Deliver each event at least once; retry on failure for ~24-72h.
  • Customers can verify authenticity; can replay events.
  • Not needed: exactly-once (impossible over HTTP; push dedupe to the consumer with event ids).

2. Core flow

Domain service --(same DB txn)--> outbox table
outbox relay --> queue (partition by endpoint)
delivery workers: POST signed payload, timeout 5-10s
  2xx -> mark delivered    else -> schedule retry (backoff + jitter)
exhausted -> dead-letter + alert + dashboard "replay"

The transactional outbox ensures an event exists if and only if the business change committed.

3. Security

Sign the body with an HMAC and a timestamp: sig = HMAC_SHA256(secret, timestamp + "." + body). Receivers reject old timestamps (replay protection) and compare in constant time. Support secret rotation (two active secrets). Block SSRF: resolve and refuse private IP ranges for customer URLs.

4. Ordering & duplicates

Global ordering is expensive; offer per-entity ordering by partitioning on entity id, and include a monotonically increasing version so consumers can ignore stale events. Always include a unique event_id, because duplicates will happen.

5. Noisy neighbours & failure

One slow customer endpoint must not block others: per-endpoint queues/concurrency limits, short timeouts, and a circuit breaker that pauses a failing endpoint (and emails the customer). Autodisable after N days of failures. Metrics: delivery latency p99, success rate by endpoint, retry depth, DLQ size.

1. Quick check back ↑

B. Because a crash between the commit and the publish loses the event (or publishing first can announce something that never committed)

You cannot atomically write to two systems. The outbox makes the DB the source of truth; a relay publishes at-least-once, and consumers dedupe.

2. Check 1 back ↑

B. Dedupe on event_id and process once, because retries make at-least-once the only honest guarantee

Exactly-once over HTTP is impossible, so the design promises at-least-once with unique event_ids and pushes dedupe to the consumer.

3. Check 2 back ↑

D. Isolate per-endpoint queues and concurrency limits with short timeouts and a circuit breaker that pauses the failing endpoint

Noisy neighbours need isolation: per-endpoint queues and limits, short timeouts, a breaker that pauses a failing endpoint, and autodisable after days of failure.
