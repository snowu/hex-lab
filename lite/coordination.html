Coordination: leaders, leases, quorums and clocks

Exactly one worker, fencing tokens, quorums, consensus and why wall clocks lie.

Designs regularly need “exactly one of these at a time”: one scheduler firing the nightly batch, one consumer per partition, one worker refreshing a bank’s token. That is coordination, and it is where confident designs quietly break.

Leader election with leases

A lease is a lock with an expiry: the holder must renew it before the time-to-live runs out, or someone else may take it. Leases are how you survive a holder that crashes. They are usually provided by a coordination service built on consensus (etcd, ZooKeeper, Consul), by a database (a row with an expiry, Postgres advisory locks), or by a managed primitive (a DynamoDB conditional write, a Durable Object).

The paused-process problem and fencing tokens

A acquires lease (token 33) ── GC pause 30s ────────────────── wakes, writes with 33 ✗
                     lease expires ── B acquires (token 34), writes with 34 ✓

A cannot know it was paused. Checking the lease right before the write does not help: the pause can happen between the check and the write. The fix lives in the resource: every lease grant comes with a fencing token that only grows, and the storage rejects any write carrying a token lower than one it has already accepted. In SQL that is a conditional write: UPDATE jobs SET ... WHERE id = :id AND fence <= :token.

Rule: a lock tells you who should act; only the resource can enforce it. Locks that only aim to save duplicate work (two workers sending the same reminder email) can skip fencing if duplicates are harmless. Locks that protect correctness (money, state transitions) cannot.

Quorums

With N replicas, a write waits for W acknowledgements and a read asks R replicas. If R + W > N, every read set overlaps every write set, so a read can find the latest value (by version). Typical: N = 3, W = 2, R = 2. Lower W or R buys latency and availability and gives up that overlap. Quorums are also why clusters have odd sizes: 3 nodes tolerate 1 failure, 5 tolerate 2, and 4 still tolerate only 1.

Consensus, in one paragraph

Consensus (Raft, Paxos) lets a group agree on one ordered log despite crashes. Raft in brief: nodes elect a leader for a numbered term with a majority vote; the leader appends entries and commits each one once a majority has stored it; a new leader must hold every committed entry. You almost never implement it. You use it via etcd, ZooKeeper, a consensus-backed database (Spanner, CockroachDB) or Kafka’s controller quorum (KRaft), and you should know what it costs: a majority round trip on every write, and no progress without a majority.

Clocks lie

  • Wall clocks drift and jump (NTP corrections, leap seconds, VM pauses). Never order events across machines by wall-clock timestamps, and never measure durations with them. Use a monotonic clock for timeouts.
  • Lamport clocks: each node keeps a counter, increments it on every event, and on receiving a message sets it to max(local, received) + 1. If A happened before B, A’s number is smaller. The reverse is not guaranteed.
  • Vector clocks keep one counter per node, so you can tell “happened before” apart from “concurrent” and detect conflicts.
  • Hybrid logical clocks combine a wall-clock part with a logical counter: close to real time, but still ordered. CockroachDB and others use them.
  • In practice the simplest ordering is often a sequence from one authority: a database sequence, a Kafka partition offset, a version column. Prefer that when you can.

Saying it in an interview

“I need one scheduler. I would take a lease in etcd or a Postgres row with an expiry, renew it at a third of the TTL, and carry the lease revision as a fencing token on every write the scheduler makes, so a paused old leader cannot double-fire. I would not build my own election.”

Challenge (Python): Leases with fencing tokens

A worker that holds a lock can pause (GC, a slow disk, a network partition) for longer than its lease. The lease expires, another worker takes over, and then the first one wakes up and writes anyway. Fencing tokens stop that write.

Implement two classes:

  • LockService(now=time.monotonic) with acquire(owner, ttl). If the lock is free or its lease has expired, grant it and return a new fencing token: an integer that is strictly larger than every token issued before (start at 1). If the same owner still holds an unexpired lease, extend it to now() + ttl and return the same token. If someone else holds an unexpired lease, return None. A lease expires when now() >= expiry.
  • FencedStore() with write(key, value, token) and read(key) (returns None if missing). The store remembers the highest token it has accepted. A write with a smaller token raises StaleTokenError (already defined) and changes nothing. Equal or larger tokens are accepted.

Answer key

1. Leases with fencing tokens back ↑

Hint: LockService keeps (owner, token, expiry) and a counter. Grant when there is no holder or now() >= expiry; renew only when the holder is the same owner and the lease is still valid. FencedStore keeps one max_token and checks it before writing.

Reference solution:

import time

class StaleTokenError(Exception):
    pass

class LockService:
    def __init__(self, now=time.monotonic):
        self.now = now
        self.counter = 0
        self.holder = None  # (owner, token, expiry)

    def acquire(self, owner, ttl):
        t = self.now()
        if self.holder is not None and t < self.holder[2]:
            if self.holder[0] != owner:
                return None
            self.holder = (owner, self.holder[1], t + ttl)
            return self.holder[1]
        self.counter += 1
        self.holder = (owner, self.counter, t + ttl)
        return self.counter

class FencedStore:
    def __init__(self):
        self.max_token = 0
        self.data = {}

    def write(self, key, value, token):
        if token < self.max_token:
            raise StaleTokenError(f'token {token} < {self.max_token}')
        self.max_token = token
        self.data[key] = value

    def read(self, key):
        return self.data.get(key)

The lock alone is not enough: a lease only says who should act, and a paused process cannot know its lease expired. The protected resource has to check the token. In practice the token is the lock’s revision (etcd’s mod_revision, a ZooKeeper zxid, or a row version in Postgres) and the check is a conditional write: UPDATE ... WHERE fence <= :token.

2. Quick check back ↑

B. Clock skew between machines; order by a logical or authoritative sequence (a per-payment version, a Lamport counter, or a single log’s offsets) instead of wall-clock time

UTC removes timezone confusion but not skew. Machines disagree on “now” by milliseconds or more, so causally related events need a logical order from one authority or a logical clock.

3. Quick check back ↑

B. It tolerates the same single failure as 3 nodes (a majority of 4 is 3) while adding write latency and cost; use 3, or 5 to tolerate 2 failures

A majority of 4 is 3, so only one node can fail, the same as with 3 nodes. Odd sizes give the best fault tolerance per node.

4. Check 1 back ↑

B. A fencing token: the storage rejects writes carrying a token smaller than the largest it has seen

A paused process cannot know its lease expired, and any check-then-write has a gap. Only the resource enforcing a monotonically increasing token closes it.

5. Check 2 back ↑

C. W = 2, R = 2

Reads see the latest write when R + W > N. With N = 3, W = 2 and R = 2 gives 4 > 3, so at least one replica in every read quorum has the write.
