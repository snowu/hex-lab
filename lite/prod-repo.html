Repositories, assets and pipelines

Version control for code and art, build automation, asset checks, and how artists can contribute without breaking things.

Games are code plus big binary files

Version control (Git) was designed for text. A game repository holds code, text assets (scenes, resources, JSON), and large binaries (images, audio, models, fonts). Binaries cannot be merged line by line, bloat the history if they change often, and make clones slow. A small amount of structure keeps all of that healthy.

Repository hygiene

  • .gitignore the generated and local files: engine caches (Godot 4: ignore .godot/, but commit the .import files that sit next to your assets, they hold the import settings), build outputs, editor settings with personal paths, logs, node_modules, zig-out and .zig-cache.
  • Commit the lock files and the engine version (a .godot-version file or README line). "It works on my Godot" is a classic.
  • Small commits with real messages ("enemy: fix stuck on corners") beat "wip". Art commits too ("slime: add hurt frame").
  • Branches: short-lived feature branches and a stable main, or trunk-based development with feature flags for a small team. Whatever you choose, keep main always playable.

Large files: Git LFS

Git LFS stores large binaries outside the normal history and keeps pointers in the repository. Use it for audio, large textures, videos and models. Pixel art PNGs are small and fine in plain Git. Decide before the first commit, because moving existing files into LFS later rewrites history.

Merging scenes and resources

  • Text formats (Godot .tscn/.tres, Unity YAML) merge reasonably, but two people editing the same scene often conflict. Own your files: agree who edits which scenes, and split big scenes into small ones (one per entity) so people rarely touch the same file.
  • Binary assets cannot merge at all: only one person should change a given sprite at a time. Lock files (Git LFS locking) or a simple convention in the team does that.
  • Keep layered source files (.aseprite, .kra, .blend) in the repository next to the exported files, or the layers are lost forever.

The asset pipeline

The path from an artist's source file to what the game loads should be automatic, documented and checked:

  1. Source (layered, editable) → export (PNG, WAV, glTF) → import (engine settings: filter nearest, no mipmaps for pixel art, loop points) → runtime.
  2. Conventions: folder structure, snake_case names, sizes (tile 16×16, sprite 32×32), palettes. Put them in the README and in automated checks.
  3. Lint the assets in CI: dimensions match the manifest, PNG has no unexpected colour profile, colours are inside the project palette, no file larger than a budget, names follow the pattern, audio is at the target loudness. A failing check on the pull request is much cheaper than discovering it in the build.
  4. Generate what can be generated (atlases, sprite sheets, localisation tables, manifests) by scripts that run in CI and locally, so nobody edits derived files by hand.

Art without git: pull requests from the editor

Artists should not have to learn branches to contribute. Tools like the spritewright editor (the project that goes with the pixel art track) open the sprites straight from a repository, let the artist draw, and send a pull request through the GitHub API. Reviewers see the before/after images in the pull request's "Files changed" tab (2-up, swipe and onion-skin views), CI runs the asset checks, and the artist never touches a command line. If your artist already knows git, the same flow works with a normal branch.

Continuous integration for games

  • On every push: run the unit tests and replay tests, lint the assets, build the game headless (or export the web build) to prove it still compiles.
  • On main or tags: export for each target platform and upload the builds as artifacts. A downloadable build per commit turns "can someone test this?" into a link.
  • Keep it fast (minutes). Slow CI stops being used.
  • Cache engine downloads and export templates.

Code review for a game

  • Review behaviour by running the branch, not only the diff.
  • Check data changes (balance numbers, level files) for intent; ask for a screenshot or short video for visual changes.
  • Look for the things in this track: hidden globals, per-frame allocation, update-order assumptions, missing dirty flags, magic numbers that should be data.

Documentation that pays

A README with how to run, test and export; one page of architecture (the loop order, the main systems and who owns what); a style guide for art and naming; a changelog. Future you is the main reader.

Checklist: starting a game repository

  1. .gitignore from your engine's template, plus build output folders.
  2. README: engine version, how to run, test, export.
  3. Folder layout agreed: scenes/, scripts/, assets/art|audio|fonts, data/, tests/, tools/.
  4. Large binaries in Git LFS from the first commit (if you use any).
  5. A CI workflow that runs the tests and an export.
  6. An asset lint (sizes, names, palette) wired into CI.
  7. A CONTRIBUTING.md for artists: the folder for each kind of file, naming, size and palette rules, and how to propose a change (pull request or the editor).
  8. A pinned engine version and a license file; a list of third-party assets and their licenses.

Answer key

1. Quick check back ↑

B. Agree ownership of binary files (or use Git LFS file locking) so only one person changes a given sprite at a time

Binary files cannot be merged. Process (ownership, locks) is the only fix.

2. Quick check back ↑

B. Layers, palettes and animation data cannot be recovered from the flattened export, so future edits and re-exports need the source

A flattened PNG is a lossy product. The source is the real asset.

3. Quick check back ↑

B. An automatic lint: dimensions, naming, colours inside the palette, file size budget

Cheap, objective rules catch most mistakes before a human has to look, and give artists immediate feedback.

4. Check 1 back ↑

D. Ignore the generated .godot/ cache but commit the .import files that hold import settings

Generated local caches stay out while the small settings files that reproduce the import stay in.

5. Check 2 back ↑

B. Generate derived files with scripts that run both locally and in CI, so nobody edits them by hand

Automation makes the source the single truth and regeneration the only path to derived files.
