Performance, memory and the frame budget

Profile first, then kill per-frame allocations, pool objects and stop doing O(n²) neighbour checks.

Rule zero: measure

Guessing where time goes is wrong most of the time. Use the profiler (Godot's Debugger → Profiler / Monitors, Tracy, or perf on native builds) and look at the slowest frame, not the average: players notice the hitch, not the mean. Also decide which side is the bottleneck: CPU (game logic, physics), GPU (fill rate, shaders, overdraw), or draw calls (too many separate things submitted).

The usual suspects

  • Allocation in the hot loop. Creating objects/strings/arrays every frame causes GC pauses (GDScript, C#) or allocator pressure (C++, Zig). Preallocate and reuse.
  • O(n²) neighbour checks. Every enemy checking every other enemy. Use a spatial hash or grid (drill below).
  • Pointer chasing. Arrays of pointers to objects scattered in memory. Prefer flat arrays of plain data.
  • Doing unneeded work. Update only what is on or near the screen. Skip animation for off-screen enemies. Lower the AI tick rate (think every 4 frames, staggered).
  • Too many draw calls. Batch by texture/material, use atlases and tile maps, instance repeated meshes.
  • Overdraw and big shaders on mobile and integrated GPUs.

Object pooling

Spawning and freeing a bullet 50 times a second churns memory. A pool allocates N bullets once and hands them out and takes them back. Acquire returns null (or recycles the oldest) when empty, which is a design decision: dropping a bullet is nearly always better than a hitch.

Zig, with the capacity in the type

fn Pool(comptime T: type, comptime n: usize) type {
    return struct {
        items: [n]T = undefined,
        used: [n]bool = @splat(false),

        fn acquire(self: *@This()) ?*T {
            for (&self.used, 0..) |*u, i| {
                if (!u.*) { u.* = true; return &self.items[i]; }
            }
            return null;   // full: the caller decides what to do
        }
    };
}

The same idea in C++

template <class T, std::size_t N>
class Pool {
    std::array<T, N> items_{};
    std::array<bool, N> used_{};
public:
    T* acquire() {
        for (std::size_t i = 0; i < N; ++i)
            if (!used_[i]) { used_[i] = true; return &items_[i]; }
        return nullptr;
    }
};

These linear scans are O(n); a real pool keeps a free list so acquire is O(1). Try improving it as an extra exercise.

Drill: Spatial hash grid for neighbour queries

Checking every pair of 5,000 entities is 12 million tests per frame. A spatial hash buckets entities into square cells so a query only looks near the point.

Build one that you rebuild every frame: clear(), then insert(x, y) for each entity (the returned id is the insertion index 0, 1, 2...), then query(x, y, r) returns the ids of all entities whose distance to (x, y) is at most r (exact distance, not whole cells). Coordinates can be negative. Order of results is unspecified.

Zig version: a fixed number of buckets with an intrusive linked list (heads[bucket], next[id]), so no allocation. Different cells can share a bucket, so skip entities whose cell is not the one you are visiting, or you will return duplicates. The tests use very few buckets to force collisions. C++ version: use an unordered_map keyed by the cell.

Starter (Zig):

const std = @import("std");

pub fn SpatialHash(comptime max_entities: usize, comptime buckets: usize) type {
    return struct {
        const Self = @This();

        cell: f32,
        heads: [buckets]i32 = @splat(-1), // bucket -> newest entity id, or -1
        next: [max_entities]i32 = undefined, // entity id -> next entity in the same bucket, or -1
        xs: [max_entities]f32 = undefined,
        ys: [max_entities]f32 = undefined,
        n: usize = 0,

        pub fn init(cell: f32) Self {
            return .{ .cell = cell };
        }

        pub fn clear(self: *Self) void {
            _ = self;
        }

        /// returns the new entity's id (0, 1, 2, ...)
        pub fn insert(self: *Self, x: f32, y: f32) u32 {
            _ = self;
            _ = x;
            _ = y;
            return 0;
        }

        /// writes matching ids into out (at most out.len of them) and returns how many
        pub fn query(self: *const Self, x: f32, y: f32, r: f32, out: []u32) usize {
            _ = self;
            _ = x;
            _ = y;
            _ = r;
            _ = out;
            return 0;
        }
    };
}

Answer key

1. Spatial hash grid for neighbour queries back ↑

Hint: cell coordinate = floor(v / cell) (floor, not truncation, or negative coordinates land in the wrong cell). To query: loop cells from floor(x - r) to floor(x + r) on both axes, walk each bucket, re-check the entity actually sits in that cell, then do the exact distance test.

Choose a cell size near the typical query radius (or the largest entity). Too small and queries visit many empty cells, too large and each cell holds too many entities. Alternatives: a quadtree (uneven density), sweep and prune (mostly 1D motion), or just the engine broadphase (Godot, Box2D and Jolt already do this). Hashing (cx, cy) with large primes and a modulo is the classic scheme from "Optimized Spatial Hashing for Collision Detection of Deformable Objects".

2. Spot the update-loop bugs (C++) back ↑

Hint: One is an allocation, one is quadratic, one is an iterator invalidation.

  • Line 3: A std::string is built (and allocated) for every enemy every frame, just to pass as a label. Build it once at spawn or pass the id.
  • Line 5: Every enemy tests every other enemy: O(n²). With 2,000 enemies that is four million distance checks per frame. Use a spatial hash or grid and query only the neighbours.
  • Line 8: Erasing from the vector while iterating it with a range-for invalidates the iterator: undefined behaviour or a crash. Mark dead enemies and remove them after the loop (or swap-remove with an index loop).

3. Quick check back ↑

B. The worst-case frames (99th percentile or spikes), usually caused by allocation, GC, loading or a periodic task

Averages hide hitches. Capture a frame-time graph and investigate the spikes: collection pauses, asset loads on the main thread, or one system doing a big batch every N frames (spread it out).

4. Quick check back ↑

B. Bucket enemies into a grid/spatial hash and query neighbouring cells

Spatial partitioning turns the all-pairs O(n²) into roughly O(n × neighbours). It is the biggest single win for crowds.

5. Check 1 back ↑

B. Preallocate a pool of bullets once and hand slots out and back, dropping or recycling the oldest when full

A pool removes per-frame allocation from the hot loop; dropping a bullet on overflow beats a hitch.

6. Check 2 back ↑

A. Build the label once at spawn and bucket enemies into a spatial grid so each queries only neighbours

Hoist per-frame allocation out of the loop and replace the O(n-squared) all-pairs check with a spatial query.
