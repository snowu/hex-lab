Deterministic lockstep and rollback

Send only inputs and make every machine compute the same world: how RTS games and fighting games work, and what determinism demands.

The idea

If two machines start from the same state and apply the same inputs in the same order with a deterministic simulation, they end in the same state, with no need to send the state. A game with 1,000 units sends only a few bytes of commands per player per tick. This is why real-time strategy games (Age of Empires, StarCraft) with thousands of units are networked this way, and why replays are tiny.

Lockstep

Every tick, each player's input is sent to all others. The simulation advances to tick t only when it has the inputs of every player for tick t. Commands are scheduled to execute a few ticks in the future (input delay) so there is time for them to arrive. Consequences: the whole game runs at the speed of the slowest connection, one stalled player pauses everyone, and the delay between clicking and the action happening is the input delay (RTS players accept 100 to 200 ms; a fighting game cannot).

Rollback netcode

Fighting games need zero perceived input delay. Rollback (GGPO, popularised for fighting games; used by Street Fighter, Skullgirls and many others) predicts instead of waiting:

  1. Each frame, run the simulation immediately with your input and a guess for the opponent's (usually "same as their last input").
  2. Save the game state every frame in a ring buffer.
  3. When the real input for a past frame arrives and it differs from the guess: roll back to the saved state of that frame, apply the correct input, and re-simulate all frames up to the present, fast and invisibly.
  4. Corrections are usually tiny (a character shifts a pixel); with low latency they are rare.

It feels like playing offline, at the cost of: the game being able to re-simulate several frames in one frame's time (so the simulation must be cheap), cheap state save/load, and effects (sounds, particles) that must not fire twice when frames are replayed.

const std = @import("std");

/// A tiny deterministic game: two players push a counter around. The state is small and plain data, so saving it is a copy.
const State = struct {
    frame: u32 = 0,
    x: [2]i32 = .{ 0, 0 },
    score: u32 = 0,

    fn step(self: *State, inputs: [2]i8) void {
        for (0..2) |p| self.x[p] += inputs[p];
        if (self.x[0] == self.x[1]) self.score += 1; // an "event" that depends on both players
        self.frame += 1;
    }
};

const MAX_ROLLBACK = 8;

const Rollback = struct {
    state: State = .{},
    saved: [MAX_ROLLBACK]State = undefined, // saved[f % MAX] is the state at the START of frame f
    used: [MAX_ROLLBACK][2]i8 = undefined, // the inputs we actually simulated that frame (with guesses)
    resimulated: u32 = 0,

    fn advance(self: *Rollback, local: i8, remote_guess: i8) void {
        const f = self.state.frame;
        self.saved[f % MAX_ROLLBACK] = self.state;
        self.used[f % MAX_ROLLBACK] = .{ local, remote_guess };
        self.state.step(.{ local, remote_guess });
    }

    /// The real remote input for an old frame arrived. If it differs from our guess, rewind and replay.
    fn correct(self: *Rollback, frame: u32, real_remote: i8) void {
        const slot = frame % MAX_ROLLBACK;
        if (self.used[slot][1] == real_remote) return; // guessed right: nothing to do
        const now = self.state.frame;
        self.used[slot][1] = real_remote;
        self.state = self.saved[slot]; // roll back
        var f = frame;
        while (f < now) : (f += 1) {
            self.saved[f % MAX_ROLLBACK] = self.state;
            self.state.step(self.used[f % MAX_ROLLBACK]); // replay with the corrected input
            self.resimulated += 1;
        }
    }
};

test "rolling back and replaying gives exactly the state of a game that had the real input all along" {
    const local = [_]i8{ 1, 1, 0, 1, 1, 0, 0, 1 };
    const remote = [_]i8{ 0, 1, 1, 1, 0, 1, 1, 0 }; // what the remote player really pressed

    // the "ground truth": a simulation that knew every input in time
    var truth = State{};
    for (0..8) |i| truth.step(.{ local[i], remote[i] });

    // the rollback client: guesses "remote repeats its last input" (starting from 0), corrected as real inputs arrive late
    var rb = Rollback{};
    var last_real: i8 = 0;
    for (0..8) |i| {
        rb.advance(local[i], last_real);
        if (i >= 2) { // the real input for frame i-2 arrives two frames late
            rb.correct(@intCast(i - 2), remote[i - 2]);
            last_real = remote[i - 2];
        }
    }
    rb.correct(6, remote[6]);
    rb.correct(7, remote[7]);

    try std.testing.expectEqual(truth, rb.state);
    try std.testing.expect(rb.resimulated > 0); // it really did rewind at least once
}

What determinism demands

  • Same inputs, same order, same step: fixed timestep, inputs applied by tick number, never by wall-clock arrival.
  • Seeded random numbers: one RNG in the simulation, advanced only by simulation code (the procgen lesson). A particle effect that draws from it desyncs the game.
  • No uninitialised memory, no pointer addresses, no hash-map iteration order in anything that affects state; iterate in a defined order (sort by id).
  • Floating point: results can differ between CPUs, compilers and optimisation flags (fused multiply-add, x87 vs SSE, different libm). Safe options: fixed-point integers for the simulation (most RTS and fighting games), or the same binary and strict flags on identical architectures. Never assume that a float simulation on a phone matches a PC.
  • No dependence on frame rate, locale, thread timing or filesystem order.
  • Everything that influences the simulation is part of the state that gets saved and checksummed.

Desyncs

When two machines drift apart (a "desync"), everything after is garbage and it is silent. Detect it by exchanging a checksum of the state every few frames; when they differ, log the frame and dump the state to find the first divergent value. Replays that diverge on playback are the same bug.

Choosing a model

GameFitsWhy
RTS with thousands of unitsLockstepState is huge, inputs are tiny; delay tolerated
Fighting game, 2 playersRollbackZero input delay matters; state is small
Shooter with many players, cheating a concernAuthoritative server + predictionServer owns the truth; clients cannot be trusted
Turn-based or card gameSimple request/response to a serverLatency hardly matters
Co-op physics gameHost authority + interpolationFloating-point physics is not deterministic across machines

Answer key

1. Quick check back ↑

B. A source of non-determinism: floating point differences, a shared RNG advanced by non-simulation code, or hash-map ordering

Lockstep only sends inputs. Any difference in how the simulation computes the result makes the states diverge, and nothing in the network layer will notice.

2. Quick check back ↑

B. The game restores the saved state of frame 100, applies the real input and re-simulates frames 100 to 103 immediately

That is the rollback: load the state, correct the input, fast-forward back to the present within one frame's time.

3. Quick check back ↑

B. Re-simulated frames would trigger them again; effects must be tied to confirmed events or de-duplicated

Replaying frames re-runs game logic, which would re-emit effects. Cosmetic output must be decoupled from the replayed simulation.

4. Check 1 back ↑

B. The simulation advances to a tick only when every input for that tick has arrived, so the slowest connection sets the pace

Lockstep trades bandwidth for synchrony: no machine may run ahead of the slowest input.

5. Check 2 back ↑

D. Use fixed-point integers for the simulation, or identical binaries and strict flags on identical architectures

Floating-point results can differ across CPUs and compilers, so deterministic games avoid relying on them.
