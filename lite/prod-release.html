Shipping and operating a game

Build targets, stores, saves across versions, telemetry and crash reports, community, and what to do after launch.

Shipping is a feature

A game is finished when someone else can run it. Getting there involves a surprising amount of work that is not gameplay, and it is cheaper if you do a little of it from the first week: export a build early and often (the checklist in the practice lesson), test it on a machine that is not yours, and treat "does the exported build work" as a daily check, not a final step.

Targets

  • Web (HTML5/WebAssembly): zero install, perfect for jams and portfolios; hosted on itch.io, GitHub Pages or your own site. Watch download size (compress, strip unused), audio autoplay rules, threading needs (some engines need special HTTP headers for threads), mobile browser performance.
  • Desktop (Windows, Linux, macOS): an executable plus data. Windows and macOS warn about unsigned programs; code signing and notarisation avoid it (and cost money and effort). Test on a clean user account.
  • Mobile: store requirements, touch controls, battery and thermal limits, many screen sizes, background/foreground transitions (save when the app is paused).
  • Consoles: platform holder programs, development kits, certification requirements. Plan months, not days, and consider a porting partner.

Distribution

  • itch.io: the easiest place to publish: free or paid, web and downloads, jams, pay-what-you-want, a page and devlog. A great first release venue.
  • Steam and other stores: a bigger audience and more requirements: store page assets (capsule art, screenshots, trailer), a fee, reviews and a wishlist system that matters a lot. Build a wishlist audience before launch.
  • Your own site with a download or a web build is always an option.

The things a store page needs

A clear one-sentence pitch, 4 to 6 good screenshots that show gameplay (not menus), a short trailer or GIFs of the core loop in the first seconds, an honest description with controls, system requirements, and a content/age note. You will spend as long on this as on a feature.

Saves across versions

Once players have saves, you are bound to them (the save-file lesson): a version number, migrations that are only ever appended, tests with old save fixtures, backups before migrating, and never crash on a newer-version save (tell the player to update). A broken save after an update is the fastest way to lose trust. For web builds, saves in the browser's storage can be cleared by the player or the browser: offer export/import.

Telemetry and crash reports (respect the player)

  • Crash reports: capture a stack trace, build number, platform and a few breadcrumbs. Ask consent. Services exist (Sentry and others), and a simple "send log" button works for a small game.
  • Telemetry: anonymous, minimal and optional events answer design questions: where do players quit, which level has the most deaths, what do they buy. Decide the questions first, collect the least data that answers them, document it in a privacy policy, and obey the law that applies (GDPR, consent for children).
  • Never collect what you do not need, and never log secrets or personal data in crash reports.

Versioning and patching

  • Version builds (1.2.3 or a date) and show the version in the game, so bug reports name it.
  • Keep a changelog and patch notes players can read.
  • For web builds, cache busting and an "update available" notice avoid players running an old cached build.
  • Keep old builds available for reproducing bugs and rolling back.

Community and feedback

A place to talk (Discord, forums), a bug report path with a template (version, steps, a replay or log), and a habit of replying. Players who report bugs are your best testers: make it easy and thank them. Be honest about what you will and will not change.

After launch

  • The first days decide most: fix the crash and progression-blocking bugs immediately.
  • Retention (do they come back on day 1, day 7) matters more than downloads; look at where players leave.
  • Do a postmortem: what went right, what went wrong, what you would do differently, with numbers (time per feature, estimates vs actuals, wishlists, sales). Write it down, even privately.

Legal and ethical basics

  • Licenses of everything you ship: code, art, fonts, sound, music, engine. Keep a credits file. Check what "free" assets allow (commercial use, attribution, modification).
  • Privacy policy if you collect any data; age ratings where stores need them.
  • Paid random rewards (loot boxes) are regulated or banned in some countries and need disclosed odds on most platforms; design monetisation you would defend to a player.
  • Accessibility options (remapping, text size, colour-blind modes, reduced motion) are both good design and increasingly expected.

Exercise: a one-page launch plan for a jam game

  1. Target: web build on itch.io plus a Windows/Linux download.
  2. Page: one-line pitch, 4 screenshots, a 15-second GIF of the core loop, controls, credits and licenses.
  3. Safety: version in the corner, a "send log" or report link, save export/import.
  4. Checks: run the exported build on a clean browser profile and another computer; test audio start after the first click; resize the window; play on a laptop trackpad.
  5. After: reply to the first ten comments, fix the top two bugs, write a short postmortem.

Answer key

1. Quick check back ↑

B. A save version number with an appended migration step, a backup of the old file, tests with old fixtures, and a graceful message for saves from a newer build

Players' progress is the most valuable data you hold. Migrations must be tested and non-destructive.

2. Quick check back ↑

B. Anonymous, optional events such as "tutorial step reached" and "quit at step", documented in a privacy policy

Collect the least data that answers a specific question, anonymously, with consent where required.

3. Quick check back ↑

B. Exporting a build early and often, and testing it on a clean machine

Export problems (missing files, paths, performance) only appear in real builds. Finding them early makes them cheap.

4. Check 1 back ↑

C. Cache busting plus an in-game update-available notice so players reload the new build

Web caches hold onto old files; versioned URLs and an explicit notice move players forward.

5. Check 2 back ↑

A. That free means commercial use, attribution, and modification rights all allow your use, and record it in a credits file

Free covers many different licenses; keep a credits file and verify each asset allows your exact use.
