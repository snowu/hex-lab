Indexes and query plans

Composite order, covering and partial indexes, and reading EXPLAIN.

An index is a sorted copy of some columns (usually a B-tree) that lets the database jump to rows instead of scanning the table. It speeds reads and slows writes, costs disk and memory, and only helps if the planner can use it.

Choosing the columns

  • Composite order: equality columns first, then the range/sort column. An index on (a, b) helps queries on a, or a and b, but not b alone (the leftmost prefix rule).
  • Selectivity: an index on a column with two values (boolean) rarely helps. High-cardinality columns do.
  • Covering index (Postgres INCLUDE): holds every column the query needs, so the table is never touched (index-only scan).
  • Partial index: ... WHERE status = 'failed' indexes only the interesting rows. Small and fast. Also enables partial UNIQUE constraints.
  • Expression index: (lower(email)) to support case-insensitive lookups.

Why the planner ignores your index

  • A function on the column: WHERE date(created_at) = ... (index the expression, or rewrite as a range).
  • Leading wildcard: LIKE '%abc'.
  • Implicit type cast, or a mismatched collation.
  • Low selectivity: reading most of the table by index is slower than a sequential scan, so the planner chooses the scan, correctly.
  • Stale statistics: run ANALYZE.

Reading a plan

In Postgres use EXPLAIN (ANALYZE, BUFFERS) and compare estimated vs actual rows: large gaps mean bad statistics. Seq Scan reads the table, Index Scan follows the index to the table, Index Only Scan never touches the table, Bitmap Heap Scan combines index results. In the exercises below you will see SQLite's version, EXPLAIN QUERY PLAN.

In production: create indexes with CREATE INDEX CONCURRENTLY (does not block writes, cannot run inside a transaction, leaves an INVALID index if it fails), and drop unused indexes found via pg_stat_user_indexes.

Answer key

1. Index the hot query back ↑

Hint: A composite index is sorted by its first column, then by the second within each first value. Put the column you compare with = first (merchant_id) and the one you range over and sort by second (created_at). Then rows for one merchant are already in created_at order.

Reference solution:

CREATE INDEX idx_payments_merchant_created ON payments (merchant_id, created_at);

Rule of thumb for composite indexes: equality columns, then the sort/range column. An index on (created_at, merchant_id) can also avoid the sort, but it walks the rows of every merchant in the date range and filters afterwards, which is far more work on a big table. Separate single-column indexes would force a sort or a bitmap merge. Every index also slows writes and costs disk, so add them deliberately.

2. A covering index back ↑

Hint: Searching and sorting columns first (merchant_id, created_at), then append every other column the query needs to return (amount_minor). In Postgres you can use INCLUDE (amount_minor) to add it without making it part of the sort key.

Reference solution:

CREATE INDEX idx_payments_cover ON payments (merchant_id, created_at, amount_minor);

Covering indexes trade write cost and size for avoiding table lookups. In Postgres, index-only scans also need the visibility map to be fresh, so VACUUM matters.

3. A partial index back ↑

Hint: CREATE INDEX name ON payments (columns) WHERE status = 'failed'. The query's own WHERE clause must imply the index predicate for the planner to use it. Index merchant_id then created_at, as before.

Reference solution:

CREATE INDEX idx_payments_failed ON payments (merchant_id, created_at) WHERE status = 'failed';

Partial indexes shine for skewed data (failed, pending, unprocessed, soft-deleted rows) and for partial UNIQUE constraints such as "one active subscription per customer". Postgres supports the same syntax.

4. Quick check back ↑

B. WHERE merchant_id = ? AND created_at >= ?

A composite index is usable from its leftmost column onward. Querying only the second column cannot jump into the tree, and a function on the column defeats the index.

5. Quick check back ↑

B. No: 95% of rows match, so a scan is cheaper. (A partial index on the rare value, WHERE is_active = false, can be great.)

Low selectivity means the index would point at nearly the whole table. The planner will choose a sequential scan. Index the rare value instead.

6. Check 1 back ↑

B. Rewrite the predicate as a range on created_at or add an expression index, because a function on the column prevents index use

Wrapping the column in a function hides its order from the planner; index the expression or leave the column bare.

7. Check 2 back ↑

C. That statistics are stale, so run ANALYZE and compare again, because large estimate gaps mean the planner chose from bad inputs

A huge estimated-versus-actual gap points at bad statistics; the planner can only pick well when ANALYZE is fresh.
