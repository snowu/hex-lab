UI, HUD and text

Layout that survives every screen size, text that stays readable, and interfaces usable with a pad, a thumb or a screen reader.

UI is a different kind of rendering

Game worlds move with the camera; UI is attached to the screen. Engines keep it separate (Godot: CanvasLayer and Control nodes) so camera movement, zoom and shake do not affect it. The challenges are not about drawing but about adapting: to resolution, aspect ratio, language, input device and the player's abilities.

Layout that adapts

  • Anchors and containers. Pin elements to the edges or corners (health bar top-left, minimap top-right) with margins, instead of absolute pixel positions. Containers (horizontal and vertical boxes, grids, margins) arrange children and resize to content, so adding a button does not require moving others.
  • Safe areas. Phones have notches and rounded corners; TVs overscan. Keep important UI inside the safe area.
  • Scale policy. Either scale the whole UI with the screen (pixel art, consistent look) or keep sizes in physical units and add room (readable on phones and desktops). Decide early and test the extremes: 16:9, ultrawide 21:9, a tall phone, and a tiny window.
  • Touch targets. About 44 to 48 logical pixels (roughly 9 mm), with space between them. Place thumb-reachable actions near the bottom corners.

Text rendering

  • Bitmap fonts: each glyph is a pre-drawn image; crisp at its native size and perfect for pixel art when drawn at an integer scale. Cheap, but one size per font.
  • Vector fonts rasterised at runtime: any size, good quality, more CPU and memory (glyph cache). Keep the number of sizes small.
  • Signed distance field (SDF) fonts: a texture stores the distance to the glyph edge, and a shader reconstructs a sharp edge at any scale and gets outlines and glows for free. Great for text that scales (3D and zooming), with some blurring of very small text.
  • Readability: contrast against any background (add an outline or a backing panel), generous line height, no all-caps paragraphs, text size scaled to the viewing distance (TV games need much larger text).

Localisation

  • Never concatenate sentences from pieces; word order differs. Use format strings with named placeholders ("{player} defeated {enemy}") and let translators reorder.
  • Text expands: German and Finnish are often 30% longer than English. Let layouts grow, and test with a pseudo-language that adds 40% length and accented characters.
  • Plurals, numbers, dates and currency follow locale rules; right-to-left languages mirror the layout; CJK needs large font files and different line-breaking.
  • Keep text in tables keyed by id, not in code and images.

Input and navigation

  • Every screen must be fully usable by gamepad and keyboard: define focus order, make the focused element obvious, and remember the last focused item when returning.
  • Show the correct button prompts for the device in use (and switch live when the player switches device).
  • Never rely only on hover.

Accessibility

  • Colour is not information alone: add shapes, icons or text to red/green states. Provide a colour-blind friendly palette or filter.
  • Remappable controls, hold-vs-toggle options, adjustable text size, subtitles with speaker names and backgrounds, and options to reduce screen shake, flashing and motion.
  • Difficulty and assist options are an accessibility feature too.
  • Check contrast ratios (aim for at least 4.5:1 for normal text).

HUD design

  • Show only what the player needs now; hide the rest or show it contextually.
  • Put information where the eyes already are: damage numbers near the hit, ammo near the weapon, health near the character in a tight action game.
  • Use change to draw attention: a health bar that animates (a trailing bar that shows what was just lost) communicates more than a number.
  • Keep it stable: elements should not jump around as values change width. Use monospaced digits or fixed-width containers.

Performance

  • UI often has many small textures and text pieces; batch with an atlas and avoid re-laying-out every frame (only when data changes: a dirty flag again).
  • Beware of per-frame string formatting and allocation ("%d/%d" % [hp, max] only when the value changes).
  • Large translucent panels are overdraw.

Answer key

1. Quick check back ↑

B. Let the button grow to its content (container layout) and test layouts with a longer pseudo-language

Text length varies by language. Layouts must adapt rather than assume English lengths.

2. Quick check back ↑

B. Many players cannot distinguish red and green; add a shape, icon or outline difference

Roughly 8% of men have red-green colour vision deficiency. Redundant coding (colour plus shape) fixes it.

3. Quick check back ↑

B. Word order and plural forms differ between languages; use a translatable template with named placeholders and plural rules

Translators need whole sentences with placeholders so they can reorder and inflect.

4. Check 1 back ↑

D. Anchor elements to edges and corners with margins, arrange with containers, and keep important UI inside the safe area

Anchors and containers adapt to size and aspect instead of assuming one screen. Safe areas avoid notches and overscan.

5. Check 2 back ↑

B. Signed distance field fonts for text that scales, and bitmap fonts at integer scale for the pixel-art dialogue

SDF reconstructs sharp edges at any scale with outlines and glows; bitmap is crisp only at its native integer size.
