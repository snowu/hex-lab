Local-first apps and cross-device sync

Save locally first, sync with compare-and-swap, never silently overwrite.

Local-first means the app works fully offline, writes to local storage immediately, and treats the cloud as optional sync. It is faster, more resilient, and the user never loses progress to a network error.

The coordinator pattern

  1. Save locally, synchronously at every save point. This must never depend on the network.
  2. Mark the snapshot dirty; debounce an upload (seconds), and flush at reliable checkpoints. Do not rely on beforeunload for network calls.
  3. Hash the serialised snapshot and skip uploads that changed nothing.
  4. Retry with backoff when offline; show a quiet status (“Saved on this device”, “Synced”).

Ordering with a server-side generation

Every cloud row has a monotonic generation controlled by the server. An upload says “I am replacing generation N”. The database applies it only if N is still current (UPDATE ... WHERE generation = N), otherwise it reports a conflict. The server, not a device clock, decides the order, and a stale device is told rather than allowed to overwrite newer data. This is compare-and-swap, the same idea as If-Match.

Conflicts

  • Last write wins by timestamp loses data and trusts clocks that disagree. Avoid it for anything valuable.
  • Never auto-pick “the bigger one” (more XP, higher level, later day): any of those can legitimately go backwards.
  • When both sides changed since the last sync, show both and let the person choose (continue this device / use the cloud / keep offline).
  • Field-level merge or CRDTs work when data has no cross-field invariants (collaborative text, counters). For a snapshot with invariants, merge only if you can prove they hold.
  • Never replace state that is in active use (mid-game, mid-edit). Resolve at a safe point.

Details that bite

  • Resetting must also go through the sync path, or an older cloud snapshot comes back on the next load.
  • A stale client (older format) must not overwrite a newer format: store a format/schema version and enforce it server-side.
  • Persist a random device id separately from the data. Reconcile on account switch rather than uploading the previous account’s data.
  • Be careful with strict constraints on columns clients write (an over-tight regex on a hash broke real installs once). Keep integrity limits to what you must enforce, such as a payload size cap.
  • Installed web apps (PWAs) keep running old code: keep a compatibility shim for the previous API shape until old clients are gone.
  • Passwordless sign-in by typed email code works across devices; magic links may not.

Service workers and storage

A service worker intercepts fetches to serve cached assets offline (cache-first for static files, network-first or stale-while-revalidate for data). localStorage is synchronous and small (a few MB); use IndexedDB for larger data. Browsers may evict storage under pressure unless you request persistence.

Answer key

1. Compare-and-swap cloud saves back ↑

Hint: Keep rows = {user: {state, generation, format_version, content_hash}}. Follow the five rules in order: missing row first, then the format check, then the unchanged check, then the generation check, then the update. Deep-copy the state on the way in.

Reference solution:

import copy

class SaveStore:
    def __init__(self):
        self.rows = {}

    def save(self, user, expected_generation, state, format_version, content_hash):
        row = self.rows.get(user)
        if row is None:
            if expected_generation is not None:
                return {'status': 'conflict', 'generation': None}
            self.rows[user] = {'state': copy.deepcopy(state), 'generation': 1, 'format_version': format_version, 'content_hash': content_hash}
            return {'status': 'ok', 'generation': 1}
        if format_version < row['format_version']:
            return {'status': 'stale_client', 'generation': row['generation']}
        if row['content_hash'] == content_hash:
            return {'status': 'unchanged', 'generation': row['generation']}
        if expected_generation != row['generation']:
            return {'status': 'conflict', 'generation': row['generation']}
        row.update(state=copy.deepcopy(state), generation=row['generation'] + 1, format_version=format_version, content_hash=content_hash)
        return {'status': 'ok', 'generation': row['generation']}

    def load(self, user):
        row = self.rows.get(user)
        return copy.deepcopy(row['state']) if row else None

In Postgres this is a function that does the same update with WHERE generation = $expected, so the check and the write are one atomic statement. The key properties: the server decides ordering, a stale device is told rather than allowed to flatten newer data, and identical uploads cost nothing. Do not resolve a real conflict automatically by timestamps or by "bigger number wins": let the person choose.

2. Decide what a sync should do back ↑

Hint: Handle the three easy cases first (no cloud, no local, equal hashes). Then compute the two booleans and return based on the four combinations. Note that the conflict case must never auto-resolve.

Reference solution:

def decide_sync(local_hash, last_synced_hash, last_generation, cloud):
    if cloud is None:
        return 'none' if local_hash is None else 'upload'
    if local_hash is None:
        return 'download'
    if local_hash == cloud['hash']:
        return 'none'
    local_changed = local_hash != last_synced_hash
    cloud_changed = last_generation is None or cloud['generation'] != last_generation
    if local_changed and cloud_changed:
        return 'conflict'
    if local_changed:
        return 'upload'
    if cloud_changed:
        return 'download'
    return 'none'

This is the three-way comparison at the heart of every sync engine (git does the same with a merge base). Comparing hashes instead of timestamps avoids device clock skew. A real client also refuses to apply remote state during a critical section, and offers an explicit "keep this device / use the cloud" choice on conflict.

3. Spot the sync bugs back ↑

Hint: One line trusts something that cannot be trusted to order events. The other replaces data nobody agreed to replace.

  • Line 3: Decides by comparing wall-clock timestamps from different devices. Clocks disagree, and a newer timestamp does not mean more or better progress. Compare content hashes and generations, and only the server’s generation orders writes.
  • Line 4: Overwrites local state silently, even if it has unsynced changes (and possibly while it is in use). If both sides changed, this destroys the local progress. A real conflict needs an explicit choice at a safe moment.
