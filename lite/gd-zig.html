Zig for game programming

A fast tour of the Zig features games care about (explicit allocators, comptime, optionals, errors, packed data) and how to build a game with it.

Why Zig for games

  • No hidden allocation or control flow. If it allocates, it takes an allocator parameter. If it can fail, the type says so. Perfect for frame-budget thinking and for arena allocators (one per frame or per level, freed in one go).
  • comptime: generic code and tables built at compile time, without a separate template language. Containers like ArrayList are ordinary functions that return types.
  • C interop is first class: @cImport and a build system that compiles C and C++ too. SDL, raylib, sokol and stb are one dependency away.
  • Safety in Debug, speed in Release: bounds checks, overflow checks and use of undefined memory are caught in Debug and Safe builds; ReleaseFast removes them.
  • Tests are part of the language: test "name" { ... } blocks in the same file, run with zig test. That is what the drills use.
Zig is pre-1.0. The language and standard library still change between releases (this lab is written and compiled against 0.17.0). When an online example does not compile, check its Zig version first. Pin a version per project in your README or build tooling.

Structs, methods and optionals

const std = @import("std");

const Enemy = struct {
    hp: i32,
    pos: [2]f32,

    fn hit(self: *Enemy, dmg: i32) bool {   // *Enemy: may modify
        self.hp -= dmg;
        return self.hp <= 0;
    }
};

pub fn main() !void {
    var e = Enemy{ .hp = 10, .pos = .{ 0, 0 } };
    std.debug.print("dead? {}\n", .{e.hit(12)});
}

Values that may be absent are optionals (?T), unwrapped with if (x) |v| ... or x orelse default. There are no null pointers by default, so a whole class of crashes is a compile error.

Tagged unions: state and shapes in one type

const Shape = union(enum) {
    circle: f32,
    rect: struct { w: f32, h: f32 },

    fn area(self: Shape) f32 {
        return switch (self) {            // the compiler checks every case is handled
            .circle => |r| std.math.pi * r * r,
            .rect => |r| r.w * r.h,
        };
    }
};

This is the natural way to model game states, AI actions, events and commands: each variant carries only its own data.

Errors are values

const LoadError = error{ NotFound, Corrupt };

fn loadLevel(name: []const u8) LoadError!u32 { ... }

const lvl = loadLevel("forest") catch |err| {
    std.debug.print("failed: {}\n", .{err});
    return;
};
// or propagate: const lvl = try loadLevel("forest");

Allocators and defer

fn sumFrames(allocator: std.mem.Allocator, count: usize) !u64 {
    const frames = try allocator.alloc(u64, count);
    defer allocator.free(frames);              // runs when the scope ends, on every path
    for (frames, 0..) |*f, i| f.* = i * i;
    var total: u64 = 0;
    for (frames) |f| total += f;
    return total;
}

In tests pass std.testing.allocator: it fails the test when you leak. In a game, hand your systems an arena for per-frame scratch memory and reset it every frame, or use fixed-capacity types (like the pools and sparse sets in the drills) so nothing allocates after startup.

comptime generics

fn Pool(comptime T: type, comptime n: usize) type {
    return struct {
        items: [n]T = undefined,
        used: [n]bool = @splat(false),
        fn acquire(self: *@This()) ?*T { ... }
    };
}
var bullets = Pool(Bullet, 256){};

Building a game

You do not need an engine to learn the fundamentals: open a window, run the fixed-timestep loop from the first lesson, draw rectangles, read input. Libraries that fit Zig well (check each one's README for the Zig version it targets):

  • raylib (simple C library, great for learning; raylib's own repo ships a build.zig and there are community Zig bindings),
  • SDL3 (windowing, input, audio, GPU; build integrations exist for Zig),
  • sokol (small cross-platform headers with Zig bindings, nice for web via WASM),
  • Mach (a game engine and toolkit written in Zig).

Plan: do the Zig drills, then recreate Pong with the fixed timestep and AABB overlap code you wrote, then Breakout using the swept test.

Extra exercise: a free-list pool in Zig

The Pool in this lesson scans for a free slot (O(n)). Rewrite it with a free list: keep next_free: [n]u32 and a head, so acquire and release(ptr) are both O(1). Write tests: acquiring more than n returns null; releasing then acquiring reuses the slot; double release is detected in Debug builds (std.debug.assert).

Answer key

1. Quick check back ↑

B. It may allocate (through the allocator you pass) and may return an error, and the caller owns and must free the returned bytes

No hidden allocation: allocation needs an allocator parameter. The ! means it can fail. Ownership of the returned buffer is by convention the caller's; read the doc comment to confirm.

2. Quick check back ↑

B. It schedules the free to run at the end of the enclosing scope on every exit path, including early returns and errors

defer keeps acquire and release next to each other, which avoids the classic early-return leak. errdefer runs only when the function exits with an error.

3. Quick check back ↑

B. Exhaustiveness: forgetting a variant is a compile error, and each branch can capture only its own payload

Add a variant and every switch that does not handle it stops compiling, so state machines and event handlers cannot silently ignore a new case.

4. Check 1 back ↑

A. Hand the system an arena for per-frame scratch and reset it once per frame

Arenas match frame lifetimes: many quick allocations, one reset, and the test allocator still catches real leaks.

5. Check 2 back ↑

B. As an optional ?T, unwrapped with if (x) |v| or orelse, so absence is explicit in the type

Optionals make absence visible to the compiler with no null pointers by default, unlike hidden sentinel conventions.
