Postgres in production

Pooling, replicas, migrations without downtime, pagination, N+1.

Connections

Each Postgres connection is a server process using several MB of memory, so thousands of direct connections fall over. Put a pooler (PgBouncer, RDS Proxy) in front. In transaction pooling mode a connection is lent for one transaction, so session state (SET, session-level advisory locks, historically prepared statements) is unreliable. Size the pool from the database's capacity, not from the number of app instances.

Replicas and lag

Streaming replicas serve reads, but replication is asynchronous: a user can write, then read stale data. Use read-your-writes routing (read from the primary for a short window after a write, or track the commit position), and monitor lag. Replicas also fail over, but promotion loses unreplicated writes unless you use synchronous replication.

Zero-downtime migrations (expand / contract)

  1. Expand: add the new column as nullable (or with a constant default, which is instant since PG 11). Never a volatile default on a big table: it rewrites the whole table.
  2. Backfill in small batches with pauses, never in one giant transaction.
  3. Deploy code that writes both, then reads the new one.
  4. Contract: add constraints safely (ADD CONSTRAINT ... NOT VALID, then VALIDATE CONSTRAINT), set NOT NULL once a validated check proves it, then drop the old column in a later release.
  • CREATE INDEX CONCURRENTLY instead of a blocking build.
  • Set lock_timeout on migrations so a DDL statement waiting for a lock cannot queue behind a long transaction and block every query behind it.

Pagination and the N+1 trap

  • OFFSET 100000 reads and discards 100,000 rows, and shifts when rows are inserted. Use keyset pagination: WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20 with a matching index.
  • N+1: one query for a list, then one per row. Fix with a join, WHERE id = ANY($1), or the ORM's eager loading.

Other things worth naming

  • Autovacuum and bloat: MVCC leaves dead rows; long-running transactions stop cleanup. Watch for idle-in-transaction sessions.
  • Partitioning (by time) for huge tables: pruning speeds queries, and dropping an old partition is instant.
  • Backups: base backup plus WAL archiving gives point-in-time recovery. A backup you have never restored is not a backup.
  • Observability: pg_stat_statements for the slowest queries, plus locks, replication lag and connection saturation.

Answer key

1. Spot the database anti-patterns back ↑

Hint: One line gets slower the further you page. The other runs once per row.

  • Line 2: OFFSET pagination reads and throws away every earlier row, so deep pages get slower and slower. And with a non-unique created_at as the only sort key, rows can repeat or vanish between pages. Use keyset pagination on (created_at, id).
  • Line 4: The classic N+1: one extra query per row (20 round trips for one page). Join the merchants table, or fetch all merchants with one WHERE id = ANY(...) query.

2. Quick check back ↑

A. ALTER TABLE ... ADD COLUMN x int NOT NULL DEFAULT 0 (a constant default is metadata-only since Postgres 11), after setting lock_timeout

Adding a column with a constant default does not rewrite the table in modern Postgres, so it is near-instant. A volatile default (like random() or clock_timestamp()) would rewrite everything. Always set lock_timeout so the DDL cannot queue behind long transactions.

3. Quick check back ↑

B. Replication lag: route reads to the primary for a short window after a write (or until the replica has caught up to the write’s position)

Asynchronous replication means a replica can briefly be behind. Read-your-writes routing is the standard fix.

4. Quick check back ↑

B. Put a connection pooler in front (PgBouncer/RDS Proxy) and cap pool sizes

Each connection is a process with real memory and scheduling cost. A pooler multiplexes many app connections onto a small number of server connections.

5. Check 1 back ↑

D. Use keyset pagination on (created_at, id) with a matching index, passing the last seen position as the cursor

OFFSET reads and discards earlier rows and shifts under inserts; a keyset seeks directly to the cursor and stays stable.

6. Check 2 back ↑

A. Join merchants in the main query or fetch all needed merchants with one WHERE id = ANY query

One query per row means 20 round trips per page; a join or a single batched lookup removes the N+1.
