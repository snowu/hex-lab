From state machines to behaviour trees

Why hand-wired state machines stop scaling, and how a tree of small reusable nodes decides what to do every tick.

Game AI is not machine learning

In games "AI" almost always means decision making and movement for non-player characters: the enemy that flanks, the shopkeeper that walks home at night, the ally that follows you. The goal is not to be intelligent but to be believable and fun: readable, fair, interesting to fight, and cheap enough to run for hundreds of characters. Techniques are old, well understood and mostly simple. This track covers the ones you will meet.

The limits of the state machine

A state machine (patterns track) is great to manage what an agent is doing. As an AI brain it scales badly: every state needs explicit transitions to others, and 30 states have up to 870 possible arrows. Adding "if low health, flee" means adding a transition from every state. Reusing "attack" in a different enemy means copying its wiring.

Behaviour trees

A behaviour tree (BT) makes the brain a tree of small nodes. Every tick the root is evaluated and each node returns one of three results: success, failure or running (still doing it, ask me again next tick). Because it is re-evaluated from the top, high-priority behaviour naturally interrupts low-priority behaviour.

  • Leaf nodes: conditions ("can I see the player?", "is health below 30%?") and actions ("move to the target", "play the attack animation"). Actions that take time return running.
  • Sequence (a logical AND): run children in order; stop at the first one that is not success. "Can see player AND in range AND attack."
  • Selector or fallback (a logical OR): run children in order; stop at the first one that is not failure. "Attack, otherwise chase, otherwise patrol": a priority list.
  • Decorators wrap one child and change its result or behaviour: inverter (swap success and failure), cooldown (fail for a while after success), repeat, until success, timeout, a condition guard.
  • Parallel: run several children at once (move and shoot).
Selector
├── Sequence                 # 1. flee when hurt
│   ├── Condition: health below 30%
│   └── Action: run to cover
├── Sequence                 # 2. fight when the player is near
│   ├── Condition: can see player
│   ├── Selector
│   │   ├── Sequence [in range, Cooldown(1.5 s, Action: shoot)]
│   │   └── Action: move toward player
└── Action: patrol           # 3. otherwise do the idle thing

Notice the order is the priority: fleeing outranks fighting outranks patrolling, and there is no wiring between behaviours. To make another enemy that never flees, delete the first branch. In the drill you implement the tick for these nodes.

The running state and memory

A walking action returns running over many ticks. A plain sequence would restart from its first child each tick (re-checking conditions every time, which keeps the AI reactive). That is the default and usually what you want. When a sequence must resume at the running child (do step 1, 2 and 3 in order without re-running step 1) use a sequence with memory, at the cost of being less reactive. Know which one your library uses.

Blackboard

Nodes need shared facts: the current target, last known player position, ammo. A blackboard is a small key-value store that the tree reads and writes. Sensors write to it ("target = player"), conditions read it. It keeps nodes independent of each other and of the game's types.

Why BTs caught on (and when they do not fit)

  • Modular and reusable: a "shoot at target" subtree is shared by all enemies.
  • Priorities and interruptions are structural.
  • Designers can edit them visually; programmers write the leaves.
  • Debuggable: highlight the path that succeeded this tick.

Drawbacks: state is implicit (hard to express "I have already done X"), they can be awkward for tasks where goals must be planned (the next lesson), and big trees need discipline (subtrees, naming). Many games combine: a state machine for animation/movement modes and a BT for decisions.

Implementation notes

  • Tick at a lower rate than rendering (4 to 10 times a second is plenty) and stagger agents across frames.
  • Keep leaf actions short and let the tree compose them.
  • Godot has community addons (LimboAI, Beehave); Unreal has built-in behaviour trees; the idea is simple enough to write in a day.
  • Always build the debug view first: a way to see each agent's current path through the tree and its blackboard values.

Drill: A behaviour tree tick

A behaviour tree decides what an enemy does by asking a tree of nodes, every tick, "can you do your job?". Each node answers success, failure or running (still busy, ask me again next tick). Implement tick for four kinds of node:

  • leaf: the answer comes from results[leaf_id] (in a real game it would run a condition or action).
  • sequence ("and"): tick children in order. The first one that is not success decides the answer (failure or running). All succeeded (or no children): success.
  • selector ("or", a fallback list): tick children in order. The first one that is not failure decides the answer. All failed (or none): failure.
  • inverter: swaps success and failure, passes running through.

Nodes live in an array. A leaf stores its result index in a. A sequence or selector stores the start of its children in a and the count in b; the children's node indices are in the kids array. An inverter stores its child's node index in a. The tree is re-evaluated from the root every tick (no memory), which keeps it reactive: if the enemy loses sight of the player, the chase branch fails on the next tick.

Starter (Zig):

const std = @import("std");

pub const Status = enum { success, failure, running };
pub const Kind = enum { leaf, sequence, selector, inverter };
pub const Node = struct { kind: Kind, a: usize = 0, b: usize = 0 };

/// leaf: a = index into results. sequence/selector: children are kids[a .. a + b]. inverter: a = child node index.
pub fn tick(nodes: []const Node, kids: []const usize, results: []const Status, root: usize) Status {
    _ = nodes;
    _ = kids;
    _ = results;
    _ = root;
    return .failure;
}

Answer key

1. A behaviour tree tick back ↑

Hint: A recursive function with a switch on the node kind. For a sequence: for each child index in kids[a..a+b], r = tick(child); if r != success return r. After the loop return success. A selector is the mirror image with failure.

Behaviour trees replaced big finite state machines in many games (Halo 2 popularised them) because they compose: you build "attack" once and reuse it under different parents, and adding a behaviour is adding a branch, not rewiring transitions. Real implementations add decorators (cooldown, repeat, "until success"), parallel nodes, a blackboard for shared data, and a memory variant so a sequence resumes at the running child. Godot has the LimboAI addon and the Beehave addon. The cost: debugging "why did it do that?" needs good tooling (highlight the active path).

2. Quick check back ↑

B. As the first (highest priority) child of the root selector, guarded by a health condition

A selector tries children in order, so earlier children outrank later ones. Putting the flee branch first interrupts anything below it each tick.

3. Quick check back ↑

B. Fails (or skips) the action for a set time after it succeeds, so the enemy cannot fire every tick

It is the standard way to rate-limit an action without a timer variable in the action itself.

4. Quick check back ↑

A. Players do not notice, and human reaction time is much slower; it saves CPU and can be staggered across agents

A decision delay of 100 to 200 ms looks like human reaction time. Movement and animation still update every frame; only the decision rate is low.

5. Check 1 back ↑

C. A sequence: it runs children in order and stops at the first non-success

Sequence is a logical AND over children, so all three steps (see, in range, shoot) must succeed.

6. Check 2 back ↑

A. On a shared blackboard: sensors write facts like the target and last known position, conditions and actions read them

The blackboard decouples nodes: writers and readers share facts without depending on each other.
