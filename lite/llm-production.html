LLM features in production

Model lifecycle, fallbacks, latency, cost, privacy and observability.

A demo needs one prompt and one API key. A production LLM feature is a dependency on a fast-changing external service, and it needs the same engineering as any other critical dependency, plus a few things that are specific to models.

Models have a lifecycle

Providers deprecate, rename and retire models on their own schedule, sometimes with little notice on smaller gateways. A real failure mode: the configured model id disappears, every call returns “model unavailable”, and the health check still says “connected” because it never called the model.

  • Pin exact model versions in configuration, not in code scattered across files, so a change is one line and one deploy.
  • Health checks exercise the model with a tiny request, or at least check that the id is still in the provider’s model list.
  • Fallback model for the same task, evaluated in advance, that the service switches to when the primary errors.
  • Surface the real error in logs and metrics (“provider 400: model unavailable”), even when users see a friendly message.
  • Track deprecation notices like dependency updates: an owner, a calendar date, an eval run before the switch.

Latency

  • Stream tokens to the user. Time to first token matters more for perceived speed than total time.
  • Generate less. Output tokens are slow; ask for short, structured output.
  • Set timeouts sized to the expected output length, and retry only on errors that are safe to retry (429, 5xx), with backoff.
  • Run independent calls in parallel, and move non-interactive work (summaries, classification) to background jobs.

Cost

  • Route by difficulty: a small, cheap model for classification and extraction; a large one only where evals show it is needed.
  • Prompt caching for stable prefixes, and plain response caching for repeated questions.
  • Budgets and limits: per-user rate limits, max tokens per call, a daily spend alert. One loop bug can burn a month’s budget overnight.
  • Log token counts per feature so you know which feature costs what.

Quality over time

Keep a versioned eval set per feature and run it on every prompt change and every model change, in CI where possible. Sample production traffic for human review. Track format failures (invalid JSON, refusals, empty replies) as a metric; they rise quietly when a model changes underneath you.

Privacy and data handling

  • Know each provider’s terms: is the data retained, and is it used for training? Some cheaper offerings are discounted because they train on prompts.
  • Route by sensitivity: generic content (public code exercises) can go to a cheaper model; customer or personal data only to providers with the right terms and region.
  • Redact secrets and personal data before sending, and do not log full prompts containing them.

Observability

For every call record: feature, model id and version, prompt template version, token counts, latency, cost, outcome (ok, error type, format failure). This turns “the AI is worse this week” into a graph you can act on.

Answer key

1. Quick check back ↑

B. Route by sensitivity: generic code to the cheap model, free-text answers that may contain real work details to a provider that does not train on prompts

Data handling terms are a routing input like cost and quality. A model cannot “forget”; only the provider’s terms decide what happens to the prompt.

2. Quick check back ↑

B. Stream tokens as they are generated and ask for shorter answers

Streaming shows the first words in under a second, and fewer output tokens cut the total time. A larger model is usually slower.

3. Check 1 back ↑

B. Made a tiny real call to the configured model (or checked the provider’s model list), so a retired or renamed model shows as unhealthy

A health check that only reads configuration proves nothing about the dependency. Exercise the actual model cheaply, or at least verify it is still listed.

4. Check 2 back ↑

B. Run your eval set on the new model and compare quality, format failures, latency and cost against the current one

Model swaps change behaviour in ways prompts do not reveal. An eval set turns “seems fine” into a measured comparison you can repeat on every future swap.
