Debugging and profiling games

Make the invisible visible: debug drawing, in-game tools, time control, reproducible bugs and finding the real bottleneck.

Games are hard to debug

A game is a real-time, stateful, visual, often random system. A breakpoint freezes time, so you lose the thing you were looking at; the bug appears once an hour; the cause is a frame ago and three systems away. The answer is not a cleverer debugger, it is building the game so it can be observed and replayed.

1. Make things visible: debug drawing

Numbers in a console are poor at describing space. Draw them: collision shapes, velocities, paths, targets, perception cones, spatial grid cells, camera bounds, the current state name above each character. Provide a toggle per category (physics, AI, navigation, audio) so you can see one thing at a time. Most engines have built-in versions (Godot: Debug → Visible Collision Shapes, Visible Navigation); add your own as soon as you write a system, not after the first bug.

2. Build tools into the game

  • Debug overlay: FPS, frame time graph, entity counts, memory, draw calls. A frame-time graph shows spikes an average hides.
  • Console / cheat commands: god, spawn goblin 5, teleport boss_room, set time 0.2, give sword. They turn a 10-minute walk to the bug into one line, and the same commands serve testers.
  • Time control: pause, single-step one frame, slow motion, fast forward. Stepping frame by frame through a jump is the way to see that the coyote timer is off by one.
  • Inspector: click an entity in the running game to see and edit its state and components (Godot's remote scene tree does this).
  • State dump and load: save the whole game state to a file at the moment of the bug and load it later.

3. Make bugs reproducible

The single biggest debugging investment is determinism (game loop and patterns tracks): a fixed timestep, one seeded random generator, and all input going through commands that can be recorded. Then "it happened once during a playtest" becomes "here is the replay file, it fails on frame 4,812" every time. Add: a seed printed on the screen (or in the log) for any procedural level, an automatic recording of the last N seconds kept in memory and written out when an assertion fails or the player presses a "report bug" key.

4. Assertions and logging

  • Assert invariants where they must hold ("health is never negative", "this id exists"), loudly in development builds. A crash at the point of corruption is far better than weird behaviour ten seconds later.
  • Log levels (error, warning, info, debug) and categories (ai, net, audio) so you can turn on only what you need. Logging every frame buries the signal: log events and changes, not state.
  • Include the frame number and timestamp in log lines so logs from different systems line up.
  • Print values where you suspect the bug, but also print what you assumed: "assumed target is not null".

5. A method for hard bugs

  1. Reproduce it (or get closer): minimal steps, seed, replay.
  2. Bisect: turn systems off (AI, physics, audio) until it stops; or bisect the version history with git bisect using the replay as the test.
  3. Form a hypothesis and test it; change one thing at a time.
  4. Fix the cause, not the symptom; if you clamped a value to hide a negative, find out who made it negative.
  5. Add a test or an assertion so it cannot return silently.

Profiling: measure, do not guess

  • Use the profiler to find where frame time goes (CPU functions, GPU passes, draw calls, memory allocation). Look at the worst frames, not the mean: players feel hitches.
  • Tools: the engine's profiler (Godot Debugger → Profiler and Monitors), Tracy (real-time frame profiler with a C and C++ API and community bindings for other languages), perf and flame graphs on Linux, RenderDoc for GPU frames.
  • Is it CPU-bound (game logic, physics, too many draw calls) or GPU-bound (fill rate, shaders)? Cheap test: halve the resolution. If the frame time drops a lot, it is GPU-bound.
  • Allocation spikes and garbage collection explain "random" hitches: count allocations per frame.
  • Profile release/export builds on target hardware. The editor, a debug build, or your fast desktop tell you little about a mid-range phone.
  • Set budgets up front (16.6 ms frame, N draw calls, M MB) and watch them in CI so regressions are caught early.

Crashes in the wild

Ship builds with symbols you keep (so a crash address maps to a function), add a crash handler that saves a log and last-state dump and offers to send it (with consent), and keep a breadcrumb trail of the last events. A reproducible report from a player is worth a hundred "it crashed".

Answer key

1. Spot the debuggability problems back ↑

Hint: One is noise, one is non-reproducibility, one hides the cause.

  • Line 2: Printing per frame per enemy floods the log so the one useful line is buried. Log changes and events (state transitions, damage taken), behind a debug category switch.
  • Line 3: Unseeded global randomness in the simulation: the stun happens at random frames, so a bug that follows it cannot be reproduced. Use a seeded generator owned by the simulation (and record the seed).
  • Line 6: Clamping hp to zero hides the real bug: something made it negative. Assert the invariant (assert(hp >= 0)) where damage is applied so you find who overdamaged.

2. Quick check back ↑

B. Make the game deterministic and record inputs and the seed, so the next occurrence arrives as a replay

A deterministic recording turns intermittent bugs into reproducible ones and makes them testable.

3. Quick check back ↑

B. Lower the render resolution: if frame time drops a lot it is GPU-bound (fill rate), if not it is probably CPU-bound

Resolution only changes pixel work. If the frame time does not move, the bottleneck is elsewhere (logic, draw calls).

4. Quick check back ↑

B. Players notice hitches, and an average of 60 fps can hide a 200 ms spike every few seconds

Stutter is about the tail of the distribution (99th percentile), not the mean.

5. Check 1 back ↑

B. Time control: pause and single-step one frame at a time through the jump to inspect timers

Stepping frame by frame exposes off-by-one timing that real-time observation hides.

6. Check 2 back ↑

D. Assert the invariant where damage is applied so the corruption crashes loudly at its cause

A crash at the point of corruption beats weird behaviour later; never hide the cause with a clamp.
