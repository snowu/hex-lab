Engineering a multi-bank aggregator

Heterogeneity, normalisation, throttling, outages and reconciliation.

The core engineering problem: thousands of banks, one reliable API. Each bank differs in formats, auth quirks, rate limits, uptime, field semantics and release schedule. Patterns that matter:

  • Adapter / anti-corruption layer per bank (or per bank-group/standard like Berlin Group, STET, UK OB). Everything above the adapter sees one canonical model.
  • Canonical model + raw payload. Normalise, but keep the original for debugging and for fields you did not map yet.
  • Per-bank resilience: timeouts, circuit breakers, rate limiters, bulkheads (separate pools), so one bad bank cannot sink others.
  • Contract tests & sandboxes per bank, plus synthetic probes in production that detect a bank changing behaviour before customers do.
  • Data freshness is a product feature: expose “as of” timestamps and degrade to cached data with a clear flag when the bank is down.
  • Reconciliation: regularly compare what you believe happened (payments, statuses) with what the bank reports. Money systems assume drift and detect it.

Simulation: One slow bank vs your worker pool

An aggregator serves three banks (illustrative names) from one pool of 64 workers at 30 requests/s each. For the first 20 seconds everything is healthy: ~99.7% success, p95 under half a second. Then Havn Bank degrades: calls take about 9 seconds and 10% fail. Step through the scenarios and watch which protection contains the damage. The breaker counts errors and calls slower than 2s as failures.

Try this in the full app:

  • no protection: after the incident Havn Bank holds the workers, queues build, and the healthy banks fail too. Look at the timeline.
  • + timeout: Havn Bank is cut off at 2s, which helps a lot but it still consumes a large share of the pool.
  • + bulkhead: each bank gets its own workers, so the healthy banks stay at baseline however slow Havn Bank is.
  • + breaker: after a few slow or failed calls Havn Bank is failed instantly, so no workers are wasted on it.
  • Raise the load to 60 req/s or shrink the pool, and see how much headroom each setup really has.
  • Drop the incident latency to 1s and raise the error rate instead: compare how the breaker reacts to errors versus slowness.

answer 3 ↓

Worked design prompt: “Design the data refresh scheduler”

  • Inputs: consents (user, bank, accounts, last refresh, status), per-bank limits, user activity signals.
  • Mechanics: priority queue keyed by next-eligible time; a token bucket per bank and a daily budget per account; jittered schedule; user-present refreshes jump the queue.
  • Failure: circuit breaker per bank, exponential backoff per consent, mark consent “needs reauth” on auth errors and notify the customer via webhook.
  • Correctness: idempotent writes (upsert by transaction id), dedupe overlapping windows, store fetch watermarks.
  • Observability: freshness SLO (e.g. 95% of active accounts < 6h old), success rate per bank, quota utilisation.

Answer key

1. Normalise two banks’ transactions back ↑

Hint: decimal.Decimal(text) * 100 is exact. Check that it is a whole number before int(...) so extra decimals fail loudly instead of truncating. dict.get(key, "") handles missing fields.

Reference solution:

from decimal import Decimal

def parse_minor(text):
    value = Decimal(text.strip()) * 100
    if value != value.to_integral_value():
        raise ValueError('more than 2 decimals: ' + text)
    return int(value)

def normalize(bank, raw):
    if bank == 'A':
        amount = raw['transactionAmount']
        return {
            'id': raw['transactionId'],
            'date': raw['bookingDate'],
            'amount_minor': parse_minor(amount['amount']),
            'currency': amount['currency'],
            'description': raw.get('remittanceInformationUnstructured', ''),
            'counterparty': raw.get('creditorName', ''),
        }
    if bank == 'B':
        day, month, year = raw['date'].split('.')
        return {
            'id': raw['id'],
            'date': f'{year}-{month}-{day}',
            'amount_minor': raw['amountMinor'],
            'currency': raw['ccy'],
            'description': raw.get('text', ''),
            'counterparty': raw.get('counterparty', ''),
        }
    raise ValueError('unknown bank: ' + str(bank))

Real mapping also handles debtor vs creditor naming by sign, booked vs pending, value date vs booking date, timezones, duplicates across pages, and banks that omit stable ids (derive a deterministic hash). Keep the raw payload next to the normalised one.

2. Quick check back ↑

B. Workers pile up waiting on X and starve every other bank; fix with per-bank timeouts, concurrency limits (bulkheads) and a circuit breaker

Classic head-of-line blocking. Isolate failure domains per dependency, and fail fast so healthy banks keep their capacity.

3. Quick check back ↑

B. Unattended access is limited (about 4 calls per 24h per account), banks also throttle aggregators, so you need a scheduler that budgets calls per account and per bank, staggers load, and favours on-demand refreshes when the user is present

Plan a refresh budget: per-account daily quota, per-bank token buckets, jitter to avoid top-of-the-hour spikes, and prioritise refreshes triggered by an active user session.

4. Check 1 back ↑

C. Keeping the raw bank payload alongside the canonical model, so unmapped fields stay available for debugging and later mapping

Normalise into a canonical model but retain the original payload. Heterogeneous banks change faster than your mappings.
