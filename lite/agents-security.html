Agents, tools & prompt-injection security

Least privilege for LLM tools; never trust model output.

An agent is a loop: the model decides on a tool call, your code executes it, the result goes back into the context, repeat. The model is a confused deputy: anything in its context (web pages, emails, tickets, files) may contain instructions that steer it. That is prompt injection, and it cannot be fully “prompted away”.

Design rules

  1. Least privilege. Expose the smallest set of tools, scoped to the end user’s permissions, not a service superuser.
  2. Treat model output as untrusted input. Validate tool arguments against a schema and an allowlist on the server.
  3. Separate read from write. Reading is cheap; writes (payments, emails, deletes) need confirmation or a human-in-the-loop for high-risk actions.
  4. Limit the lethal trifecta: private data + untrusted content + an exfiltration channel (outbound requests/links). Remove at least one.
  5. Budget and observe. Cap steps, tokens and spend; log every tool call with its arguments for audit.

MCP and third-party tools

The Model Context Protocol (MCP) is an open protocol, introduced by Anthropic in 2024 and now widely supported, for connecting models to tools and data. An MCP server exposes tools (actions), resources (data) and prompts; an MCP client inside the AI application discovers them and offers them to the model. It plays the role for AI tools that a common driver interface plays for hardware: one integration, many applications.

The security view: an MCP server is code and text you are trusting, like a dependency.

  • Tool descriptions are prompt input. A malicious or compromised server can put instructions in a tool’s description or results. Review servers like packages: source, maintainer, pinned versions.
  • Scope the credentials. Give each server the narrowest token for the current user, never a shared admin key.
  • Mixing servers mixes trust. A server that reads untrusted content (web, email) plus one that can send data out recreates the lethal trifecta across two tools.
  • Keep the server-side checks. Authorisation, allowlists and confirmation for writes belong in the server and the API behind it, not in the model’s good behaviour.

Challenge (Python): Guard a tool call

Implement validate_tool_call(call, registry). call is a dict {'tool', 'args'} coming from a model; registry maps tool names to {'args': {name: 'string' | 'number'}, 'max_amount': optional}. Return {'ok': True} if the tool exists, the args have exactly the declared keys with the declared types, and, if max_amount is set, args['amount'] is a finite number between 0 (exclusive) and max_amount (inclusive). Otherwise return {'ok': False, 'reason': '...'} with any non-empty reason. Never raise: the input is untrusted.

Answer key

1. Guard a tool call back ↑

Hint: Check isinstance(tool, str) before using it as a dict key (a list would raise TypeError). bool is a subclass of int in Python, so exclude it explicitly. math.isfinite handles NaN and infinity.

Reference solution:

import math

def validate_tool_call(call, registry):
    def no(reason):
        return {'ok': False, 'reason': reason}

    tool = call.get('tool') if isinstance(call, dict) else None
    if not isinstance(tool, str) or tool not in registry:
        return no('unknown tool')
    spec, args = registry[tool], call.get('args')
    if not isinstance(args, dict):
        return no('args must be an object')
    if set(args) != set(spec['args']):
        return no('args must be exactly: ' + ', '.join(sorted(spec['args'])))
    for name, kind in spec['args'].items():
        v = args[name]
        if kind == 'string' and not isinstance(v, str):
            return no(f'{name} must be a string')
        if kind == 'number' and (isinstance(v, bool) or not isinstance(v, (int, float))):
            return no(f'{name} must be a number')
    if 'max_amount' in spec:
        amount = args.get('amount')
        if not math.isfinite(amount) or amount <= 0 or amount > spec['max_amount']:
            return no('amount out of range')
    return {'ok': True}

Real systems also check authorisation (can THIS user act on THIS account?), rate limits, and require human confirmation for money movement. Pydantic or JSON Schema do the shape checks for you; the point is that you validate on the server, not trust the model.

2. Quick check back ↑

B. Remove or gate the send capability (confirmation, allowlisted recipients) so injected instructions cannot cause irreversible exfiltration

You cannot rely on the model to resist injection. Architect so a successful injection has limited blast radius: least privilege, confirmations, and breaking the exfiltration channel.

The lethal trifecta is private data plus untrusted content plus an exfiltration channel. Removing one leg limits what an injection can achieve.
