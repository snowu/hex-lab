Observer and event queue

Let things react to each other without knowing each other: signals, callbacks, and queues that decouple in time.

The problem

The player picks up a coin. The score must go up, a sound must play, an achievement may unlock, the HUD must flash, analytics logs it. If the coin code calls all of those directly, the coin knows about the whole game, and removing the HUD breaks it. We want the coin to say "I was collected" and let whoever cares react.

Observer

The subject keeps a list of observers and calls each one when something happens. Godot's signals, C#'s event, JavaScript's addEventListener are all this.

# GDScript
signal collected(value)            # in coin.gd
func _on_body_entered(body):
    collected.emit(5)              # coin knows nothing about who listens

# somewhere else
coin.collected.connect(hud.add_score)

In C++ an observer list is a vector of callbacks; in Zig a slice of function pointers plus a context pointer. The shape is always the same: register, notify, unregister.

What goes wrong

  • Lifetime. If a subscriber is destroyed but still registered, the next notification calls freed memory (C++/Zig crash) or a dead object (GDScript error). Always unregister in the destructor/_exit_tree, or use an engine that cleans up connections for you (Godot disconnects signals when either node is freed).
  • Re-entrancy. A handler may add or remove observers, or trigger the same event again, while the list is being walked. Iterate over a copy, or defer the changes.
  • Order. The order handlers run in is usually unspecified. If two handlers depend on each other's work, you have hidden coupling: make it explicit.
  • Invisible control flow. "Who reacts to this event?" is not answered by reading the code that emits it. Keep events few and meaningful, name them in the past tense (collected, died), and avoid chains where handlers emit events that trigger handlers.
  • Leaks. Connecting every time an object is respawned without disconnecting stacks up duplicate handlers (the "I get double score" bug).

Event queue: decoupling in time

Observer still runs the handlers right now, inside the sender. That is a problem when a handler is slow (loading a sound) or when it is unsafe to run at that moment (you cannot delete an object in the middle of the physics step). An event queue stores the events and processes them later, at a point you choose in the frame. The sender fires and forgets; the receiver pulls when ready.

  • Typical use: audio requests ("play explosion"), input events, game-wide messages, network messages, deferred UI updates.
  • Implementation: a ring buffer (you build one in the drill): fixed memory, O(1) push and pop, no allocation during play.
  • The design decision is the full-queue policy. Drop the new event, drop the oldest, grow, block, or treat it as a bug. Use the simulation below to feel the difference. Audio can usually drop; a "level complete" event must never be lost.
  • Costs: events run later (latency, and the world may have changed since: carry the data you need in the event, not a pointer to something that may be gone), and debugging is harder because the stack trace no longer shows who sent it. Log or tag events with a sender id.

Observer, queue or direct call?

UseWhen
Direct callTwo things that always go together. Do not decouple what is not independent.
Observer / signalOne source, several unrelated reactions, handled immediately and cheaply.
Event queueHandling must wait for a safe point, can be slow, crosses threads, or the order and rate need control.

Drill: Event queue: a fixed-size ring buffer

An event queue decouples who sends from who handles and from when. The standard implementation is a ring buffer: a fixed array with a head (oldest item) and a count, so push and pop are O(1) and nothing is ever allocated.

  • push(v): store at the back. If the queue is full, store nothing and return false.
  • pushOverwrite(v): always store; if full, the oldest item is dropped to make room. Returns true if something was dropped.
  • pop(): remove and return the oldest item (FIFO), or nothing if empty. peek() returns it without removing.
  • len(): number of items.

The queue must keep working after the indices wrap around the end of the array many times.

Starter (Zig):

const std = @import("std");

pub fn RingQueue(comptime T: type, comptime capacity: usize) type {
    return struct {
        const Self = @This();

        items: [capacity]T = undefined,
        head: usize = 0, // index of the oldest item
        count: usize = 0,

        pub fn len(self: *const Self) usize {
            return self.count;
        }

        /// false (and nothing stored) when full
        pub fn push(self: *Self, v: T) bool {
            _ = self;
            _ = v;
            return false;
        }

        /// always stores v; true if the oldest item had to be dropped
        pub fn pushOverwrite(self: *Self, v: T) bool {
            _ = self;
            _ = v;
            return false;
        }

        pub fn pop(self: *Self) ?T {
            _ = self;
            return null;
        }

        pub fn peek(self: *const Self) ?T {
            _ = self;
            return null;
        }
    };
}

Answer key

1. Event queue: a fixed-size ring buffer back ↑

Hint: The back is at (head + count) % capacity. pop reads items[head], then head = (head + 1) % capacity and count -= 1. pushOverwrite when full: drop the oldest first (advance head, count -= 1), then push.

The Event Queue pattern fixes two problems of direct callbacks: the sender no longer blocks while handlers run, and a handler can be run later at a safe point in the frame (so a collision handler cannot delete an object mid-physics-step). The ring buffer choice shows the real design decision: what happens when it is full. Drop the new event, drop the oldest, grow, or block? Input and audio queues usually drop; a network send queue may want to disconnect the client instead. Make the policy explicit.

2. Spot the observer bugs (C++) back ↑

Hint: One is missing API, one is mutation during iteration, one is a lifetime problem.

  • Line 4: There is no way to unsubscribe, so listeners can never be removed. Return a handle/id from subscribe and provide unsubscribe.
  • Line 6: A listener may call subscribe (or unsubscribe) while this loop runs, which can reallocate the vector and invalidate the iteration (undefined behaviour). Iterate over a copy, or defer changes until emit finishes.
  • Line 11: The lambda captures this, but the destructor never unsubscribes, so after a Player is destroyed the hub still calls a dangling pointer. Unsubscribe in the destructor (RAII handle).

3. Quick check back ↑

B. Push requests onto an event queue, merge or drop duplicates, and let the audio system pull a limited number per frame

A queue lets the receiver control the rate and policy (cap voices, merge identical sounds), instead of the senders overwhelming it.

4. Quick check back ↑

B. Each respawn ran the connection again without disconnecting, so the handler is registered many times

Connect once, or disconnect when returning the object to the pool. Duplicate registration is the classic "lapsed" and "duplicate listener" bug.

5. Check 1 back ↑

C. Keep a way to unregister (a handle or id from subscribe) and always disconnect in the destructor or _exit_tree; prefer engines that auto-disconnect like Godot signals

Observer lifetime must be managed. A dead subscriber left registered is called after it is gone.

6. Check 2 back ↑

B. Push the requests onto an event queue processed at a safe point, with an explicit when-full policy: audio may drop but a level-complete event must never be lost

Queues decouple in time so slow or unsafe work waits for a chosen point. The full-queue policy is the core design decision.
