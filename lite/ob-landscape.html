The open banking landscape

PSD2, the players, and the end-to-end account-data flow.

Source note: this track combines general PSD2 knowledge with details from Neonomics’ public developer docs (UAPI v3.x at the time of writing). It is not insider knowledge of their internals. Read their docs yourself before the interview; being able to discuss their actual API is a strong signal.

PSD2 (EU Payment Services Directive 2) obliges banks to give licensed third parties access to customer accounts, with customer consent, via secure APIs. In Norway it applies through the EEA agreement and Norwegian law, with Finanstilsynet as the supervisor.

TermMeaning
ASPSPThe bank (Account Servicing Payment Service Provider).
PSUThe end user (Payment Service User) who owns the account.
TPPThird-Party Provider: regulated actor accessing bank APIs.
AISPAccount Information Service Provider: reads balances and transactions.
PISPPayment Initiation Service Provider: starts payments from the user’s account (“pay by bank”).
CBPIICard-based payment instrument issuer: funds-confirmation checks.
SCAStrong Customer Authentication: two of knowledge/possession/inherence (e.g. BankID).

An aggregator like Neonomics holds the TPP licence and certificates once, and exposes one API to its customers (fintechs, merchants, lenders) over many banks, each with its own quirks. The customer builds against one integration instead of thousands.

Account-data flow, as described in Neonomics’ public docs (simplified)

Step through it:

1. Authenticate your application

Your backend gets an access (and refresh) token from the token endpoint using the client id and secret from the developer portal. Requests are additionally signed (QSeal). See the signature-generation guide in their docs.

2. Create a session

POST /ics/v3/session returns a session id tied to a bank. You then send the session id in a header on account and payment calls. Deleting the session invalidates it.

3. Call accounts, hit “consent required”

Listing accounts without consent yields an error 1426. That error is the signal to start consent, you do not guess.

4. Initiate consent → user does SCA

The consent endpoint returns a URL. You redirect the PSU there; they authenticate with their bank (e.g. BankID) and approve access. Some banks (Swedish ones, Handelsbanken Finland per the docs) need the PSU’s IP in a header.

5. Fetch data

Now GET /ics/v3/accounts, then balances and transactions by account id. Remember normalisation: banks differ in formats, pagination, and what “booked” versus “pending” means.

Answer key

1. Quick check back ↑

B. AISP

Read-only account data is the AISP role. Paying out of the user’s account is PISP. Aggregators let customers rely on the aggregator’s licence rather than obtaining their own.

2. Quick check back ↑

B. Treat it as a normal state transition: start the consent flow, redirect the user to the returned URL, and resume after they return

“Consent required” is expected, not an incident. Model the integration as a state machine: no session → session → consented → data, and handle expiry of each state.

3. Check 1 back ↑

C. PISP, which initiates payments; the aggregator holds the licence and exposes one API over many banks

Starting a payment from the user account is the PISP role. An aggregator carries the licence once so customers integrate a single API.

4. Check 2 back ↑

A. Normalise into one canonical model (keeping the raw payload for debugging) and document what booked versus pending means per bank

Banks differ in formats, pagination, and field semantics. Normalise above an adapter layer but keep the original payload.
