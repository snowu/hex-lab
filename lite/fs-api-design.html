API design that survives its clients

Pagination, idempotency, errors, versioning, and the backend-for-frontend pattern.

Resources and verbs

Model nouns, not actions: POST /payments, GET /payments/{id}, PATCH /payments/{id}. Use verbs for the HTTP method, status codes for the outcome, and keep responses consistent. PUT (full replace) and DELETE are naturally idempotent; POST is not, so accept an Idempotency-Key (see the Reliability track).

Pagination

  • Offset (?page=500) gets slower as pages get deeper and skips or repeats rows when data changes.
  • Keyset / cursor: ?after=<opaque cursor> with a stable sort (including a unique tiebreaker). Fast on any page, stable under inserts. Make the cursor opaque and signed so you can change internals and clients cannot forge it.

Errors

One predictable shape, such as { "error": "kind", "message": "..." } or RFC 9457 application/problem+json. Classify them for callers (user_auth, forbidden, not_found, quota, upstream) so a client knows whether to re-login, retry or give up, and map upstream failures to 502/503 instead of leaking them.

Concurrency control over HTTP

Return an ETag; the client sends If-Match on update; a mismatch returns 412. This is optimistic locking for APIs, the same idea as a version or generation column.

Evolving an API

  • Additive changes (new optional fields) are safe. Removing or renaming a field is breaking.
  • Clients must ignore unknown fields. Servers should tolerate old clients for a while.
  • Version when you must (/v2 or a header) and deprecate with dates and metrics on who still uses the old one.
  • Document with OpenAPI, and test the contract.

Backend for frontend

A small server-side layer that exists to serve one frontend: it holds secrets, works around CORS to third-party APIs, aggregates several calls into one, caches shared data, and shapes responses for the UI. A serverless function at the edge is a natural fit. Keep it thin: it should not become a second monolith.

REST vs GraphQL vs RPC: REST is simple, cacheable and ubiquitous; GraphQL lets clients ask for exactly what they need (at the cost of caching, N+1 and query-cost control); RPC (gRPC) is efficient between services.

Challenge (Python): Keyset pagination with a signed cursor

Write paginate(items, limit, cursor, secret) for a feed. items are dicts with id and created_at (sortable) in any order. Return {'items': [...], 'next_cursor': str | None}, newest first (sort by (created_at, id) descending, so ties are stable). The opaque cursor encodes the last item's (created_at, id) plus an HMAC signature so clients cannot forge or edit it; the next page returns only items strictly after that position. cursor=None means the first page; next_cursor is None on the last page. Raise ValueError('invalid cursor') for a tampered, garbled or wrong-secret cursor and ValueError('limit must be 1-100') for a bad limit.

Answer key

1. Keyset pagination with a signed cursor back ↑

Hint: Sort with key=(created_at, id), reverse=True. Cursor = base64url(json [created_at, id]) + "." + a truncated HMAC of that payload. To decode: split, recompute and compare_digest the signature, then keep only rows whose (created_at, id) tuple is less than the cursor tuple. next_cursor exists only if more rows remain after this page.

Reference solution:

import base64
import hashlib
import hmac
import json

def _sign(payload, secret):
    return hmac.new(secret.encode(), payload.encode(), hashlib.sha256).hexdigest()[:32]

def _encode(last, secret):
    payload = base64.urlsafe_b64encode(json.dumps([last['created_at'], last['id']]).encode()).decode().rstrip('=')
    return payload + '.' + _sign(payload, secret)

def _decode(cursor, secret):
    try:
        payload, sig = cursor.split('.')
        if not hmac.compare_digest(sig, _sign(payload, secret)):
            raise ValueError
        created_at, row_id = json.loads(base64.urlsafe_b64decode(payload + '=' * (-len(payload) % 4)))
        return created_at, row_id
    except (ValueError, TypeError, AttributeError):
        raise ValueError('invalid cursor')

def paginate(items, limit, cursor, secret):
    if not isinstance(limit, int) or isinstance(limit, bool) or not 1 <= limit <= 100:
        raise ValueError('limit must be 1-100')
    ordered = sorted(items, key=lambda r: (r['created_at'], r['id']), reverse=True)
    if cursor is not None:
        position = _decode(cursor, secret)
        ordered = [r for r in ordered if (r['created_at'], r['id']) < position]
    page = ordered[:limit]
    more = len(ordered) > limit
    return {'items': page, 'next_cursor': _encode(page[-1], secret) if more else None}

This is the API-level twin of the SQL keyset query: WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT n. Opaque, signed cursors let you change the internals later and stop clients from crafting positions. Include a tiebreaker (id) or rows with equal timestamps will be skipped or repeated.

2. Quick check back ↑

B. An ETag/version: the client sends If-Match, and the server returns 412 Precondition Failed when it no longer matches

Optimistic concurrency: the update is conditional on the version the client last saw. The same idea as compare-and-swap with a generation number.

3. Quick check back ↑

A. 400 or 422 with a clear field-level error (422 if you separate syntax from semantics)

It is the client’s mistake, not the server’s. Return a 4xx with a machine-readable error naming the field.

4. Quick check back ↑

B. So you can change the underlying sort/keys later without breaking clients, and so clients cannot forge positions to probe data

Clients should treat the cursor as a black box. A signature (HMAC) stops tampering and enumeration tricks.

5. Check 1 back ↑

B. Accept an Idempotency-Key so a retried request with the same key executes once

PUT and DELETE are naturally idempotent but POST is not, so the key makes a retry safe against double execution.

6. Check 2 back ↑

Clients tolerate unknown fields but not renamed ones; evolve additively and version breaking changes explicitly.
