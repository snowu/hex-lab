Grids, pathfinding and simple AI

Tile maps as graphs, BFS, Dijkstra and A*, plus the steering and state-based AI that makes enemies look alive.

A map is a graph

A tile map is a graph: each walkable tile is a node, neighbours are edges. Pathfinding asks for the cheapest route between two nodes.

  • BFS (breadth-first): finds the shortest path when every step costs the same. Spreads like a flood.
  • Dijkstra: handles different costs (mud costs 3, road costs 1). Uses a priority queue.
  • A*: Dijkstra plus a heuristic that estimates the remaining distance, so it heads toward the goal instead of flooding in all directions. The heuristic must never overestimate (be admissible) to stay optimal. Manhattan distance on a 4-way grid, octile or Euclidean on 8-way.

When one path is not enough

  • Many units, one goal: compute one flow field (a BFS/Dijkstra from the goal, storing direction per tile) and every unit just reads its tile.
  • Open worlds: grids get huge. Use a navmesh (walkable polygons) or a coarse waypoint graph, then steer locally.
  • Moving obstacles: replan only when blocked, not every frame. Path requests can be queued and spread over several frames.

Steering behaviours

The path says where; steering says how to move so it looks natural: seek (toward a point), arrive (slow down near it), flee, avoid obstacles, separate from neighbours to avoid stacking. Add up the weighted vectors, clamp the result (the same accelerate-and-cap function from the first drill), and you have boids and crowds.

Decision making

Most game AI is far simpler than people expect: a state machine (patrol → chase → attack → return), sometimes a behaviour tree or utility scoring. Believable beats smart: add reaction delay, limited vision and mistakes. Players read intent, so telegraph attacks before they land.

Drill: Shortest path on a tile map

The grid is a list of equal-length rows. '#' is a wall, anything else is floor. Return the number of steps of the shortest 4-directional path from start to goal (both (row, col)), or -1 if there is none. A start or goal inside a wall is unreachable.

Zig: take an allocator and return an error union (you need scratch memory for the search; free it with defer).

Starter (Zig):

const std = @import("std");

/// Steps in the shortest 4-directional path, or -1 if unreachable.
pub fn shortestPath(allocator: std.mem.Allocator, grid: []const []const u8, start: [2]usize, goal: [2]usize) !i32 {
    _ = allocator;
    _ = grid;
    _ = start;
    _ = goal;
    return -2;
}

Answer key

1. Shortest path on a tile map back ↑

Hint: Breadth-first search: a queue of cell indices and a distance array filled with -1 (doubles as the visited set). Set a cell's distance when you enqueue it, not when you pop it, or the queue grows huge on open maps.

BFS is optimal when every step costs the same. With terrain costs use Dijkstra, and add a heuristic (Manhattan distance on a 4-way grid) to get A*. Games also cache paths, share one flow field between many units, or spread the search across frames. In Zig note how the allocator is an explicit parameter: the caller decides where the memory comes from, which makes tests catch leaks for free (std.testing.allocator fails the test on a leak).

2. Quick check back ↑

B. The heuristic can overestimate, so A* may return a path that is not the shortest

An inadmissible heuristic trades optimality for speed (“weighted A*”). That is sometimes a good deal in games, but know that you are making it.

3. Quick check back ↑

B. One BFS/flow field from the player each time the player moves tile, and each zombie follows its tile's direction

A flow field is computed once for the goal and shared. Per-unit cost is a single array lookup.

4. Check 1 back ↑

A. BFS: it finds the shortest path on uniform costs without needing a heuristic

BFS is the right tool for uniform costs; Dijkstra and A-star pay off once costs differ or a heuristic can guide the search.

5. Check 2 back ↑

B. It may return a non-shortest path: overestimating heuristics break admissibility and optimality

An admissible heuristic never overestimates. Inflating it (weighted A-star) speeds up search but sacrifices the shortest-path guarantee.
