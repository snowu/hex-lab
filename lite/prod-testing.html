Testing a game

What is worth automating in a game, how to keep logic testable, golden replays, bots and fuzzing.

"You cannot test games" is half true

Feel, fun and visuals need people. But a surprising amount of a game is ordinary logic that tests well: rules, damage and economy calculations, inventory, parsing of data and saves, pathfinding, AI decisions, save migrations, network message handling. Automated tests catch regressions in those while you work on the parts that need human judgement.

Make the code testable: separate simulation from presentation

The most important design rule: keep the game logic free of engine types (no nodes, no rendering, no audio calls, no wall-clock time). Logic takes inputs and a time step and produces a new state plus events; a thin layer turns state into pixels and sounds. Then a test can create a world in one line, feed commands, and check the state, in milliseconds, without a window. This is also what makes determinism, replays and rollback possible: the same design pays three times.

Kinds of automated tests that work for games

  • Unit tests: pure functions and small modules: damage formula, cost curve, pity timer, A* on a tiny map. Fast; written like the drills in this lab (Zig and C++ have tests built in or one framework away; Godot has GUT and gdUnit).
  • Golden-replay tests: record a list of commands and a seed once, then assert that replaying them produces the same final state checksum. Any unintended change in behaviour trips the test. When you meant to change behaviour, regenerate the golden value deliberately and review the diff (the sample below).
  • Property tests and invariants: generate many random situations and assert rules that must always hold ("health never exceeds max", "total items are conserved by a trade", "a path never crosses a wall"). They find the case you did not think of.
  • Fuzzing: feed random and mutated bytes to the parsers (save files, network packets, level files) and make sure they fail gracefully and never crash or hang.
  • Headless simulation and bots: run thousands of automated playthroughs or encounters without rendering, and measure win rates, time to kill, economy balance, deadlocks. This is the "balance benchmarks" idea: a script that plays the game faster than a human.
  • Smoke tests: launch the exported game, load each level, check it does not crash or log errors in 30 seconds. Cheap and catches broken builds.
  • Screenshot tests: render a known scene and compare images; useful for UI and shaders, brittle across GPUs, so use tolerance and one reference machine.
  • Performance tests: run a standard scene and assert frame time, allocations and memory stay within budget.
const std = @import("std");

/// A small deterministic simulation: a seeded random generator, a position, and commands that change it.
const Sim = struct {
    rng: u64,
    x: i32 = 0,
    hp: i32 = 100,
    frame: u32 = 0,

    fn init(seed: u64) Sim {
        return .{ .rng = seed };
    }

    fn nextRand(self: *Sim) u32 {
        self.rng = self.rng *% 6364136223846793005 +% 1442695040888963407;
        return @intCast(self.rng >> 33);
    }

    fn step(self: *Sim, cmd: u8) void {
        switch (cmd) {
            'L' => self.x -= 1,
            'R' => self.x += 1,
            'H' => self.hp = @min(100, self.hp + 5),
            else => {},
        }
        if (self.nextRand() % 10 == 0) self.hp -= 7; // a random hazard: deterministic because the generator is seeded
        self.frame += 1;
    }

    /// A summary of the whole state: if any field changes, the checksum changes.
    fn checksum(self: *const Sim) u64 {
        var h: u64 = 1469598103934665603; // FNV-1a
        inline for (.{ @as(u64, @bitCast(@as(i64, self.x))), @as(u64, @bitCast(@as(i64, self.hp))), @as(u64, self.frame) }) |v| {
            h = (h ^ v) *% 1099511628211;
        }
        return h;
    }
};

fn run(seed: u64, commands: []const u8) u64 {
    var sim = Sim.init(seed);
    for (commands) |c| sim.step(c);
    return sim.checksum();
}

const recorded = "RRRLRHRRLLLRRRHRLRRRRHLLRR"; // the recorded command stream, as it would be loaded from a replay file

test "the same replay always reproduces the same checksum" {
    try std.testing.expectEqual(run(42, recorded), run(42, recorded));
}

test "a different seed or a different command changes the outcome, so the test is sensitive" {
    try std.testing.expect(run(42, recorded) != run(43, recorded));
    try std.testing.expect(run(42, recorded) != run(42, "RRRLRHRRLLLRRRHRLRRRRHLLRL"));
}

test "golden value: if you change game rules on purpose, regenerate this number and review the change" {
    try std.testing.expectEqual(@as(u64, 16487696168835199546), run(42, recorded));
}

What not to automate

  • "Is it fun", "does it feel responsive", "is this readable" are playtest questions.
  • Pixel-exact visuals on many GPUs: too brittle for the value.
  • Anything you would rewrite next week: wait until a prototype becomes a design.

Manual and playtest discipline

  • Keep a short regression checklist for each release (menus, save and load, each level start, pause, quit, input devices, settings persistence).
  • Test on the lowest-end device you support and on a clean machine without your dev tools.
  • Watch real players (the design lesson): record sessions, note where they hesitate.
  • Keep a bug tracker with reproduction steps, build number and the replay or seed attached.

Where to start

  1. Separate the simulation from the engine for new code.
  2. Write unit tests for formulas and parsers first (cheap, high value).
  3. Add a golden replay of one complete level.
  4. Fuzz your save loader.
  5. Add a headless bot once you have balance questions.

Answer key

1. Quick check back ↑

B. Investigate: the checksum changed, so behaviour changed. Find the first frame where state differs, then decide whether it is a bug or an intended change (and only then regenerate the golden value)

A golden test exists to flag unintended changes. Refreshing it blindly defeats the purpose.

2. Quick check back ↑

B. Pure logic that takes state, input and a time step and returns new state, with the engine layer only presenting it

No engine, no wall-clock, no globals in the logic: that is also what determinism needs.

3. Quick check back ↑

B. Fuzzing the save parser with random and mutated files

Fuzzing explores malformed inputs far beyond what a human would think to try.

4. Check 1 back ↑

A. Property and invariant tests: generate many random trades and assert conservation always holds

Invariants over generated cases find the edge case nobody thought to write by hand.

5. Check 2 back ↑

C. Compare with a tolerance on one reference machine instead of demanding pixel-exact matches everywhere

Screenshot tests are brittle across hardware, so tolerance plus a single reference keeps the signal without the noise.
