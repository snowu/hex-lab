Overload, backpressure and safe rollouts

Shed load before it sheds you, bound every queue, and ship changes gradually.

Most outages at scale are not a component dying. They are a component overloaded: it slows down, callers retry, it slows down further, and a small surge becomes a total outage. Senior designs plan for the surge.

Why overload collapses

  • Queues hide overload until it is too late. An unbounded queue turns “too much traffic” into “every request is 40 seconds old”, and requests whose callers have already given up still get processed.
  • Retries multiply load. Three layers that each retry three times turn one failing request into 27 calls at the bottom.
  • Latency eats capacity. By Little’s law, requests in flight = arrival rate × latency. If latency goes from 100ms to 2s, you need 20× the connections and threads for the same traffic.

The toolbox

ToolWhat it does
Bounded queues and concurrency limitsCap work in flight; anything over the cap is rejected immediately
Load sheddingReturn 429/503 fast when over capacity. Shed the cheapest work first: background refreshes before user-facing reads, reads before payments
BackpressureTell the producer to slow down instead of buffering: a consumer pulls at its own pace (Kafka), a bounded channel blocks the writer, a 429 with Retry-After
Deadline propagationPass the remaining time budget downstream; drop work whose deadline has already passed
Retry budgetsRetry at most ~10% extra traffic per client, retry only at one layer, always with backoff and jitter
Graceful degradationServe cached or partial results with a flag, turn off expensive features (recommendations, search suggestions) first
Adaptive concurrencyLower the concurrency limit automatically when latency rises (as TCP congestion control does)

Safe rollouts

Many incidents come from changes, so the cheapest reliability work is making changes small and reversible:

  • Canary: send 1% → 10% → 50% → 100% of traffic to the new version, comparing error rate and latency against the old one at each step, and roll back automatically if it is worse.
  • Blue/green: run the new version alongside the old one and switch traffic at once; rollback is switching back. Simple, but every user moves at the same moment.
  • Feature flags: deploy the code dark, then turn the behaviour on per tenant or per percentage. This separates deploying from releasing, and a kill switch is faster than any redeploy.
  • Expand/contract migrations: add the new column or table, write to both, backfill, switch reads, then remove the old one, so every step can be rolled back on its own.
  • Bake time and change freezes around peak periods (month-end for payments).
In a design round: “Each bank adapter has a concurrency limit and a bounded queue. Over the limit we shed background refreshes first and return 503 with Retry-After to API clients, while user-present requests keep a reserved slice of capacity. New adapter versions go out behind a per-bank flag and a 1% canary.”

Self-check: your service at 3× traffic

  1. Where is the first bounded resource (DB connections, threads, a bank’s rate limit)? What happens when it fills?
  2. Is any queue unbounded? What is the oldest request it could hold?
  3. How many layers retry? What is the worst-case multiplier?
  4. What do you shed first, and what does the client see?
  5. Which feature would you turn off first, and is there a flag for it today?

Answer key

1. Quick check back ↑

B. Load on the downstream can grow up to 27× (3 × 3 × 3) exactly when it is weakest; retry at one layer only, with a retry budget, backoff and jitter

Retries multiply across layers. Idempotency makes them safe for correctness, not for load. Retry in one place and cap the retry rate.

2. Quick check back ↑

B. Background account refreshes and other deferrable work, keeping capacity for user-present payments and status checks

Shed by priority: deferrable and background work first, protect the money-moving and user-present paths. Shedding randomly treats a cron job like a customer at checkout.

3. Check 1 back ↑

B. Admission control: bound concurrency and queue length and reject excess work fast (429/503), ideally lowest priority first

Without a bound, every request waits behind every other one and all of them time out. Rejecting some quickly keeps the rest fast; that is load shedding.

4. Check 2 back ↑

B. It limits the blast radius: bad versions hurt 1% of traffic, and automated checks against the baseline can stop the rollout

Progressive delivery turns a bad deploy from an outage into a small, measured experiment that rolls back on its own.
