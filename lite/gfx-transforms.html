Transforms, matrices and hierarchies

Position, rotation and scale as matrices, why order matters, parent-child hierarchies, pivots, and a first look at 3D.

Why matrices

Moving, rotating and scaling a sprite are three separate operations, but a hierarchy of them (a hand on an arm on a body on a platform) needs to be combined and undone. A matrix packs any combination into one object you can multiply, invert and apply to many points cheaply. In 2D, an affine transform needs six numbers (a 2×2 matrix for rotation, scale and shear plus a translation); in 3D, twelve (a 4×4 matrix with a fixed last row, which is what engines store).

Homogeneous coordinates in one paragraph

Translation is an addition, rotation and scale are multiplications, so they do not combine with a single operation. The trick: add a third coordinate that is always 1, (x, y, 1). Then translation also becomes a multiplication (the translation numbers sit in the third column), and all three combine by plain matrix multiplication. That is the whole reason 3×3 matrices appear in 2D and 4×4 in 3D.

Order of operations

Matrix multiplication is not commutative: A * B is not B * A. With column vectors (the convention in most maths and in Godot), M = T * R * S means scale first, then rotate, then translate: the sprite scales around its own origin, turns around it, then moves to its place. That is almost always what you want, and it is the order every engine uses for a node's local transform. Reverse it and the object swings around the world origin instead of its own pivot. The simulation shows it.

Parents and children

A child's world transform is world = parent_world * child_local. Walk the tree from the root multiplying. Moving the parent moves everything below it for free; the child only knows its offset. This is how skeletons, turrets on tanks, UI panels and vehicles carrying passengers work. Because multiplications are cheap but a tree can be large, engines cache world transforms and recompute only the changed part (the dirty flag lesson).

Pivot, origin and anchor

The pivot is the point the sprite rotates and scales around. A character's pivot at its feet makes y-sorting and ground contact simple; a pivot at the centre is natural for a spinning coin. Changing the pivot without moving the picture means translating the sprite by the pivot offset. Put the pivot where the gameplay needs it, and be consistent across a set of sprites.

Non-uniform scale and shear

Scale a parent by (2, 1) and rotate a child inside it: the child's axes are no longer perpendicular, the child is sheared. Engines either forbid it, apply it only at the leaf, or accept the shear. In the simulation, drag parent x-scale away from 1 and watch the axes of the last node. Rule: avoid non-uniform scale on nodes that have rotating children.

Inverse transforms

To convert a mouse position (world or screen) into a node's local coordinates, apply the inverse of its world matrix. An inverse exists only if the transform does not flatten space (a scale of 0 does not have one). The drill implements inverse for the 2D case.

A look at 3D

  • Model → world → view → projection. The classic pipeline multiplies four matrices: the model matrix places the object, the view matrix is the inverse of the camera's transform, and the projection maps the view volume (a frustum for perspective, a box for orthographic) into the screen cube. Orthographic projection has no perspective; many "2.5D" games use it.
  • Rotations. Euler angles (three angles) are intuitive but suffer gimbal lock and awkward interpolation. Quaternions (four numbers) have no lock, interpolate smoothly with slerp and compose cheaply; engines store rotation as quaternions and expose Euler angles for editing.
  • Normals (directions perpendicular to surfaces) transform with the inverse-transpose of the model matrix, not the model matrix itself, once non-uniform scale is involved.

Debugging transforms

  1. Draw the axes of the node (red x, green y in many tools).
  2. Print the local and world positions and compare.
  3. Check the order: does it rotate around its pivot or around the origin?
  4. Check units (degrees vs radians; pixels vs tiles).
  5. Check handedness: 2D screen y points down, which flips rotation direction compared with a maths textbook.

Drill: 2D transforms: matrices and the order of operations

A 2D transform (move, rotate, scale) is an affine matrix stored as six numbers: x' = a*x + c*y + tx and y' = b*x + d*y + ty. Parent and child nodes combine by multiplying their matrices. Implement:

  • identity, translate(x, y), rotate(radians) (counter-clockwise: rotating (1, 0) by 90° gives (0, 1)), scale(sx, sy).
  • mul(parent, child): the matrix that applies the child first, then the parent. This is how a child's local transform becomes a world transform.
  • apply(m, x, y): transform a point.
  • inverse(m): the matrix that undoes m, or nothing if it cannot be undone (a zero determinant, e.g. scale(0, 1)). You need it to turn a mouse position back into local coordinates.

Starter (Zig):

const std = @import("std");

/// x' = a*x + c*y + tx ; y' = b*x + d*y + ty
pub const Mat = struct { a: f64, b: f64, c: f64, d: f64, tx: f64, ty: f64 };
pub const identity = Mat{ .a = 1, .b = 0, .c = 0, .d = 1, .tx = 0, .ty = 0 };

pub fn translate(x: f64, y: f64) Mat {
    _ = x;
    _ = y;
    return identity;
}

pub fn rotate(rad: f64) Mat {
    _ = rad;
    return identity;
}

pub fn scale(sx: f64, sy: f64) Mat {
    _ = sx;
    _ = sy;
    return identity;
}

/// The matrix that applies c first and then p (a child inside a parent).
pub fn mul(p: Mat, c: Mat) Mat {
    _ = p;
    return c;
}

pub fn apply(m: Mat, x: f64, y: f64) [2]f64 {
    _ = m;
    return .{ x, y };
}

pub fn inverse(m: Mat) ?Mat {
    _ = m;
    return null;
}

Answer key

1. 2D transforms: matrices and the order of operations back ↑

Hint: Treat it as the 3×3 matrix [[a c tx], [b d ty], [0 0 1]] and multiply: for mul(p, c): a = p.a*c.a + p.c*c.b; b = p.b*c.a + p.d*c.b; c = p.a*c.c + p.c*c.d; d = p.b*c.c + p.d*c.d; tx = p.a*c.tx + p.c*c.ty + p.tx; ty = p.b*c.tx + p.d*c.ty + p.ty. Inverse: det = a*d - b*c; the 2×2 part inverts to [d -c; -b a] / det, and the translation becomes -(inverse2x2 · (tx, ty)).

Order of operations is the number-one transform bug. "Rotate then translate" and "translate then rotate" are different things: the first spins a thing around its own centre and then moves it, the second moves it and then swings it around the origin. Scene graphs (Godot Node2D, Unity Transform) store position/rotation/scale per node and multiply down the tree, usually caching the result with a dirty flag (see the patterns track). Non-uniform scale combined with rotation produces shear, which is why some engines forbid it on parents. 3D uses 4×4 matrices and quaternions for rotation, but the ideas are the same.

2. Quick check back ↑

B. Translate and rotate were composed in the wrong order, or the pivot is not at the base

Rotate-then-translate swings the object around the origin. Translate · rotate applies rotation around the object's own origin, which must be at the pivot.

3. Quick check back ↑

B. No gimbal lock, smooth interpolation (slerp) and cheap composition

Euler angles are good for editing, quaternions are good for computing and blending.

4. Quick check back ↑

B. Convert the screen position to world space with the inverse of the camera transform, then divide by the tile size

World space is where tiles live. The inverse of the world→screen transform brings the mouse into it.

5. Check 1 back ↑

C. Non-uniform parent scale plus a rotating child produces shear; avoid non-uniform scale on nodes that have rotating children

Scaled axes are no longer perpendicular, so child rotation shears. Keep ancestor scale uniform or apply it at the leaf.

6. Check 2 back ↑

B. The extra 1 turns translation into a multiplication so translation, rotation and scale combine with plain matrix multiplication

Homogeneous coordinates unify addition and multiplication into one operation that composes and inverts cleanly.
