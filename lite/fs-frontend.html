Hydration attaches JavaScript to server-rendered HTML so it becomes interactive; it costs bytes and CPU. A no-framework page with one ES module and CDN scripts is perfectly valid for small tools: fewer moving parts, trivial deploys.

Performance: what users feel

  • Core Web Vitals: LCP (largest content shown, good ≤ 2.5 s), INP (responsiveness to interactions, good ≤ 200 ms), CLS (layout shift, good ≤ 0.1).
  • Ship less JavaScript: code-split, lazy-load rarely used libraries (load the auth/sync SDK only when someone signs in), compress, cache hashed assets for a year.
  • Avoid layout shift: reserve space for images and embeds. Avoid long main-thread tasks: chunk or move work to a Web Worker (as this site does for Python).
  • Measure with real-user data and Lighthouse, not guesses.

State

  • Server state (data that lives on the backend and goes stale) is different from UI state (an open menu). Use a cache layer with invalidation for the first (stale-while-revalidate again), plain local state for the second.
  • Optimistic updates: update the UI immediately, send the request, roll back on failure. Pair with idempotent endpoints.
  • Handle all four states in every view: loading, empty, error, success. Handle out-of-order responses (cancel the old request with AbortController).

Accessibility essentials

  • Semantic HTML first (button, a, label, headings). ARIA only to fill gaps.
  • Everything reachable and usable by keyboard with a visible focus. Sufficient colour contrast. Alt text. Respect prefers-reduced-motion and prefers-color-scheme.

Security basics

  • XSS: never put untrusted data into HTML with innerHTML; use textContent or a framework’s escaping, and sanitise if you must render HTML. Add a Content-Security-Policy to limit what scripts may run.
  • Third-party scripts have full access to the page: pin versions, use Subresource Integrity, keep them few.
  • CSRF applies to cookie auth (see the HTTP lesson). Validate input on the server; client checks are only UX.
  • Never put secrets in frontend code: it is public by definition. Public project keys are fine if authorisation is enforced server-side.

Testing and delivery

Many fast unit tests, some component tests, a few end-to-end tests with a real browser (Playwright) for the critical flows. Treat the build, the cache-busting strategy and the deployment as part of the product.

Hint: One line builds a URL from user input; the other builds HTML from server data. (A third problem, out-of-order responses, is a good extra to mention: cancel old requests with AbortController.)

  • Line 2: The query is concatenated into the URL without encodeURIComponent(q): characters like &, # or spaces change the request and can inject extra parameters.
  • Line 4: innerHTML with untrusted titles is stored/reflected XSS: a title containing <img onerror=…> runs script as your site. Build elements with textContent (or escape/sanitise).

2. Quick check back ↑

B. Static generation (SSG) served from a CDN

Pre-built HTML from a CDN has the lowest latency and no server work. Rebuild when content changes.

3. Quick check back ↑

B. Reserve space (width/height or aspect-ratio) for images, embeds and late-loading content

CLS measures unexpected movement. If the browser knows the size up front, nothing shifts when the content arrives.

4. Quick check back ↑

B. Cancel the previous request with AbortController (and ignore stale responses), optionally debouncing input

Responses can arrive out of order. Abort the superseded request or tag each request and ignore the outdated one.

5. Quick check back ↑

B. Anything shipped to the browser is public; keep secrets on a server, and rely on server-side authorisation for public keys

Build-time variables end up in the bundle. A public project identifier is fine only because authorisation is enforced elsewhere.

6. Check 1 back ↑

C. Build elements with textContent or an escaping framework plus sanitisation and a Content-Security-Policy

Untrusted strings in innerHTML execute as markup; textContent keeps them as text and CSP limits script sources.

7. Check 2 back ↑

A. An idempotent endpoint so retries are safe, with rollback on failure

Optimistic UI bets the request succeeds; idempotency makes retries safe and rollback covers rejection.
