Integration and stability

How acceleration becomes motion, why the obvious method explodes, and which integrator to use.

Simulating motion

Physics gives you forces, so accelerations: a = F / m. To get motion you must integrate: velocity is the integral of acceleration, position the integral of velocity. Computers do it in small steps of size dt, approximating the continuous curve with straight segments. How you take each step decides whether the simulation is accurate, stable, or blows up.

Explicit (forward) Euler

position += velocity * dt
velocity += acceleration * dt

The most natural code, and the worst. It uses the old velocity to move, so each step overshoots a little. For anything that oscillates (springs, orbits, pendulums, bouncing) the overshoot adds energy every step: the spring swings wider and wider until it explodes. The simulation below shows it.

Semi-implicit (symplectic) Euler

Swap the two lines: update the velocity first, then move with the new velocity.

velocity += acceleration * dt
position += velocity * dt

Same cost, one line moved, and the energy stays bounded: it wobbles around the true value instead of growing. This is the default in most game engines (Box2D, Bullet, Godot's physics) and the right first choice. Note that for a jump under constant gravity the answer is slightly different from explicit Euler: how high you jump depends on the integrator and the step size. That is one more reason to fix the step (game loop lesson).

Velocity Verlet

Uses the average of the old and new acceleration, and is second-order: halving the step cuts the error by four, not two. It is the integrator behind ropes and cloth (next lessons) and molecular simulations.

position += velocity * dt + 0.5 * a_old * dt * dt
a_new = acceleration(position)
velocity += 0.5 * (a_old + a_new) * dt

RK4 and friends

Runge-Kutta 4 evaluates the forces four times per step and is very accurate for smooth problems, but it is not symplectic (energy slowly drifts) and costs four force evaluations. It is used for orbits and vehicle simulations where accuracy per step matters more than cost. For most games, semi-implicit Euler or Verlet with a fixed step is the better trade.

Stability: stiff springs and large steps

Every integrator has a limit. A spring with stiffness k and unit mass oscillates with angular frequency sqrt(k). Semi-implicit Euler is stable only while dt * sqrt(k) < 2; beyond that it explodes whatever you do. That is why a very stiff spring (a character attached to a cursor, a hard suspension) needs a small step, substeps (run the physics 2 to 8 times per frame), or an implicit method that is unconditionally stable (it solves for the new state instead of extrapolating) at the price of a bit of artificial damping.

Damping and friction

Real systems lose energy. Simple damping: velocity *= pow(damping_per_second, dt) (not velocity *= 0.99 per frame, which depends on the frame rate: see the smoothing lesson). Add it deliberately; do not rely on integration error to "calm things down", because then the behaviour changes with the step size.

Practical recipe

  1. Fixed timestep for the simulation (60 Hz is common).
  2. Semi-implicit Euler by default; Verlet if you have constraints or want better accuracy.
  3. Substep stiff parts instead of shrinking the global step.
  4. Clamp or cap velocities to stay in the stable range and to prevent tunneling.
  5. Test energy: simulate a frictionless spring or pendulum for 10,000 steps and see if it stays bounded. You will do exactly that in the drill.

Drill: Integrators: why the order of two lines matters

A spring with unit mass accelerates by a = -k * x. An integrator turns acceleration into motion one time step at a time. The obvious version (explicit Euler: x += v*dt; v += a*dt) adds energy every step and the spring slowly explodes. The starter does exactly that. Implement two better ones:

  • semiImplicit (symplectic Euler): update the velocity first, then move using the new velocity. Same cost, but the energy stays bounded.
  • velocityVerlet: x += v*dt + a*dt*dt/2, compute the new acceleration from the new position, then v += (a_old + a_new) * dt / 2. More accurate for the same step size.

The tests run 10,000 steps (k = 4, dt = 0.01) and check how far the total energy v²/2 + k x²/2 drifts, and compare positions with the exact solution cos(t) for k = 1.

Starter (Zig):

const std = @import("std");

pub const State = struct { x: f64, v: f64 };

// Spring with unit mass: acceleration = -k * x.
// The starter is explicit Euler, which gains energy every step. Fix both functions.
pub fn semiImplicit(s: State, k: f64, dt: f64) State {
    const a = -k * s.x;
    return .{ .x = s.x + s.v * dt, .v = s.v + a * dt };
}

pub fn velocityVerlet(s: State, k: f64, dt: f64) State {
    const a = -k * s.x;
    return .{ .x = s.x + s.v * dt, .v = s.v + a * dt };
}

Answer key

1. Integrators: why the order of two lines matters back ↑

Hint: semiImplicit: v_new = v + (-k*x)*dt; x_new = x + v_new*dt. velocityVerlet: a = -k*x; x_new = x + v*dt + 0.5*a*dt*dt; a_new = -k*x_new; v_new = v + 0.5*(a + a_new)*dt.

Gaffer On Games, "Integration Basics", is the reference. Explicit Euler is first-order and unconditionally unstable for oscillators; semi-implicit Euler is also first-order but symplectic, which is why it is what most game physics engines (Box2D, Bullet, Godot) use. Verlet is second-order and the basis of rope and cloth. RK4 is more accurate per step but costs four force evaluations, usually not worth it for games. Whatever you pick, integrate with a fixed timestep (see the game loop lesson): a variable dt makes the energy behaviour unpredictable.
