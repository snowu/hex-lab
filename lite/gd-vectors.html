Vectors, movement and steering

Position, direction, speed, and the two operations (dot and cross) that answer most gameplay questions.

A vector is a pair (or triple) of numbers. It can mean a position (where), a displacement (from here to there) or a velocity (displacement per second). Most game maths is moving things with them.

The operations you use every day

OperationWhat it gives you
a + b, a - bCombine movements. target - self is the vector pointing from you to the target.
v * sScale. velocity * dt is how far you move this frame.
length(v)Distance or speed. Use length_squared to compare distances without a square root.
normalize(v)Same direction, length 1. Guard against the zero vector.
dot(a, b)How much two directions agree: 1 same, 0 perpendicular, -1 opposite (for unit vectors).
cross(a, b) (2D)Which side b is on relative to a (sign), and the area of the parallelogram.
lerp(a, b, t)Point a fraction t of the way from a to b.

Questions the dot product answers

  • Is the player in front of the guard? dot(guard.facing, normalize(player - guard)) > cos(half_fov). No angles or trig needed.
  • How fast am I moving toward the goal? dot(velocity, direction_to_goal).
  • Slide along a wall: remove the part of the velocity that points into the wall: v - n * dot(v, n) for a unit normal n. That one line is how characters glide along walls instead of sticking.

The diagonal-speed bug

Holding right and up gives input (1, 1) which has length 1.414. If you multiply that by speed, diagonal movement is 41% faster. Normalise (or clamp the length), then scale. In the drill you cap a velocity vector by its length, not per axis.

Angles

Use atan2(y, x) (never atan(y/x), which loses the quadrant and divides by zero) to get a heading, and avoid storing angles when a direction vector works. Interpolating angles needs wrap-around care (350° to 10° is a 20° turn, not 340°). Godot's lerp_angle handles it.

Screen versus maths axes. In 2D engines y usually grows downward. Rotation sign, "up" and cross-product signs all flip. Write a comment the first time you rely on it.

Drill: Acceleration with a speed cap

Implement accelerate(v, a, dt, max_speed): add a * dt to the velocity, then limit the length of the resulting vector to max_speed, keeping its direction.

The classic bug: clamping x and y separately lets diagonal movement be about 41% faster than straight movement.

Starter (Zig):

const std = @import("std");

pub const Vec2 = struct { x: f32, y: f32 };

pub fn accelerate(v: Vec2, a: Vec2, dt: f32, max_speed: f32) Vec2 {
    _ = a;
    _ = dt;
    _ = max_speed;
    return v;
}

Answer key

1. Acceleration with a speed cap back ↑

Hint: speed = sqrt(x*x + y*y). If speed > max_speed, multiply both components by max_speed / speed. If speed is 0 you never enter the branch, so there is no division by zero.

The same idea in one line of GDScript: velocity = velocity.limit_length(max_speed). Normalising input before multiplying by speed is the other half: Input.get_vector() already returns a length-clamped vector, which is why it exists.

2. Quick check back ↑

A. dot(f, normalize(d)) > cos(45°)

Half of 90° is 45°. A unit-vector dot product equals the cosine of the angle between them, so compare with cos(45°) (about 0.707). Add a distance check for range.

3. Quick check back ↑

B. v - 2 * n * dot(v, n)

Reflection: subtract twice the component of v along the normal. -v only works for a head-on hit. Subtracting just once (v - n * dot(v, n)) is the “slide along the wall” projection instead.

4. Check 1 back ↑

B. Normalise or clamp the input length before scaling by speed, since (1, 1) has length 1.414

The diagonal input vector is 41 percent longer, so cap by length before applying speed.

5. Check 2 back ↑

A. Compare length_squared against the squared ranges to skip the square root

Squared distances order the same as distances, so length_squared answers nearer-or-farther with no square root.
