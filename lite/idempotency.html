Idempotency & exactly-once effects

Make retries safe. Implement an idempotency-key store.

Networks fail after the server did the work. The client cannot tell, so it retries. Without idempotency a retried “pay €100” pays twice. The standard solution: the client sends an Idempotency-Key (UUID) per logical operation; the server stores the result under that key and returns it on repeats.

The details that get asked

  • Same key, different payload → reject (422/409), it is a client bug.
  • Concurrent duplicate while the first is in flight → return 409 / wait; never run twice.
  • Failure semantics: store the outcome only when it is deterministic; allow retry after transient failure.
  • Scope keys per customer; expire them (e.g. 24h) and say so in the API docs.
  • Atomicity: claim the key and perform the effect in one DB transaction (unique constraint on key), or use the outbox.

Challenge (Python): Idempotent handler wrapper

Implement make_idempotent(handler) returning an async function call(key, payload) (the handler is async def handler(payload)):

  • The first call with a key runs the handler and caches the result.
  • A repeat with the same key and an equal payload returns the cached result without calling the handler again.
  • Same key but a different payload: raise ValueError('key reused with different payload').
  • Concurrent duplicates (the first still running) must share the same in-flight work, so the handler runs once.
  • If the handler raises, do not cache the failure: a later retry with the same key may run again.

Starter:

import asyncio
import json

def make_idempotent(handler):
    async def call(key, payload):
        pass
    return call

Answer key

1. Retrying a charge back ↑

B. 40 then "balance: 40"

The first call charged 30 (balance 70) but timed out, so the client retried and charged another 30. The customer paid 60 for a 30 purchase. An idempotency key lets the server recognise the retry and return the first result instead of applying it again.

2. Idempotent handler wrapper back ↑

Hint: Register the key synchronously BEFORE awaiting anything, so a concurrent caller sees it: store (fingerprint, task) with asyncio.ensure_future(handler(payload)). Fingerprint the payload with json.dumps(payload, sort_keys=True). On failure, pop the key.

Reference solution:

import asyncio
import json

def make_idempotent(handler):
    seen = {}  # key -> (payload fingerprint, task)

    async def call(key, payload):
        fingerprint = json.dumps(payload, sort_keys=True)
        hit = seen.get(key)
        if hit is not None:
            if hit[0] != fingerprint:
                raise ValueError('key reused with different payload')
            return await hit[1]
        task = asyncio.ensure_future(handler(payload))
        seen[key] = (fingerprint, task)
        try:
            return await task
        except Exception:
            seen.pop(key, None)
            raise

    return call

Real implementations persist this in a database: a unique constraint on (customer, key), a status (in_progress / completed), a lock timeout for crashed workers, and a TTL (for example 24h). The in-memory version only works inside one process.

3. This payment endpoint is idempotent. Is it? back ↑

Hint: Ask what happens if two identical requests arrive together, and what happens if the server dies between two lines.

  • Line 2: Check-then-act is not atomic. Two concurrent requests with the same key both see "no existing record" and both reach the bank. Claim the key first with an atomic insert guarded by a unique constraint.
  • Line 6: The key is recorded only after the side effect. If the process crashes between the bank call and this write, the retry will initiate the payment again. Record the key as in progress before calling the bank, then complete it afterwards.
