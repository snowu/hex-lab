The game loop and delta time

Why a game is a loop, what a frame budget is, and why frame-rate dependent code is the first bug everyone ships.

A game is one loop that runs until you quit. Each trip around it is a frame:

while (running) {
    poll_input();        // what did the player press since last frame?
    update(dt);          // advance the world by dt seconds
    render();            // draw the result
}

At 60 frames per second one frame has 16.6 ms to do all of that (8.3 ms at 120 Hz, 33 ms at 30). That is the frame budget. Miss it and the player sees stutter. Everything else in this track is about spending that budget wisely or making the game behave when you overspend it.

Delta time

If you move a character by 5 pixels each frame, it moves 300 px/s on a 60 Hz monitor and 720 px/s on a 144 Hz one. The game plays at different speeds on different machines. The fix is to move by speed × dt, where dt is the real time the last frame took:

# GDScript (Godot 4)
func _process(delta):
    position.x += speed * delta         # speed in px/s, correct at any frame rate

That handles movement, but not everything. Physics integration, collision and anything that must be reproducible still depends on how big dt is (try the simulation below).

Fixed timestep

The standard answer is to run the simulation in fixed slices (say 1/60 s) and let the rendering run as fast as it likes:

acc += frame_time;
while (acc >= STEP) {        // catch up in whole steps
    simulate(STEP);
    acc -= STEP;
}
draw(interpolate(acc / STEP)); // blend previous and current state

Now the physics of a jump is identical on every machine and on every replay. You get determinism (replays, rollback netcode, reproducible bugs) for free. Godot does exactly this: _physics_process runs at a fixed rate (60 by default), _process runs every rendered frame.

The spiral of death: if one frame takes 200 ms (alt-tab, a long load, a breakpoint), the loop wants to run twelve physics steps to catch up. Those take longer than a frame, so the next frame is even further behind. Always cap the number of steps per frame and throw the excess away. You will write exactly that in the drill below.

Drill: Fixed timestep with an accumulator

Implement fixed_steps. frame_ms holds the real duration of each frame in whole milliseconds. The game simulates in fixed slices of step ms. For every frame report how many simulation steps ran.

  • Add the frame time to an accumulator, then run one step (subtract step) while the accumulator holds at least one.
  • Spiral-of-death guard: never run more than max_steps in one frame. If you hit the cap and are still behind, throw the rest of the accumulator away (set it to 0) instead of trying to catch up.

Starter (Zig):

const std = @import("std");

/// Writes into out[i] how many simulation steps ran during frame i. out.len == frame_ms.len.
pub fn fixedSteps(frame_ms: []const u32, step: u32, max_steps: u32, out: []u32) void {
    _ = frame_ms;
    _ = step;
    _ = max_steps;
    for (out) |*o| o.* = 0;
}

answer 4 ↓

Think it through: how would you make a game run the same on every machine?

  • Separate simulation (fixed step, deterministic) from rendering (as fast as possible, interpolated).
  • Never use frame count as time. Use dt or the fixed step.
  • Cap catch-up steps (spiral of death) and decide what to drop: time, not state.
  • Seed all gameplay randomness, keep it out of rendering (see the procgen lesson).
  • Floating point is deterministic on one machine and compiler but can differ across platforms. For lockstep multiplayer use fixed-point or integers.

Answer key

1. Quick check back ↑

B. It moves 2.4 times faster, because the function runs 2.4 times as often

The update is per frame, not per second. Multiply by delta (5 * 60 * delta if you think in px/s) so distance depends on time, not on how many frames happened.

2. Quick check back ↑

B. _physics_process runs at a fixed rate for stable simulation, _process runs every rendered frame for visuals and UI

Physics and gameplay that must be deterministic go in the fixed-rate callback; per-frame visuals (animation blending, UI, camera smoothing) go in _process.

3. Fixed timestep with an accumulator back ↑

Hint: acc += t; then while (acc >= step and n < max_steps) { acc -= step; n += 1 }. Afterwards, if acc is still >= step you were behind: acc = 0. Only drop on a real backlog ([50] with step 10 and cap 5 runs exactly 5 and leaves 0 anyway).

Gaffer On Games, "Fix Your Timestep", is the reference. The simulation stays deterministic because it only ever sees the same dt, and rendering interpolates with alpha = acc / step. Without the cap one long frame (alt-tab, a breakpoint) makes the next frame run hundreds of steps, which takes longer, which makes the backlog bigger: the spiral of death.

4. Spot the frame-rate bugs back ↑

Hint: One mistake is about which callback this is in, one is about time, one is about doing the same lookup 60 times a second.

  • Line 7: Physics movement (velocity, gravity, move_and_slide) belongs in _physics_process. In _process the collision step runs at the display rate, so tunnelling and tuning vary between machines.
  • Line 9: velocity.y += gravity adds a fixed amount every frame, so gravity is three times stronger at 180 fps than at 60. Use gravity * delta (with gravity in px/s²).
  • Line 10: get_node with an absolute path every frame walks the scene tree each time. Cache it once (@onready) or better, have the UI listen to a signal when health changes.
