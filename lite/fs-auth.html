Auth: sessions, JWTs, OAuth and row-level security

Authentication vs authorisation, verifying tokens correctly, and letting the database enforce tenancy.

Authentication answers “who are you?”; authorisation answers “what may you do?”. Most real breaches are authorisation bugs (the BOLA/IDOR from the code-review lesson), not broken login.

Verifying a JWT correctly

  1. Parse the three parts: header.payload.signature (base64url JSON).
  2. Choose the algorithm yourself: never trust the header's alg (the none and algorithm-confusion attacks).
  3. Verify the signature (HMAC with a shared secret, or RSA/ECDSA with the issuer's public key from its JWKS, handling key rotation).
  4. Check the claims: exp (required), nbf, iss, aud, and a little clock skew.
  5. Only then read sub.

Because a JWT cannot be revoked, keep access tokens short-lived and use a refresh token (stored more carefully, rotated on use) to get new ones.

OAuth 2.0 / OpenID Connect in one paragraph

For browser and mobile apps use the authorization code flow with PKCE: the app sends the user to the identity provider with a hashed code_challenge; after login the provider redirects back with a one-time code; the app exchanges it, proving possession with the original code_verifier, for tokens. PKCE means an intercepted code is useless. OIDC adds an ID token (who the user is) on top of OAuth's access token (what the app may call). Do not use the implicit flow.

Passwordless: email code vs magic link

A magic link with PKCE depends on a verifier stored in the browser that requested it, so opening the email on a different device fails. A typed one-time code works on whichever device you are on. (This is the reason a cross-device cloud save should sign in with a code.) Rate-limit code attempts and keep codes short-lived.

Row-level security: the database as the tenant boundary

With Supabase the browser holds a publishable (anon) key that only identifies the project, plus the user's own JWT. PostgREST sets the JWT claims for the query, and RLS policies decide which rows are visible:

alter table notes enable row level security;
create policy "own rows" on notes
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
  • Even if an API route forgets a WHERE user_id = ..., the database still refuses other tenants' rows. Defence in depth for BOLA.
  • The service-role key bypasses RLS: never ship it to a browser or commit it. Only a trusted server may hold it.
  • A common pattern: a thin backend (a Worker) that holds secrets and forwards the user's JWT to the database, so RLS still applies instead of the backend acting as an all-powerful user.
  • Write functions as security invoker so they run with the caller's permissions, and revoke execute ... from public, anon.

Challenge (Python): Verify a JWT (HS256)

Write verify_jwt(token, secret, *, now, issuer=None, audience=None, leeway=0) for HS256 tokens. Return the claims dict, or raise ValueError with exactly one of these messages:

  • 'malformed token': not three dot-separated base64url parts holding JSON objects.
  • 'unsupported alg': the header alg is anything but HS256 (including none: never let the token choose its own verification).
  • 'bad signature': HMAC-SHA256 of header.payload does not match (compare in constant time).
  • 'missing exp', 'token expired' (when now >= exp + leeway), 'token not yet valid' (when now < nbf - leeway).
  • 'wrong issuer' / 'wrong audience' when you were given an expected value and the claim differs (aud may be a string or a list).

Check in that order. Times are in seconds.

Answer key

1. Verify a JWT (HS256) back ↑

Hint: Split into three parts, base64url-decode with padding fixed (part + "=" * (-len(part) % 4)), json.loads, check header["alg"] first, then recompute hmac.new(secret, f"{h}.{p}", sha256).digest() and compare with hmac.compare_digest, then the time and identity claims in the stated order.

Reference solution:

import base64
import hashlib
import hmac
import json

def _b64d(part):
    return base64.urlsafe_b64decode(part + '=' * (-len(part) % 4))

def verify_jwt(token, secret, *, now, issuer=None, audience=None, leeway=0):
    try:
        header_b64, payload_b64, sig_b64 = token.split('.')
        header = json.loads(_b64d(header_b64))
        claims = json.loads(_b64d(payload_b64))
        sig = _b64d(sig_b64)
    except (ValueError, AttributeError, TypeError):
        raise ValueError('malformed token')
    if not isinstance(header, dict) or not isinstance(claims, dict):
        raise ValueError('malformed token')
    if header.get('alg') != 'HS256':
        raise ValueError('unsupported alg')
    expected = hmac.new(secret.encode(), f'{header_b64}.{payload_b64}'.encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(sig, expected):
        raise ValueError('bad signature')
    exp = claims.get('exp')
    if not isinstance(exp, (int, float)):
        raise ValueError('missing exp')
    if now >= exp + leeway:
        raise ValueError('token expired')
    nbf = claims.get('nbf')
    if nbf is not None and now < nbf - leeway:
        raise ValueError('token not yet valid')
    if issuer is not None and claims.get('iss') != issuer:
        raise ValueError('wrong issuer')
    if audience is not None:
        aud = claims.get('aud')
        if audience not in (aud if isinstance(aud, list) else [aud]):
            raise ValueError('wrong audience')
    return claims

The attacks this blocks: alg=none, algorithm confusion (RS256 key used as an HS256 secret), tampered claims, replay after expiry, and tokens meant for another service. Real systems verify against the issuer’s public keys (JWKS) and handle key rotation. A JWT cannot be revoked before it expires, which is why access tokens are short-lived.

2. Spot the token-handling mistakes back ↑

Hint: One line trusts the attacker for how verification works. The other trusts a token that may be stale or meant for someone else.

  • Line 4: The token chooses its own algorithm: alg: none skips verification entirely, and a forged header can steer you into a weaker or confused algorithm. The server must decide the algorithm (and the key) itself.
  • Line 6: Returns sub without checking exp, nbf, iss or aud: expired tokens and tokens issued for another service are accepted forever.
