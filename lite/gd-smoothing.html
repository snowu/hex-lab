Interpolation, easing and smoothing

Lerp, easing curves, and the classic “lerp smoothing is broken” bug that makes cameras feel different at every frame rate.

Lerp, and what it is not

lerp(a, b, t) = a + (b - a) * t. For a fixed t from 0 to 1 it is a straight blend, and that is how you animate over a fixed duration: advance t = elapsed / duration and apply an easing function to change how it feels.

Easing

  • Ease-out (fast then slow) feels natural for things that arrive (UI sliding in, a card landing).
  • Ease-in (slow then fast) for things leaving or accelerating.
  • Ease-in-out for movement between two rest points.
  • Back/overshoot and bounce for playful feedback, elastic sparingly.
  • Smoothstep 3t² - 2t³ is the cheap polynomial ease you will see in shaders.

The classic smoothing bug

Camera follow is often written pos = lerp(pos, target, 0.1) every frame. It looks fine and is wrong: the fraction closed per second depends on the frame rate. At 144 fps the camera is far snappier than at 30. The fix treats it as exponential decay:

pos = lerp(pos, target, 1.0 - exp(-k * delta))     # k is the "stiffness", 1/seconds

Splitting a second into 30 or 144 steps now gives the same result, because decay composes: exp(-k·a) · exp(-k·b) = exp(-k·(a+b)). The simulation below shows the naive version needing different times at different frame rates.

Springs

For motion that should overshoot and settle (camera shake recovery, UI bounce, a hanging sign), use a damped spring: accelerate toward the target with a = stiffness * (target - x) - damping * v. Integrate it in your fixed step, or use an analytic solution so large steps stay stable.

Other places this shows up

  • Render interpolation: draw between the previous and current physics state using the fixed-timestep remainder.
  • Animation blending and colour transitions.
  • Audio: fade volumes with a ramp, never snap (it clicks).

Drill: Frame-rate independent smoothing

Smoothing a camera with pos += (target - pos) * 0.1 every frame behaves differently at 30 and 144 fps. Implement damp(current, target, k, dt) so it moves toward target exponentially, and running it for 1 second as one step or as 60 steps of 1/60 s gives the same result. The starter is the naive version, which fails the frame-rate test.

Starter (Zig):

const std = @import("std");

pub fn damp(current: f64, target: f64, k: f64, dt: f64) f64 {
    return current + (target - current) * k * dt;
}

Answer key

1. Frame-rate independent smoothing back ↑

Hint: The exact solution of dp/dt = -k (p - target) is p = target + (p0 - target) * exp(-k * dt). Apply it twice and you get exp(-k * (dt1 + dt2)), which is why splitting the time changes nothing.

Search for "lerp smoothing is broken" for the well-known talk and write-ups. The naive version is also unstable: with k * dt above 2 it overshoots and oscillates. Godot users often write lerp(a, b, 1.0 - exp(-k * delta)) for exactly this reason.

2. Quick check back ↑

B. Ease-out

Ease-out starts fast (immediate feedback) and decelerates into the final value.

3. Quick check back ↑

B. The speed of convergence depends on the frame rate

Every frame closes 10%, so more frames per second means closing more per second. Use 1 - exp(-k * delta).

4. Check 1 back ↑

A. Ease-out, because it starts fast for immediate feedback then decelerates into the final value

Ease-out matches arriving motion: fast response up front, gentle landing at the target.

5. Check 2 back ↑

B. A damped spring that accelerates toward the target with stiffness minus damping, integrated in the fixed step

Springs carry velocity through the target so they overshoot and settle; plain lerp can only approach monotonically.
