Kafka: partitions, groups, delivery guarantees

What you must be able to explain, plus partitioner and assignment code.

Mental model

Kafka is a distributed, partitioned, replicated commit log. A topic is split into partitions; each partition is an ordered, append-only log with a leader and follower replicas. Messages keep their position (offset), and consumers track their own offsets, so reading does not delete data (retention is time/size based; compacted topics keep the latest value per key).

ConceptWhy it matters
Key → partitionhash(key) mod partitions keeps all events of one entity (e.g. a payment id) in one partition, so they stay ordered. Ordering is guaranteed only within a partition.
Consumer groupPartitions are divided among the group’s consumers; each partition is read by one consumer per group. More consumers than partitions → idle ones. Different groups each get all messages.
RebalanceWhen members join/leave, partitions are reassigned and processing pauses. Prefer cooperative/sticky assignors, static membership, and short, idempotent processing.
Replicationreplication.factor=3, min.insync.replicas=2, producer acks=all: survives a broker loss without losing acknowledged writes (at the cost of latency).
Producer idempotenceenable.idempotence=true dedupes producer retries inside a partition.

Delivery semantics

  • At-most-once: commit offset before processing; a crash loses messages.
  • At-least-once (the usual default): process, then commit; a crash causes redelivery, so consumers must be idempotent.
  • Exactly-once exists inside Kafka (idempotent producer + transactions, read-process-write between topics), but not for external side effects such as calling a bank. For those: at-least-once + idempotency keys / dedupe table / outbox.

Operational realities

  • Poison messages: retry with backoff topics, then a dead-letter topic, never block a partition forever or silently skip.
  • Hot partitions: a skewed key (one huge merchant) overloads one partition. Salt the key if ordering allows.
  • Consumer lag is the key health metric. Alert on lag growth rate and age of the oldest unprocessed message.
  • Schemas: use a schema registry (Avro/Protobuf/JSON Schema) with compatibility rules so producers cannot break consumers.
  • Partition count is hard to change safely (it remaps keys), so size it for the future.

Predict the output: What does a crash before the commit cause?

A tiny at-least-once consumer: process, then commit. It crashes while handling the second message, then restarts.

log = ['pay-1', 'pay-2', 'pay-3']
committed = 0                      # next offset to read
processed = []

def consume(crash_after):
    global committed
    for i in range(committed, len(log)):
        processed.append(log[i])           # side effect
        if i + 1 == crash_after:
            return                         # crash before the commit below
        committed = i + 1                  # commit after processing

consume(2)    # crashes while handling pay-2
consume(99)   # restart
print(','.join(processed))

Kafka vs SQS/RabbitMQ: how to answer

  • Kafka: replayable log, high throughput, ordering per key, multiple independent consumer groups, stream processing. You manage partitions/ordering; heavier to operate (or use MSK/Confluent).
  • SQS: fully managed queue, per-message ack, visibility timeout, DLQ built in, effectively unlimited scale; no replay, no ordering unless FIFO queues (with throughput limits).
  • RabbitMQ: rich routing (exchanges), per-message ack, good for task queues and complex routing; lower throughput than Kafka.
  • Pick by need: replay/fan-out/stream processing → Kafka; simple decoupled jobs → SQS; routing flexibility → RabbitMQ.

Answer key

1. Keyed partitioner back ↑

Hint: Validate first (bool is an int subclass, so rule it out), then fnv1a(str(key)) % num_partitions. Python’s % is already non-negative for a positive modulus.

Reference solution:

def fnv1a(text):  # 32-bit FNV-1a
    h = 2166136261
    for ch in text:
        h ^= ord(ch)
        h = (h * 16777619) & 0xFFFFFFFF
    return h

def partition_for(key, num_partitions):
    if not isinstance(num_partitions, int) or isinstance(num_partitions, bool) or num_partitions <= 0:
        raise ValueError('num_partitions must be a positive integer')
    return fnv1a(str(key)) % num_partitions

Kafka’s default partitioner uses murmur2 on the key bytes. Never use Python’s built-in hash() for this: string hashing is randomised per process (PYTHONHASHSEED), so different producers would disagree. Follow-up: what happens to ordering if you increase the partition count?

2. Range assignment for a consumer group back ↑

Hint: divmod(num_partitions, len(consumers)) gives the base size and the remainder. Walk the sorted consumers with a running start offset.

Reference solution:

def assign_range(num_partitions, consumers):
    ordered = sorted(consumers)
    if not ordered:
        return {}
    base, extra = divmod(num_partitions, len(ordered))
    out, start = {}, 0
    for i, consumer in enumerate(ordered):
        count = base + (1 if i < extra else 0)
        out[consumer] = list(range(start, start + count))
        start += count
    return out

Compare with round-robin (spreads evenly across topics), sticky (minimises movement on a rebalance) and cooperative-sticky (incremental rebalance without stopping the world).

3. What does a crash before the commit cause? back ↑

B. pay-1,pay-2,pay-2,pay-3 then "committed 3"

pay-2 was processed but never committed, so after the restart it is read again: the side effect runs twice. That is at-least-once delivery. The fix is not to avoid it but to make the handler idempotent.

4. Quick check back ↑

B. Use the payment id as the message key so they hash to one partition, and process each partition sequentially

Per-key ordering comes from keyed partitioning plus sequential processing per partition. Parallelise across keys, not within one.

5. Quick check back ↑

B. The message is redelivered (at-least-once), so the DB write must be idempotent (upsert by event id / unique constraint)

Kafka’s transactional exactly-once does not extend to your database. Make handlers idempotent or use the transactional outbox/inbox pattern.

6. Quick check back ↑

B. 8 consumers are idle; parallelism is capped by the partition count

Within a group, one partition → one consumer. Extra members are standby for failover only.

7. Spot the Kafka consumer bugs back ↑

Hint: One line is about ordering of commit vs work. The other is about what happens when the same message arrives twice.

  • Line 3: The offset is committed before the work is done, which is at-most-once. If the process crashes after the commit and before the charge, that payment is lost forever. Commit after processing (at-least-once).
  • Line 4: charge_customer has no idempotency key, so once you fix the ordering and get redelivery, a retry double-charges. Also a malformed payload makes json.loads raise and blocks the partition. Use an idempotency key (for example topic-partition-offset), and send poison messages to a dead-letter topic.

8. Check 1 back ↑

B. Retry with backoff topics and then park the event on a dead-letter topic so the partition can progress

Poison messages must never block a partition forever nor vanish silently. Bounded retries plus a dead-letter topic preserve progress and evidence.

9. Check 2 back ↑

D. Replication factor 3 with min.insync.replicas=2 and producer acks=all: acknowledged writes survive a broker loss but pay extra latency

Durability comes from synchronously replicated writes. The acks=all plus in-sync-replicas quorum trades latency for surviving broker loss.
