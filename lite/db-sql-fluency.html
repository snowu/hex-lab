SQL fluency: joins, windows, anti-joins

The queries senior interviews actually ask, and the NULL traps.

Mental model

A query logically runs: FROM/JOIN → WHERE → GROUP BY → HAVING → window functions → SELECT → DISTINCT → ORDER BY → LIMIT. That is why WHERE cannot see aggregates (use HAVING) and why you cannot filter on a window function directly (wrap it in a CTE).

Joins

NeedUse
Rows that match on both sidesINNER JOIN
Everything from the left, matched where possibleLEFT JOIN (right columns are NULL when no match)
Rows with no match (anti-join)NOT EXISTS (...) or LEFT JOIN ... WHERE right.id IS NULL
Compare rows of one table with each otherself-join, or a window function

NULL: three-valued logic

  • NULL = NULL is not true; use IS NULL. x <> 1 is not true when x is NULL, so those rows disappear.
  • COUNT(*) counts rows, COUNT(col) ignores NULLs, SUM of nothing is NULL (wrap in COALESCE).
  • x NOT IN (subquery) returns no rows at all if the subquery yields any NULL. Prefer NOT EXISTS.

Window functions

FunctionUse
ROW_NUMBER() OVER (PARTITION BY g ORDER BY t DESC)top-1 / top-N per group, dedupe
RANK() / DENSE_RANK()ranking with ties
SUM(x) OVER (PARTITION BY g ORDER BY t)running totals
LAG(x) / LEAD(x)compare with previous/next row (gaps, deltas)
SQLite vs Postgres. The exercises run on SQLite so they work in your browser. Window functions, CTEs and NOT EXISTS are identical. Differences you should know: Postgres has DISTINCT ON, LATERAL, FILTER on aggregates (SQLite has it too), real timestamptz and interval arithmetic (we use julianday here), and RETURNING on every DML statement.

Answer key

1. NULL semantics in SQL back ↑

B. (3, 2), then [], then [(2,)]

COUNT(*) counts all 3 rows but COUNT(x) skips the NULL, so (3, 2). NOT IN against a list that contains NULL makes every comparison UNKNOWN, so no rows are returned. And x <> 1 is UNKNOWN for the NULL row, so only 2 comes back. Three-valued logic bites in production queries.

2. Latest entry per account (window function) back ↑

Hint: ROW_NUMBER() OVER (PARTITION BY account ORDER BY created_at DESC, id DESC) numbers each account's entries newest first. Wrap it in a CTE and keep rn = 1. (In Postgres, DISTINCT ON does this in one line.)

Reference solution:

WITH ranked AS (
  SELECT a.owner, t.id AS tx_id, e.amount_minor,
         ROW_NUMBER() OVER (PARTITION BY a.id ORDER BY t.created_at DESC, t.id DESC) AS rn
  FROM accounts a
  JOIN entries e ON e.account_id = a.id
  JOIN transactions t ON t.id = e.transaction_id
)
SELECT owner, tx_id, amount_minor FROM ranked WHERE rn = 1

The alternative is a correlated subquery or a self-join on MAX(created_at), which breaks on ties. Window functions are the standard answer for "top N per group".

3. Running balance back ↑

Hint: SUM(...) OVER (PARTITION BY account ORDER BY time, id). Always include a unique tiebreaker in the window ORDER BY, otherwise rows with equal timestamps get an arbitrary order. The final ORDER BY is separate from the window ORDER BY.

Reference solution:

SELECT a.owner, t.created_at, e.amount_minor,
       SUM(e.amount_minor) OVER (PARTITION BY a.id ORDER BY t.created_at, t.id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_balance
FROM entries e
JOIN accounts a ON a.id = e.account_id
JOIN transactions t ON t.id = e.transaction_id
ORDER BY a.owner, t.created_at, t.id

The default frame with an ORDER BY is RANGE, which treats rows with equal sort keys as peers and can surprise you. Spell out ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW for a running total.

4. Accounts with no recent activity (anti-join) back ↑

Hint: "No matching rows" is an anti-join: NOT EXISTS (correlated subquery) or LEFT JOIN ... WHERE right.id IS NULL. Prefer NOT EXISTS over NOT IN: if the subquery can return a NULL, NOT IN returns no rows at all.

Reference solution:

SELECT a.owner
FROM accounts a
WHERE NOT EXISTS (
  SELECT 1 FROM entries e
  JOIN transactions t ON t.id = e.transaction_id
  WHERE e.account_id = a.id AND t.created_at >= '2024-06-05'
)

NOT IN (subquery containing NULL) evaluates to UNKNOWN for every row, a classic silent bug. The next predict question shows it.

5. Find double charges (self-join) back ↑

Hint: Join the table to itself. a.id < b.id stops you matching a row with itself and listing every pair twice. Convert the time difference into minutes and check it is between 0 and 10.

Reference solution:

SELECT a.id AS first_id, b.id AS second_id
FROM payments a
JOIN payments b
  ON a.customer_id = b.customer_id
 AND a.merchant_id = b.merchant_id
 AND a.amount_minor = b.amount_minor
 AND a.id < b.id
 AND (julianday(b.created_at) - julianday(a.created_at)) * 1440 BETWEEN 0 AND 10

The proper fix is prevention: an idempotency key with a unique constraint. This query is the detective control that finds what slipped through. At scale you would self-join within a time window using an index on (customer_id, merchant_id, amount_minor, created_at).

6. Quick check back ↑

B. SELECT * FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)

NOT EXISTS is correct even if orders.customer_id contains NULLs, and the planner turns it into an efficient anti-join. NOT IN silently returns nothing if the subquery has a NULL.

7. Check 1 back ↑

B. Only in an outer query or CTE, because WHERE runs before window functions

Logical order runs window functions after WHERE and GROUP BY, so filter on their results one layer out.

8. Check 2 back ↑

A. Use HAVING for the aggregate condition, because WHERE cannot see aggregates

WHERE filters rows before grouping while HAVING filters groups after aggregation.
