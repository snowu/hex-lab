The network and your game

Latency, jitter and loss; client-server versus peer-to-peer; what to send and how small you can make it.

What the network really is

A multiplayer game is a distributed system where the parts must agree about a fast-changing world, over a connection that is slow, unreliable and out of order. Four numbers describe a link:

QuantityMeaningTypical
Latency (ping, RTT)Time for a message to go there and back10 to 30 ms same city, 80 to 150 ms across a continent, 200+ ms across oceans or on mobile
JitterVariation of latency from packet to packetWi-Fi and mobile often ±20 to 50 ms
Packet lossFraction of packets that never arrive0 to 2% normally, bursts much higher
BandwidthBytes per second the link carriesPlenty on average, but limited and metered on mobile; your budget is usually tens of KB/s per player

Light in fibre moves ~200,000 km/s, so 10,000 km costs 50 ms one way before any router adds a thing: you cannot code your way below the physics. Everything in this track is about hiding latency, tolerating loss and keeping everyone's picture consistent.

TCP, UDP and what games use

  • TCP gives a reliable, ordered byte stream. If one packet is lost, everything behind it waits for the retransmission (head-of-line blocking): a lost position update from half a second ago delays the fresh ones. Fine for chat, login, downloads, turn-based games.
  • UDP sends independent datagrams: no ordering, no delivery guarantee, no delay from old packets. Real-time games use UDP and build only the reliability they need on top: unreliable channel for positions (the next update replaces a lost one), reliable ordered for events like "player died" and chat. Libraries: ENet (used by Godot's high-level multiplayer), Steam Networking Sockets, Valve's GameNetworkingSockets, Yojimbo, QUIC.
  • In a browser you get WebSockets (TCP) or WebRTC data channels (UDP-like, unordered/unreliable mode) and WebTransport. A web game on WebSockets suffers head-of-line blocking: keep messages small and design for it.

Ticks and rates

A server simulates in fixed ticks (20, 30, 60, 128 per second). It sends snapshots of the world at a possibly lower rate (10 to 30 Hz is typical). Clients send inputs at their frame rate or the tick rate. Higher rates cost bandwidth and CPU for diminishing returns: choose them from the genre (a turn-based card game needs almost nothing; a competitive shooter needs 60+).

State or inputs?

  • Send state (positions, health): simple, robust, bandwidth grows with the number of things.
  • Send inputs and let everyone simulate: tiny messages, but requires determinism (lockstep lesson).
  • Most real-time games combine them: clients send inputs, the server sends state.

Making it small

Bandwidth is the budget you can plan. Example: 16 players × 20 snapshots/s × 16 entities per snapshot × 12 bytes ≈ 61 KB/s outgoing from the server per client if you send everything to everyone. Tricks, in order of payoff:

  1. Send only what changed (delta compression): against the last snapshot the client acknowledged.
  2. Interest management: only entities near or visible to this player, and at lower rates for far ones.
  3. Quantisation: positions do not need 32-bit floats. If the map is 200 units wide and 1 cm accuracy is enough, a 16-bit integer suffices (below).
  4. Bit packing: a boolean costs 1 bit, not a byte; an enum of 5 values costs 3 bits.
  5. Avoid sending derived data (the client can compute it) and avoid strings (send ids).
  6. Compression (LZ4, zstd) helps larger, less regular messages.
const std = @import("std");

/// Map a float in [lo, hi] onto 0..65535 and back. The error is at most half a step: (hi - lo) / 65535 / 2.
fn quantize(v: f32, lo: f32, hi: f32) u16 {
    const clamped = std.math.clamp(v, lo, hi);
    const t = (clamped - lo) / (hi - lo);
    return @intFromFloat(@round(t * 65535.0));
}

fn dequantize(q: u16, lo: f32, hi: f32) f32 {
    return lo + (@as(f32, @floatFromInt(q)) / 65535.0) * (hi - lo);
}

/// Write a quantised position into 4 bytes (little-endian), the way a snapshot packet would.
fn writePos(buf: *[4]u8, x: f32, y: f32) void {
    std.mem.writeInt(u16, buf[0..2], quantize(x, -100, 100), .little);
    std.mem.writeInt(u16, buf[2..4], quantize(y, -100, 100), .little);
}

fn readPos(buf: *const [4]u8) [2]f32 {
    return .{
        dequantize(std.mem.readInt(u16, buf[0..2], .little), -100, 100),
        dequantize(std.mem.readInt(u16, buf[2..4], .little), -100, 100),
    };
}

test "a position fits in 4 bytes with millimetre-level error on a 200-unit map" {
    var buf: [4]u8 = undefined;
    writePos(&buf, 12.3456, -78.9012);
    const p = readPos(&buf);
    const max_err: f32 = 200.0 / 65535.0 / 2.0 + 1e-4;
    try std.testing.expect(@abs(p[0] - 12.3456) <= max_err);
    try std.testing.expect(@abs(p[1] - -78.9012) <= max_err);
    try std.testing.expectEqual(@as(usize, 4), buf.len); // versus 8 bytes for two f32
}

test "values outside the range are clamped, never wrapped" {
    try std.testing.expectEqual(@as(u16, 65535), quantize(500, -100, 100));
    try std.testing.expectEqual(@as(u16, 0), quantize(-500, -100, 100));
}

Getting started in Godot

Godot 4's high-level multiplayer API sits on ENet (also WebSocket and WebRTC peers). You choose one peer to be the server (id 1), others connect as clients. @rpc functions are remote procedure calls (specify who may call, who runs, and whether it is reliable). The MultiplayerSpawner and MultiplayerSynchronizer nodes replicate scenes and properties for you. They are a good start for turn-based and casual games; for fast-paced games you will want your own snapshot and prediction logic on top (next lessons).

Test with a bad network

Your LAN is a lie. Test with simulated latency, jitter and loss: Linux tc netem, clumsy on Windows, Network Link Conditioner on macOS, browser dev tools throttling, or a built-in toggle in your own game (the simulation in the next lesson has these sliders). If it only works at 0 ms it does not work.

Answer key

1. Quick check back ↑

B. A lost old position is useless anyway; TCP would hold back fresh updates until the lost one is retransmitted (head-of-line blocking)

The next snapshot supersedes the lost one, so retransmitting it wastes time and delays newer data.

2. Quick check back ↑

A. About 7 KB/s (12 × 20 × 30)

12 × 20 bytes = 240 bytes per snapshot, × 30 = 7,200 bytes/s. Delta compression, interest management and quantisation can cut that several times.

3. Quick check back ↑

B. Dedicated authoritative server run by you

If a program you control decides what is true, a hacked client can only send inputs, not facts.

4. Check 1 back ↑

B. You cannot code below the physics of light in fibre: the techniques must hide latency, not eliminate it

Distance sets a floor on latency, so networking is about hiding delay and tolerating loss.

5. Check 2 back ↑

D. Interest management: send only nearby or visible entities, at lower rates for far ones, plus deltas

Not sending irrelevant state beats shrinking it; deltas and quantisation cut what remains.
