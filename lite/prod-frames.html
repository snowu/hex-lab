Frame pacing, threads and job systems

Why average FPS lies, where stutter comes from, and how engines use every core.

The frame budget says the work must fit in 16.7 ms. This lesson is about the two things that budget hides: frames that are uneven, and work that could run on other cores.

Measure frame time, not FPS

  • Think in milliseconds: 16.7 ms at 60 Hz, 8.3 ms at 120 Hz, 6.9 ms at 144 Hz.
  • Averages hide spikes. A frame-time graph and the worst percentiles (99th percentile, “1% lows”) show what players feel.
  • Test on the target hardware, in a long session, with the debug overlay on (see debugging and profiling).

Pacing: frames and the display

  • The display refreshes at a fixed rate. With vsync, a finished frame waits for the next refresh: no tearing, but more input latency, and a frame that misses the deadline is shown twice.
  • Uneven cadence judders. 50 FPS on a 60 Hz display means some frames stay on screen for one refresh and some for two, so motion advances unevenly. A steady 30 often looks better than a wobbly 50. Frame caps should divide the refresh rate, or use variable refresh rate (VRR) displays, which show each frame when it is ready.
  • Double vs triple buffering: triple buffering keeps the GPU busy when a frame misses, at the cost of up to one more frame of latency.
  • Fixed simulation step plus render interpolation (see the game loop) keeps motion smooth even when render frame times vary.

Why threads

Single-core speed has barely grown for years; the number of cores has. A game that runs everything on one thread leaves most of the machine idle. Two common models:

  • Main thread + render thread: the main thread simulates frame N+1 while the render thread submits frame N. Simple and effective, and it adds a frame of latency.
  • Job system: work is cut into small jobs run by a pool of worker threads, about one per core. Jobs declare dependencies, forming a task graph each frame; idle workers steal jobs from busy ones. Big engines run almost everything this way.

What parallelises well

Independent work over many items: animation poses, particles, culling, physics broadphase and separate physics islands, pathfinding requests, audio mixing, asset decompression. Data stored as packed component arrays (see entities and components) splits naturally into ranges, one per job. Gameplay scripts whose order matters, and anything touching the engine’s scene graph, usually stay on the main thread.

Rules that keep it correct

  1. No shared mutable state inside jobs. Each job reads shared input and writes its own output slice. Combine results at a known sync point.
  2. Avoid locks in hot paths. Contended locks serialise threads; atomics on one shared counter cause cache-line ping-pong, and so do two threads writing neighbouring data (false sharing).
  3. Keep results independent of thread count when you need determinism (replays, lockstep): fixed partitioning and ordered reductions, because floating-point sums give different results in a different order.
  4. Finish engine work on the main thread. In Godot, the active scene tree is not thread-safe: compute on a WorkerThreadPool task or a Thread, then hand results back with call_deferred. Load resources with ResourceLoader.load_threaded_request.
// C++ sketch: one job per range, each writes only its own slice
void update_particles(std::span<Particle> ps, float dt, JobPool& pool) {
    const size_t chunk = 4096;
    for (size_t start = 0; start < ps.size(); start += chunk) {
        auto slice = ps.subspan(start, std::min(chunk, ps.size() - start));
        pool.submit([slice, dt] { for (auto& p : slice) p.integrate(dt); });
    }
    pool.wait_all();   // the sync point: after this, the main thread may read every particle
}

Answer key

1. Quick check back ↑

B. First-use work such as shader compilation or a synchronous asset load; pre-warm shaders and preload the enemy during the loading screen

A one-time hitch per new thing points at first-use costs. Move them to load time: preload assets and pre-compile the shaders and pipelines they need.

2. Quick check back ↑

B. Build the data (or nodes not yet in the tree) on the worker, then add them to the active scene tree from the main thread with call_deferred

The active scene tree is not thread-safe. Do the heavy computation off the main thread and hand the result to the main thread to attach.

3. Quick check back ↑

B. The frame rate does not divide the refresh rate, so frames stay on screen for uneven times; cap at 30, reach 60, or use variable refresh rate

Smoothness needs an even cadence. Frames shown for 1, 1, 2, 1, 2 refreshes make motion stutter even at a high average.

4. Check 1 back ↑

B. The frame-time distribution: a frame-time graph and percentiles such as the 99th percentile or “1% lows”, which show the spikes

A single 100 ms frame among fifty 16 ms frames barely moves the average but is a visible hitch. Measure frame times and their worst percentiles.

5. Check 2 back ↑

B. The jobs spend their time waiting on the shared lock; give each job its own pre-sized output slice so they never contend

Parallel work only scales when jobs do not share mutable state. Partition the data, write to separate slices, and combine at a known sync point.
