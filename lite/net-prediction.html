Prediction, interpolation and lag compensation

How a game feels instant at 100 ms: predict yourself, show others in the past, and let the server rewind time for fairness.

The problem

With an authoritative server, pressing "move right" means: send the input (50 ms), the server processes it, sends the result back (50 ms), then you see yourself move. A 100 ms delay on every action is unplayable. Three techniques make a networked game feel as if the delay is not there. They are the standard of every modern action game (Quake, Counter-Strike, Overwatch, Rocket League all use variations). Gaffer On Games and Valve's "Source Multiplayer Networking" page explain them in depth.

1. Client-side prediction (your own character)

The client applies your input immediately using the same movement code as the server, and also sends it with a sequence number. You see yourself move at once. The server later confirms the real result.

2. Server reconciliation

When a snapshot arrives it says "after processing your input number N, you are at P". The client has already moved on past N with inputs the server has not seen. So it rewinds to P and replays the inputs after N to compute the corrected present (the first drill). If the prediction was right, the replay lands on the same position and nothing visible happens. If the server disagreed (you were pushed, or hit a wall you did not know about), the replay produces a different position and you are corrected. Hide the snap with a short smoothing of the visual position.

Requirements: movement must be deterministic given (state, input, dt) so client and server compute the same thing; inputs must be tagged and buffered; everything the server can change (knockback, teleport) must come back in snapshots.

3. Entity interpolation (everyone else)

You cannot predict other players: you do not know their inputs. They arrive as snapshots 10 to 30 times a second, so drawing the latest one makes them jump. Instead draw them slightly in the past, blended between the two snapshots around the render time (the second drill). The delay (typically 100 ms, about two snapshot intervals) guarantees you almost always hold a snapshot on each side. You trade a small, constant visual delay of others for perfectly smooth motion.

Extrapolation (dead reckoning) guesses forward from the last velocity when snapshots run out. Brief extrapolation hides a lost packet; long extrapolation produces rubber-banding corrections. Cap it (about 100 to 250 ms) and hold or fade after that.

4. Lag compensation (shooting fairly)

Because you see others in the past, when you click on a target you are aiming at where it was. The server, receiving your shot later, would find it already moved. Lag compensation: the server keeps a short history of positions and, when processing your shot, rewinds the world by your latency plus interpolation delay and tests the hit against that past state. "What you see is what you hit" for the shooter, at the cost that a player behind cover can be hit slightly "after" reaching it. Limit the maximum rewind (200 ms or so) so high-ping players do not dominate.

Putting it together

ThingTechnique
My own movementPrediction + reconciliation
Other playersSnapshot interpolation (render in the past)
Projectiles you firedPredict locally (spawn immediately), server owns the truth
Hit detectionServer-side with lag compensation
Physics objectsServer simulates; clients interpolate (or predict if you interact)

Things that go wrong

  • Prediction drift: the client's code differs from the server's (different float order, missing a rule). Share the movement code, step with the same fixed dt, and log corrections: frequent ones are a bug.
  • Over-correction jitter: snapping every time a snapshot differs by a pixel. Use a tolerance; correct small errors by blending, large ones by snapping.
  • Interpolation delay too small: you run out of snapshots and objects freeze or extrapolate. Add jitter margin.
  • Visual vs simulation position: keep a separate smoothed render position so corrections do not teleport the camera.
  • Sequence number wrap-around: compare with wrap-aware arithmetic if you use small integers.

Drill: Client-side prediction and reconciliation

In an online game the server is the authority, but waiting a round trip to see your own character move feels terrible. So the client predicts: it applies each input immediately and sends it to the server tagged with a sequence number. Later the server reports "after processing your input number N, you are here". The client must reconcile: start from the server's position and replay the inputs the server has not seen yet.

  • reconcile(server_pos, acked, pending): server_pos plus the dx of every pending input whose seq is greater than acked.
  • dropAcked(pending, acked): how many leading inputs of pending (sorted by increasing seq) have seq <= acked and can be forgotten.

Starter (Zig):

const std = @import("std");

pub const Input = struct { seq: u32, dx: i32 };

/// server_pos is where the server says we were after processing input number acked.
/// Replay the inputs the server has not seen yet (seq > acked) on top of it.
pub fn reconcile(server_pos: i32, acked: u32, pending: []const Input) i32 {
    _ = acked;
    _ = pending;
    return server_pos;
}

/// How many leading inputs (sorted by seq) are acknowledged and can be dropped.
pub fn dropAcked(pending: []const Input, acked: u32) usize {
    _ = pending;
    _ = acked;
    return 0;
}

Drill: Snapshot interpolation for remote players

The server sends a position snapshot 10 to 30 times a second, but you draw 60+ frames a second. To show other players smoothly you render them slightly in the past and blend between the two snapshots around the render time. Implement interpolate(snaps, render_t):

  • Snapshots are sorted by t. Find the two around render_t and blend their x linearly.
  • Before the first snapshot, return the first position; after the last, return the last (hold, no extrapolation).
  • Two snapshots with the same t must not divide by zero.
  • An empty list returns nothing.

Starter (Zig):

const std = @import("std");

pub const Snapshot = struct { t: f64, x: f64 };

/// Position at render_t, blended between the snapshots around it. snaps is sorted by t.
pub fn interpolate(snaps: []const Snapshot, render_t: f64) ?f64 {
    _ = snaps;
    _ = render_t;
    return null;
}

Answer key

1. Client-side prediction and reconciliation back ↑

Hint: Both are single loops over the pending inputs. For reconcile just skip inputs with seq <= acked. For dropAcked count from the front and stop at the first input that is not yet acknowledged.

This is the core of the Quake/Source/Overwatch style of netcode (Gaffer On Games "Networked Physics" and the Valve "Source Multiplayer Networking" page explain it with pictures). It only works if movement is deterministic given the same inputs and the same step, so the client's replay matches the server's processing: another reason for fixed timesteps and no floating-point surprises. Mispredictions (the server says you were blocked) are corrected by replay; a visible snap is hidden by smoothing the error out over a few frames. Other players are not predicted this way: they are shown slightly in the past using snapshot interpolation (the next drill).

2. Snapshot interpolation for remote players back ↑

Hint: If render_t <= first.t return first.x; if >= last.t return last.x. Otherwise find i with snaps[i].t <= render_t < snaps[i+1].t and return lerp with f = (render_t - t0) / (t1 - t0).

Choosing the delay is the design decision: it must cover one send interval plus jitter, so you always have two snapshots to blend between (typically 2 to 3 intervals, 100 ms is common). Too small and you run out of snapshots and the character freezes or you extrapolate and it jitters; too big and others look far behind. This is why shooters need lag compensation on the server: your shot is aimed at what you saw in the past. Interpolate rotation with a slerp/shortest-angle blend, and teleports (respawn) must not be blended.

3. Quick check back ↑

B. Starts from 100 and re-applies inputs 41 to 47 to get the corrected present

The server only knows inputs up to 40. Replaying 41 to 47 on top of its answer restores the client's lead without losing correctness.

4. Quick check back ↑

B. So there are normally two snapshots to blend between, producing smooth motion instead of jumps

Interpolation needs data on both sides of the render time; the delay buys it.

5. Quick check back ↑

B. Lag compensation: the server rewinds other players to what you saw when you fired and tests the hit there

It evaluates the shot against the world as the shooter saw it (within a cap).

6. Check 1 back ↑

A. Prediction drift: the client movement code differs from the server, so sharing the code and stepping with the same fixed dt is required

Frequent corrections signal divergence between the two simulations, not normal network noise.

7. Check 2 back ↑

C. Correct small errors by blending and reserve snapping for large ones, using a tolerance

A tolerance with blend-for-small and snap-for-large hides noise without letting real divergence linger.
