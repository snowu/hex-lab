Animation systems in code

Clips, frame data, animation state machines, blending, root motion and events.

Drawing frames is art. Deciding which frame shows, when it changes, and what gameplay happens on which frame is programming, and it decides how responsive a game feels.

Clips are data

A clip is a list of frames (sprite rects or poses) with a duration per frame, a loop mode (loop, once, ping-pong) and optional events on specific frames. Keep it as data exported from your tool (Aseprite tags and frame durations export to JSON), not hard-coded indexes. Advance clips by elapsed time, not by counting rendered frames, or animation speed depends on the frame rate.

clip "slash": frames [4, 5, 6, 7, 8], durations ms [50, 50, 33, 33, 80], loop: false
  events: frame 6 → "hit_start", frame 8 → "hit_end", frame 5 → "whoosh_sfx"

Who drives whom

The gameplay state machine is authoritative (see input and state machines). The animation layer maps each gameplay state to a clip or blend and reports back through events: “the hit frame happened”, “the clip finished”, “a foot touched the ground” (for footstep sounds and dust). Gameplay never reads “which frame is showing” to make decisions, and animation never guesses the gameplay state from velocity.

Frame data for actions

Action games describe every attack as three phases, in frames of the fixed simulation step:

PhaseWhat happensDesign knob
StartupWind-up; the attack is committed but cannot hit yetLonger startup = easier to react to, feels heavier
ActiveThe hitbox existsHow long the attack threatens space
RecoveryFollow-through; the attacker is vulnerableThe punishment window for whiffing

Cancel windows say when another action may interrupt this one (for example a dodge from frame 12 onwards). Combined with an input buffer, they decide whether controls feel tight or sluggish. Because hitboxes come from frame data on the fixed step, the result is deterministic, which replays and rollback netcode need (see lockstep and rollback).

Transitions

  • A transition table: from state, to state, condition, whether it waits for the clip to end (exit time) or cuts immediately.
  • Priorities and “any state” transitions: hit-stun and death interrupt everything; a jump may interrupt running but not an attack’s active frames.
  • Short transition clips (run → stop skid, land) do the job blending does in 3D, and are the main tool for sprite animation, which cannot blend between frames.

Blending (skeletal animation)

With skeletons (3D, or 2D tools such as Spine), poses can be mixed:

  • Crossfade over 0.1-0.25 s between clips instead of popping.
  • Blend spaces / blend trees: pick and mix clips by a parameter. Idle → walk → run by speed; eight-way strafing by direction.
  • Layers and masks: the upper body plays “shoot” while the legs keep running.
  • Additive clips on top of anything: breathing, recoil, flinch.

Root motion versus code-driven movement

Code-driven: physics moves the character and animation matches it. Responsive, and the default for platformers and most action games. Match the playback rate to the actual speed, or the feet visibly slide. Root motion: the animation’s root bone moves the character, so a lunge covers exactly the distance the animator drew. Great for melee, climbing and cinematic moves, worse for responsiveness. Many games mix them per state.

Procedural touches

Small runtime adjustments sell a lot: IK to plant feet on slopes and point heads at targets, springs for hair, tails and cloth-like secondary motion (see smoothing), and tweens for squash and stretch.

Which clock?

Anything that affects gameplay (hitboxes, invulnerability frames, events that spawn projectiles) advances on the fixed simulation step. Purely visual animation can advance on the render frame and interpolate. Mixing them up is how a game behaves differently at 30 and 144 FPS.

In engines

Godot: AnimationPlayer keys any property and has method-call tracks for events; AnimationTree adds state machines and blend spaces; AnimatedSprite2D covers simple sprite clips. Unity’s Animator and Unreal’s Animation Blueprints implement the same ideas: state machines, blend spaces, layers and notifies (events).

Exercise: write the frame data for one attack

  1. Pick a move from a game you know (or your own). At 60 steps per second, write startup, active and recovery in frames.
  2. Mark the cancel window and what it may cancel into.
  3. List the events and their frames: sound, hitbox on and off, effects, camera.
  4. Write the transition rules into and out of the attack, including which states can interrupt it.
  5. Change one number (startup +4 frames) and write down how the move would feel different. That is the design conversation frame data makes possible.

Answer key

1. Quick check back ↑

B. Scale the playback rate by the actual speed, or blend between walk and run clips by speed, so the stride matches the distance moved

Foot sliding is a mismatch between distance moved and distance the stride covers. Match them with playback rate or a speed-driven blend.

2. Quick check back ↑

B. Add a cancel window to the attack’s frame data so the dodge is allowed only from a chosen frame onwards, keeping startup and part of recovery committed

Commitment is designed in frame data. A cancel window keeps the attack’s risk while still letting skilled players chain moves.

3. Quick check back ↑

B. Frame data stepped by the fixed, deterministic simulation, so every client and every resimulation agrees

Rollback re-runs the simulation many times per frame. Gameplay timing must be a pure function of simulation steps, not of rendering.

4. Check 1 back ↑

B. Apply damage from the attack’s active frames (frame data or an animation event on the contact frame), not on the button press

Gameplay timing for an action belongs in its frame data: startup, active, recovery. The hitbox exists only during the active frames, which match what the player sees.

5. Check 2 back ↑

B. Make the gameplay state the single source of truth: the animation layer maps states to clips (using speed only for blending inside a state) and never guesses gameplay from physics values

Two systems deciding the same thing from different inputs will disagree at the edges. Gameplay decides; animation follows and only uses parameters such as speed to blend within the chosen state.
