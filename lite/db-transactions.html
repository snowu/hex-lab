Transactions, isolation and locking

Anomalies, isolation levels in Postgres, and the right tool for each race.

ACID in one line each: Atomic (all or nothing), Consistent (constraints hold), Isolated (concurrent transactions do not see each other's mess), Durable (committed means safe after a crash). Postgres uses MVCC: each transaction works on a snapshot, so readers do not block writers and writers do not block readers.

Isolation levels in Postgres

LevelWhat you getStill possible
Read committed (default)each statement sees data committed before it startednon-repeatable reads, phantoms, lost updates, write skew
Repeatable readone snapshot for the whole transaction (snapshot isolation; also prevents phantoms in Postgres)write skew. A concurrent update to a row you also change raises 40001 and you must retry
Serializablebehaves as if transactions ran one at a time (SSI)nothing, but any transaction can fail with 40001: retry loops are mandatory

The anomalies, plainly

  • Lost update: two transactions read the same value, both write a result computed from it; one overwrite wins.
  • Non-repeatable read: the same row read twice in one transaction gives two values.
  • Phantom: the same query run twice returns a different set of rows.
  • Write skew: two transactions each read an overlapping set, then write different rows, and together break a rule (two doctors both go off call).

Which tool for which race

ProblemFix
Read-modify-write on one rowAtomic UPDATE ... SET balance = balance - $1 WHERE id = $2 AND balance >= $1 and check the row count; or SELECT ... FOR UPDATE
Work queue with many workersSELECT ... FOR UPDATE SKIP LOCKED LIMIT n
Duplicate creationUNIQUE constraint + INSERT ... ON CONFLICT DO NOTHING
Invariant across rows (write skew)Serializable + retry, or lock the rows you read, or encode the rule as a constraint
Update without holding a lock across user think timeOptimistic locking: a version column and WHERE version = $old
DeadlocksAlways lock rows in the same order (for example by id). Retry on 40P01
Rules of thumb: keep transactions short; never call an external API (a bank!) while holding row locks or an open transaction; always code a retry loop for 40001 and 40P01.

Answer key

1. This withdrawal is not safe back ↑

Hint: Two requests run this function at the same moment. Where can they both be past the same check?

  • Line 2: A plain SELECT takes no lock, so two requests can both read the same balance. Lock the row (SELECT ... FOR UPDATE) or do the check inside the UPDATE.
  • Line 5: It writes a value computed from a stale read, so the second writer overwrites the first (lost update). Use UPDATE accounts SET balance = balance - %s WHERE id = %s AND balance >= %s and treat rowcount == 0 as insufficient funds.

2. Quick check back ↑

B. SELECT ... WHERE status = 'new' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED, then mark it in the same transaction

SKIP LOCKED skips rows another transaction already locked instead of waiting, so workers take different jobs concurrently. The plain SELECT-then-UPDATE races, and a table lock serialises everything.

3. Quick check back ↑

C. Roll back and retry the whole transaction (with a retry limit and backoff)

The database is protecting you from a lost update. The transaction must be retried from the start, since its snapshot is stale. Design every transaction to be safe to retry.

4. Quick check back ↑

B. It holds locks and a connection for as long as the network call takes, and the call cannot be rolled back if the transaction later aborts

Slow external calls turn into lock contention and connection exhaustion, and the side effect is not atomic with the database. Use the outbox pattern: commit the intent, then perform the call from a worker.

5. Check 1 back ↑

C. One atomic UPDATE that decrements only when funds suffice and checking its row count, or locking the row with SELECT FOR UPDATE

Read-modify-write from a stale read overwrites; either lock the row or make the check part of the write itself.

6. Check 2 back ↑

A. Because write skew spans different rows with no write-write conflict, so only Serializable plus retry, locking the rows read, or a constraint stops it

Snapshot isolation catches concurrent writes to the same row, but write skew writes different rows that jointly break an invariant.
