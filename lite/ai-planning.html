Utility AI and planners

Choosing by scores, and planning a sequence of actions toward a goal: two alternatives to hand-written priorities.

Utility AI: choose by scoring

A behaviour tree encodes priorities you decided in advance. Utility AI instead gives every possible action a score from 0 to 1 computed from the current situation, and runs the highest. "Drink a potion" scores high when health is low and potions remain; "attack" scores high when an enemy is close; "take cover" when under fire and the weapon is empty. No explicit priorities: the right behaviour emerges from the numbers.

  • Each action has several considerations: an input (health 0.3) mapped through a response curve (linear, quadratic, logistic or any custom shape) to a 0 to 1 value. Designers shape behaviour by editing curves.
  • Multiply the considerations (any 0 vetoes) or average them with a compensation factor to avoid the score collapsing as considerations are added.
  • Inertia: add a bonus to the action currently running so the agent does not flip-flop when two scores hover around each other (a drill exercise). Other fixes: a minimum action duration, cooldowns.
  • Good for: many competing options (a life simulation: eat, sleep, socialise, work), behaviour that should adapt smoothly, ambient NPCs. The Sims is the classic reference. Dave Mark's talks on "infinite axis utility systems" are the standard source.
  • Weaknesses: scores are hard to tune and debug when there are many actions ("why did it prefer that?") so log the scores, and it expresses sequences poorly.

Planners: let the AI work out the steps

Both trees and utility systems choose among actions you wired up. A planner instead takes a goal and a set of actions described by what they need and what they change, and searches for a sequence that gets from the current state to the goal.

GOAP: goal-oriented action planning

Made famous by F.E.A.R. (Jeff Orkin). The world is a set of boolean facts (hasWeapon, weaponLoaded, enemyDead). Each action has preconditions (facts that must hold), effects (facts it sets or clears) and a cost. The planner runs a search (A* or breadth-first) over world states from the current state to one that satisfies the goal and returns the cheapest action list. The point is emergence and flexibility: if the weapon is already loaded the plan is shorter; if the door is locked the planner may route through the window; designers add an action and the AI finds new ways to use it.

const std = @import("std");

// World facts as bits in a byte.
const HAS_WEAPON: u8 = 1 << 0;
const LOADED: u8 = 1 << 1;
const ENEMY_VISIBLE: u8 = 1 << 2;
const ENEMY_DEAD: u8 = 1 << 3;

const Action = struct {
    name: []const u8,
    needs: u8, // facts that must be true
    sets: u8, // facts made true
    clears: u8 = 0, // facts made false
    cost: u32 = 1,
};

const actions = [_]Action{
    .{ .name = "pick up weapon", .needs = 0, .sets = HAS_WEAPON },
    .{ .name = "load weapon", .needs = HAS_WEAPON, .sets = LOADED },
    .{ .name = "approach enemy", .needs = 0, .sets = ENEMY_VISIBLE, .cost = 3 },
    .{ .name = "shoot", .needs = HAS_WEAPON | LOADED | ENEMY_VISIBLE, .sets = ENEMY_DEAD, .clears = LOADED },
};

/// Cheapest plan as a list of action indices (Dijkstra over the 256 possible states), or null if the goal is unreachable.
fn plan(start: u8, goal: u8, out: []usize) ?usize {
    var dist: [256]u32 = @splat(std.math.maxInt(u32));
    var prev_state: [256]u8 = undefined;
    var prev_action: [256]usize = undefined;
    var done: [256]bool = @splat(false);
    dist[start] = 0;
    while (true) {
        // pick the unfinished state with the smallest distance
        var best: ?usize = null;
        for (0..256) |s| {
            if (!done[s] and dist[s] != std.math.maxInt(u32) and (best == null or dist[s] < dist[best.?])) best = s;
        }
        const cur = best orelse return null;
        if (cur & goal == goal) { // goal facts all true: rebuild the plan backwards
            var n: usize = 0;
            var s: usize = cur;
            while (s != start) : (s = prev_state[s]) n += 1;
            if (n > out.len) return null;
            var i = n;
            s = cur;
            while (s != start) : (s = prev_state[s]) {
                i -= 1;
                out[i] = prev_action[s];
            }
            return n;
        }
        done[cur] = true;
        const cur_state: u8 = @intCast(cur);
        for (actions, 0..) |a, ai| {
            if (cur_state & a.needs != a.needs) continue;
            const next: u8 = (cur_state | a.sets) & ~a.clears;
            const nd = dist[cur] + a.cost;
            if (nd < dist[next]) {
                dist[next] = nd;
                prev_state[next] = cur_state;
                prev_action[next] = ai;
            }
        }
    }
}

test "the planner finds the cheapest sequence and adapts to the starting state" {
    var out: [8]usize = undefined;
    const n = plan(0, ENEMY_DEAD, &out).?;
    try std.testing.expectEqual(@as(usize, 4), n);
    try std.testing.expectEqualStrings("shoot", actions[out[n - 1]].name);
    // already armed and loaded: only approach and shoot are needed
    const short = plan(HAS_WEAPON | LOADED, ENEMY_DEAD, &out).?;
    try std.testing.expectEqual(@as(usize, 2), short);
    // impossible goal
    try std.testing.expect(plan(0, 1 << 7, &out) == null);
}

HTN planners

Hierarchical task networks plan top-down: a goal ("kill the player") decomposes through authored methods into subtasks ("get in range", "attack") until primitive actions remain. Designers keep more control than with GOAP (the structure is authored), and planning is cheaper. Guerrilla's Killzone 2 is the best-known example of an HTN planner in a shipped shooter.

They combine well: a utility layer picks a goal, a planner builds the steps, a behaviour tree or state machine executes them. Start with the simplest that works. Most shipped enemies are a behaviour tree or a plain state machine.

Drill: Utility AI: scoring and not flip-flopping

In utility AI every possible action gets a score from 0 to 1 and the agent does the best one. A score is built from considerations (health is low, enemy is close, ammo left...), each already mapped to 0..1 by a response curve.

  • score(considerations): multiply them, after clamping each to [0, 1]. A 0 vetoes the action. An empty list scores 1.
  • pick(scores, current, inertia): the index of the best action. The action currently running gets inertia added to its score first, so the agent does not flip between two actions whose scores hover around each other. Ties go to the lowest index. Returns nothing for an empty list. A current that is out of range is ignored.

Starter (Zig):

const std = @import("std");

/// Multiply the considerations, each clamped to 0..1. An empty list scores 1.
pub fn score(considerations: []const f64) f64 {
    _ = considerations;
    return 0;
}

/// Index of the best action; the current one gets +inertia. Ties: lowest index. Empty: null.
pub fn pick(scores: []const f64, current: ?usize, inertia: f64) ?usize {
    _ = scores;
    _ = current;
    _ = inertia;
    return null;
}

Answer key

1. Utility AI: scoring and not flip-flopping back ↑

Hint: score: start at 1.0 and multiply by clamp(c, 0, 1). pick: loop i, value = scores[i] + (i == current ? inertia : 0); keep the best with a strict ">" so earlier indices win ties.

Multiplying considerations is the simplest "and" (Dave Mark and Kevin Dill's GDC talks on utility AI are the reference). Designers shape behaviour by editing curves, not code. The inertia (or "commitment") term is not optional in practice: without it two close scores make the agent twitch between actions every frame. Other fixes are a minimum action time and cooldowns. Compare with behaviour trees: utility AI is better at "choose the most appropriate thing now" among many options, trees are better at scripted sequences.

2. Quick check back ↑

B. Add inertia: give the current action a bonus (or a minimum duration) so small score changes do not cause switches

Hysteresis prevents flip-flopping. Without it any utility system twitches around ties.

3. Quick check back ↑

B. Notice the precondition of the next action no longer holds, abandon the plan and replan from the current world state

Plans are valid only while their assumptions hold. Check preconditions as you execute and replan when they fail.

4. Quick check back ↑

A. You want designers to author exact, predictable fights with clear priorities and reuse

Trees give authored control and readability; planners trade some control for flexibility.

5. Check 1 back ↑

D. It scores 0 no matter how good the others are: any 0 vetoes the product

Multiplication makes each consideration a veto, which is why averaging with compensation is sometimes preferred.

6. Check 2 back ↑

B. The planner searches from the current world state, so an already-satisfied precondition shortens the plan

Plans emerge from the start state plus action preconditions and effects, so they adapt to what already holds.
