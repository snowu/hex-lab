CAP, said usefully

During a network Partition you pick Consistency (reject some requests) or Availability (answer, maybe stale). Outside partitions the real trade is latency vs consistency (PACELC). “It depends on the operation” is the right answer: balance display can be stale; double-spending cannot.

Consistency models, by name

“Strong” and “eventual” are the two ends. Senior answers name the guarantee a feature actually needs, because the cheaper ones are often enough:

GuaranteeWhat the user seesTypical way to get it
LinearizableEvery read sees the latest committed write, as if there were one copySingle leader/primary reads, consensus (etcd, Spanner), conditional writes
Read-your-writesYou always see your own changes; others may lagRead from the primary for a short window, or carry a version/LSN token
Monotonic readsYou never see time go backwards between readsPin a session to one replica, or reject replicas older than the last version seen
CausalA reply is never visible before the message it answersTrack dependencies (version vectors), or route causally related data together
EventualReplicas converge if writes stop; any read may be staleAsync replication, caches, CDNs

Map features to guarantees: a balance check before a withdrawal needs linearizable (or a conditional write that enforces it); “I just edited my profile” needs read-your-writes; a feed that flickers between replicas needs monotonic reads; a like counter is fine eventual.

Quick estimation drill

Stream of 2,000 events/s, each 1 KB, retained 30 days. Storage? 2,000 × 1KB = 2 MB/s ≈ 173 GB/day ≈ 5.2 TB/30d, ×3 replicas ≈ 15.6 TB. Say the number, then say what you would do (tiering, compression, shorter hot retention).

Answer key

1. Quick check back ↑

B. Monotonic reads: successive reads hit replicas at different lag, so time appears to go backwards

Each replica is internally consistent; the problem is jumping between them. Pin the session to one replica or carry the last-seen version so lagging replicas are skipped.

2. Quick check back ↑

B. Replication lag; route the user’s reads to the primary for a short window after a write (read-your-writes)

Classic replication lag. Common fixes: sticky reads to the primary after writes, or pass a version/LSN token and read from a replica that has caught up.

3. Quick check back ↑

B. Cache stampede (thundering herd)

Mitigations: request coalescing (single flight), early/probabilistic refresh, jittered TTLs, serving stale while revalidating.

4. Check 1 back ↑

B. Single-flight request coalescing with jittered TTLs or serving stale while revalidating

That collapse is a cache stampede. The mitigations are coalescing concurrent misses, jittered TTLs, early refresh, or stale-while-revalidate.

5. Check 2 back ↑

C. It depends on the operation: a balance display can be stale, but double-spending money cannot

During a partition you pick consistency or availability per operation (PACELC beyond that: latency vs consistency). Correctness requirements decide.
