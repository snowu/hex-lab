Bytecode, scripting and data languages

Why games embed interpreters, how a stack machine works, and where to draw the line between code and scripts.

Why not just write it in the engine language?

Native code is fast, but it has costs that games feel sharply: iteration time (recompiling a C++ or Zig game to tweak a boss takes minutes), safety (a modder's or designer's bug must not crash the game or hang it in an infinite loop), who can write it (designers, modders), and portability (the same behaviour on every platform). The answer in most engines is a scripting layer: GDScript in Godot, C# in Unity, Blueprints in Unreal, Lua in many studio engines.

Levels of "behaviour as data"

  1. Numbers: damage 12, cooldown 0.4 (type object, previous lessons).
  2. Choices of built-in behaviour: "effect: burn, duration 3, damage 2". A fixed menu of effects with parameters. The easiest to make safe and fast.
  3. Expressions: damage = 10 + level * 2. A tiny expression language, usually parsed at load time.
  4. Programs: loops, variables, conditions. Now you have a real language, and the safety questions begin.

Move down the list only when the level above cannot express what designers need. Each step multiplies the work of tooling, error messages and debugging.

Bytecode: a virtual machine

The bytecode pattern defines a tiny instruction set and an interpreter loop that runs it, so behaviour is stored as a flat array of instructions. A stack machine is the simplest design: instructions pop operands from a stack and push results. (2 + 3) * 4 compiles to push 2, push 3, add, push 4, mul. Jumps give you loops and conditions. You write this interpreter in the drill.

# the interpreter is a loop and a switch
while true:
    op = program[pc]; pc += 1
    match op.kind:
        PUSH:  stack.push(op.arg)
        ADD:   b = stack.pop(); a = stack.pop(); stack.push(a + b)
        JZ:    if stack.pop() == 0: pc = op.arg
        HALT:  return stack.pop()

What the VM gives you

  • Sandboxing. The script can only do what instructions allow. A step limit stops infinite loops, a stack limit stops runaway recursion, bounds-checked access stops memory errors. The host cannot be crashed by script bugs.
  • Determinism and serialisation. A program is plain data: saveable, sendable over a network, diff-able, replayable.
  • Hot reload. Swap the program array while the game runs.
  • Portability. The same bytecode runs on every platform the VM runs on (WebAssembly is this idea taken to its conclusion).

Stack vs register machines, and compilers

A stack VM has short instructions and a trivial compiler. A register VM (Lua 5, Dalvik) names its operands and needs fewer instructions to do the same work, which is often faster to interpret. Either way you usually do not write bytecode by hand: a compiler turns a friendly syntax (a visual graph, a text language) into it. Writing a compiler from expressions to a stack machine is a classic first compiler project (post-order traversal of the expression tree).

The honest costs

  • You are building a language: syntax errors, line numbers in error messages, a debugger, documentation. Budget for it, or use an existing one (embed Lua, use GDScript) instead of inventing one.
  • Interpreted code is slower than native. Keep hot loops (physics, pathfinding) native, scripts for decisions and events.
  • The boundary between native and script (what functions the script may call) is the API of your game: design it deliberately and keep it small.

Drill: Bytecode: a tiny stack virtual machine

Game scripting often compiles to bytecode: a flat array of tiny instructions run by a loop. Write the interpreter for a stack machine. The stack holds at most 16 values. Each instruction executed counts as one step.

opeffect
push npush the number (fails with StackOverflow if full)
add sub mul divpop b, pop a, push a op b (div truncates toward zero; b == 0 is DivideByZero). Too few values: StackUnderflow
dup / swapduplicate the top / swap the top two
jz addrpop a value; if it is 0 continue at addr, else carry on
jmp addrcontinue at addr
haltstop and return the value on top of the stack (StackUnderflow if empty)

A jump to an address outside the program is BadJump. Running past the end without halt is NoHalt. More than max_steps steps is StepLimit (this is what stops an infinite loop in a script from freezing the game).

Starter (Zig):

const std = @import("std");

pub const Op = union(enum) { push: i32, add, sub, mul, div, dup, swap, jz: usize, jmp: usize, halt };
pub const VmError = error{ StackUnderflow, StackOverflow, DivideByZero, BadJump, StepLimit, NoHalt };

/// Run the program and return the value on top of the stack when it halts.
pub fn run(program: []const Op, max_steps: usize) VmError!i32 {
    _ = program;
    _ = max_steps;
    return error.NoHalt;
}

Answer key

1. Bytecode: a tiny stack virtual machine back ↑

Hint: Keep pc (program counter), a stack array with a length, and a step counter. Loop: if steps == max_steps return StepLimit; if pc >= program.len return NoHalt; steps += 1; switch on the op. Write small helpers pop() and push() that return the stack errors, so every op stays short.

This is the Bytecode pattern at its smallest. Real engines (Lua, GDScript, Wren, the Godot VM, WebAssembly) are this loop with more opcodes, registers instead of a stack, and type tags. Why bother instead of calling native functions? Safety (a script cannot crash or hang the host: note the step limit and the stack checks), portability, hot reload and modding. Notice how every failure is an explicit error value: in Zig an error set, in C++ a result struct. A "switch (op)" loop is also the interpreter used inside most emulators.

2. Quick check back ↑

B. A per-run instruction (step) budget that aborts the script with an error

Because the host controls the interpreter loop, it can count steps and stop. Native code cannot be stopped this way.

3. Quick check back ↑

B. Per-frame collision detection for thousands of objects

Hot inner loops run every frame on lots of data; interpretation overhead hurts there. Decisions and events are rare and benefit from fast iteration.

4. Quick check back ↑

B. A fixed set of named effects with parameters in data (type object), and add new effect kinds in code when needed

Climb the ladder only as far as necessary. Data with a menu of effects is the cheapest, safest and most debuggable option.

5. Check 1 back ↑

A. push 2, push 3, add, push 4, mul, with jumps for control flow; the interpreter is a loop and a switch over PUSH, ADD, JZ and HALT

Operands are pushed and operators pop them and push results; jumps give branching and looping.
