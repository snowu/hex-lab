Async patterns: pools, retries, timeouts

Concurrency control and resilience with asyncio.

Real services spend their lives waiting on other services. Three utilities show up constantly: bounded concurrency, retry with backoff + jitter, and timeouts. Be able to write each from scratch.

Classic traps: asyncio.gather over 10,000 coroutines starts 10,000 requests at once. Retrying non-idempotent calls can double-charge. Retrying without jitter makes a thundering herd.

Answer key

1. gather: completion order vs result order back ↑

B. done b, done c, done a, then [a, b, c]

The coroutines run concurrently, so they finish in order of their delays: b (20ms), c (40ms), a (60ms). But gather returns results in the order the awaitables were passed in, not the order they completed. If you need completion order, use asyncio.as_completed.

2. map_limit back ↑

Hint: asyncio.Semaphore(limit) as an async context manager around each call, then asyncio.gather the wrapped coroutines (gather keeps input order).

Reference solution:

import asyncio

async def map_limit(items, limit, fn):
    sem = asyncio.Semaphore(limit)

    async def run(i, item):
        async with sem:
            return await fn(item, i)

    return await asyncio.gather(*(run(i, x) for i, x in enumerate(items)))

This creates one task per item, which is fine for thousands but not millions: for huge inputs start “limit” worker tasks that pull from an asyncio.Queue instead. asyncio.TaskGroup (3.11+) gives structured cancellation if one job fails.

3. Retry with exponential backoff back ↑

Hint: A loop over attempt numbers. In the except branch: re-raise if this was the last attempt or the error is not retryable; otherwise sleep and continue. A bare “raise” keeps the original traceback.

Reference solution:

import asyncio

async def default_sleep(ms):
    await asyncio.sleep(ms / 1000)

async def retry(fn, *, retries=3, base_ms=100, sleep=default_sleep, should_retry=lambda e: True):
    attempt = 0
    while True:
        try:
            return await fn(attempt)
        except Exception as e:
            if attempt >= retries or not should_retry(e):
                raise
            await sleep(base_ms * 2 ** attempt)
            attempt += 1

Talking points: full jitter, a retry budget, honouring Retry-After, and only retrying idempotent operations (or those with idempotency keys). Catch Exception, never BaseException: you do not want to swallow cancellation.

4. Spot the concurrency bugs back ↑

Hint: One line starts too much work at once; the other starts work nobody waits for.

  • Line 6: Unbounded concurrency: asyncio.gather over every account starts every bank call at once. With 5,000 accounts that hits bank rate limits and exhausts sockets. Bound it with an asyncio.Semaphore (the map_limit pattern).
  • Line 8: asyncio.create_task without keeping or awaiting the task is fire-and-forget. sync_all returns before mark_synced finishes, exceptions are only logged as "Task exception was never retrieved", and the event loop holds only a weak reference, so the task can even be garbage-collected mid-flight. Await it (gather) or use asyncio.TaskGroup.

5. Quick check back ↑

B. You should respect Retry-After; hammering earlier wastes budget and may get you blocked

The server told you exactly when to come back. Respect it (and cap it), and consider a per-bank circuit breaker so one throttled bank does not consume your worker pool.

6. Check 1 back ↑

C. Bound concurrency with a semaphore or worker pool so only N requests are in flight at once

Unbounded gather starts 10,000 requests at once. Bounded concurrency is the control that protects both your pool and the downstream service.

7. Check 2 back ↑

B. Retrying a non-idempotent call can double-charge, and retrying without jitter causes a thundering herd

The lesson warns retrying non-idempotent calls can double-charge and retrying without jitter makes a thundering herd. Use backoff plus jitter and make the operation safe to repeat.
