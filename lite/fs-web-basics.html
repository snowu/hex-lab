HTTP, caching, CORS and cookies

What the browser, the CDN and your server each decide.

A request, end to end

browser cache → (DNS, TCP, TLS) → CDN / edge cache → your app → database
     each layer can answer instead of the next one

Most performance and many bugs come from not knowing which layer answered. Your tools: Cache-Control, validators (ETag), Vary, and the status code.

Cache-Control in one table

DirectiveMeaning
max-age=Nfresh for N seconds in any cache
s-maxage=Nsame, but only for shared caches (CDNs); overrides max-age there
no-storenever keep a copy (sensitive data)
no-cachemay be kept, but must revalidate before every reuse (not “do not cache”)
private / publiconly the user's browser vs also shared caches
immutablenever changes: skip revalidation (use with hashed file names)
stale-while-revalidate=Nserve stale for N more seconds while refreshing in the background
stale-if-error=Nserve stale if the origin is failing
  • Validators: ETag + If-None-Match returns 304 Not Modified with no body, so revalidation is cheap.
  • Vary: lists request headers that change the response (Accept-Encoding, Origin). A cache keys on them. Never publicly cache a response that depends on Authorization or a cookie.
  • Cache busting: a static host that serves max-age=600 keeps yesterday's script on phones. Put a version in the URL (app.js?v=<commit> or a content hash in the file name) so every deploy is a new URL no cache can hold.
  • Version your cache keys when the shape of a cached payload changes, or old objects will be served to new code.

CORS: what it is and is not

The same-origin policy stops a page on origin A from reading responses from origin B. CORS is how B opts in. It protects the user's browser, not your server: curl ignores it. That is also why a public page cannot call a third-party API directly (it has no CORS headers and you cannot hide a secret in a page): a small backend does the call.

  • Simple requests (GET/HEAD/POST with plain content types, no custom headers) are sent directly; the browser then checks Access-Control-Allow-Origin.
  • Preflighted requests (PUT/DELETE, Authorization, Content-Type: application/json) first send OPTIONS with Access-Control-Request-Method/Headers. Answer with allowed methods/headers and Access-Control-Max-Age.
  • Credentials: cookies need Access-Control-Allow-Credentials: true and an explicit origin (never *). Never reflect any Origin back with credentials: any website could then read your users' private data.
  • Add Vary: Origin whenever the allowed origin varies.

Cookies and CSRF

  • HttpOnly (JavaScript cannot read it, limiting XSS damage), Secure (HTTPS only), SameSite=Lax|Strict|None (cross-site sending), the __Host- prefix.
  • CSRF exists because browsers attach cookies automatically. Defences: SameSite, anti-CSRF tokens, checking Origin. A bearer token in the Authorization header is not attached automatically, so it is not CSRF-prone (but it is exposed to XSS if kept in localStorage).

Challenge (Python): CORS response headers

Write cors_headers(method, request_headers, allowed_origins, allow_credentials=False, allowed_methods=('GET','POST','PUT','DELETE'), allowed_headers=('content-type','authorization'), max_age=600) returning the CORS headers to add to the response (a dict, possibly empty). Rules:

  • Header names in request_headers are case-insensitive. No Origin header, or an origin that is not allowed → {} (the browser will block it).
  • An allowed origin gets Access-Control-Allow-Origin: <that origin> and Vary: Origin. If '*' is in the allow list and credentials are off, any origin gets Access-Control-Allow-Origin: * (no Vary). A wildcard never works with credentials.
  • With credentials add Access-Control-Allow-Credentials: true.
  • A preflight is OPTIONS with Access-Control-Request-Method. The requested method and every requested header must be allowed, otherwise return {}. If allowed add Access-Control-Allow-Methods (all allowed methods, comma-joined), Access-Control-Allow-Headers (the requested headers, only if any were requested) and Access-Control-Max-Age (as a string).
  • Any other method is a normal request: no preflight headers.

Answer key

1. Parse a Cache-Control header back ↑

Hint: Split on commas, strip, then str.partition("=") into name and value. Lowercase the name, strip quotes from the value, and use str.isdigit() to accept only non-negative integers.

Reference solution:

NUMERIC = {'max-age', 's-maxage', 'stale-while-revalidate', 'stale-if-error'}
FLAGS = {'public', 'private', 'no-store', 'no-cache', 'immutable', 'must-revalidate'}

def parse_cache_control(header):
    out = {}
    for part in (header or '').split(','):
        part = part.strip()
        if not part:
            continue
        name, _, value = part.partition('=')
        name, value = name.strip().lower(), value.strip().strip('"')
        if name in out:
            continue
        if name in NUMERIC:
            if value.isdigit():
                out[name] = int(value)
        elif name in FLAGS:
            out[name] = True
    return out

Remember the semantics too: no-store means never keep it; no-cache means keep it but revalidate every time; s-maxage applies only to shared caches (CDNs); immutable promises the URL never changes (use with hashed file names).

2. CORS response headers back ↑

Hint: Lowercase the request header names first. Decide the origin headers, then (only for OPTIONS plus Access-Control-Request-Method) validate the requested method and every requested header against the allow lists, returning {} on any miss.

Reference solution:

def cors_headers(method, request_headers, allowed_origins, allow_credentials=False,
                 allowed_methods=('GET', 'POST', 'PUT', 'DELETE'),
                 allowed_headers=('content-type', 'authorization'), max_age=600):
    req = {k.lower(): v for k, v in request_headers.items()}
    origin = req.get('origin')
    if not origin:
        return {}
    if origin in allowed_origins:
        out = {'Access-Control-Allow-Origin': origin, 'Vary': 'Origin'}
    elif '*' in allowed_origins and not allow_credentials:
        out = {'Access-Control-Allow-Origin': '*'}
    else:
        return {}
    if allow_credentials:
        out['Access-Control-Allow-Credentials'] = 'true'
    wanted = req.get('access-control-request-method')
    if method.upper() == 'OPTIONS' and wanted:
        if wanted.upper() not in {m.upper() for m in allowed_methods}:
            return {}
        asked = [h.strip() for h in req.get('access-control-request-headers', '').split(',') if h.strip()]
        permitted = {h.lower() for h in allowed_headers}
        if any(h.lower() not in permitted for h in asked):
            return {}
        out['Access-Control-Allow-Methods'] = ', '.join(allowed_methods)
        if asked:
            out['Access-Control-Allow-Headers'] = ', '.join(asked)
        out['Access-Control-Max-Age'] = str(max_age)
    return out

CORS protects the user’s browser, not your server: curl ignores it. Never reflect an arbitrary Origin together with credentials, because then any website can read the logged-in user’s data. Vary: Origin keeps shared caches from serving one origin’s headers to another. This is exactly why a public page cannot call an upstream API directly and a small backend (a Worker) does it.

3. Spot the session and CORS mistakes back ↑

Hint: One line is about how the cookie is protected. The other is about who may read authenticated responses.

  • Line 3: The session cookie has no HttpOnly, Secure or SameSite attributes: scripts can read it (XSS steals the session), it can travel over HTTP, and it is attached to cross-site requests (CSRF).
  • Line 4: Reflecting whatever Origin the request sent is the same as allowing every website. Combined with credentials (next line) any malicious page can make the victim’s browser call this API with their cookie and read the response. Allow-list exact origins.
