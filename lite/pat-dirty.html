Dirty flag and caching

Do expensive work only when its inputs changed, and the cache-invalidation bugs that come with it.

The problem

Some values are expensive to compute from other values: a node's world transform from its parents, a bounding box from its children, the shortest path from the map, the layout of a UI panel, the total weight of an inventory. Recomputing them every frame is wasteful when almost nothing changed. Computing them only when something did change is a cache, and the hard part of any cache is knowing when it is stale.

The pattern

Keep a boolean next to the cached value. Every code path that changes an input sets the flag. When someone reads the value: if the flag is clear, return the cache; otherwise recompute, store, clear the flag.

# GDScript
var _dirty := true
var _cached_weight := 0.0

func add_item(item):
    items.append(item)
    _dirty = true                     # the invariant: any change marks it dirty

func total_weight() -> float:
    if _dirty:
        _cached_weight = items.reduce(func(a, i): return a + i.weight, 0.0)
        _dirty = false
    return _cached_weight

Hierarchies: propagate the flag down

In a transform tree, moving a node changes the world transform of all its descendants. So set_local marks the node and every descendant dirty; reading a world value cleans only the nodes you actually read, parent first. Siblings and ancestors are not touched. This is exactly the structure in the drill, and the reason Godot's Node2D.global_position is cheap to read repeatedly.

When to clean: lazily or in a batch

  • Lazy (on read): pay only for what is used, but a read might unexpectedly be slow (a hitch the first time something is read after a big change).
  • Batch (once per frame at a known point): predictable cost, but you may compute things nobody reads, and reads before the clean see stale data.

The bugs

  • Forgetting to set the flag on one path (a second setter, a method that changes the data directly, loading a save). The symptom is "the value is wrong until something unrelated triggers a refresh". Funnel all writes through one function, or make the data private so only code that sets the flag can modify it.
  • Stale reads in the same frame when cleaning is batched.
  • Cleaning too eagerly: marking dirty on every write and recomputing on every read can be slower than no cache if reads and writes alternate. Measure.
  • The related patterns: double buffering (sequencing lesson) and memoization with an explicit key. A version number instead of a boolean ("recompute if my inputs' versions changed") avoids one-dirty-flag-per-reader when many consumers cache the same source.

Where games use it

Transform hierarchies, physics shape updates, navmesh rebuilds, text and UI layout, lighting rebuilds, "the save is out of date" prompts, and shader parameter uploads. Rule: if a value is derived and read more often than it changes, give it a dirty flag.

Drill: Dirty flag: lazy world transforms

In a scene graph a node's world position is its parent's world position plus its own local offset (1-D here to keep it small). Recomputing every world value every frame is wasteful when almost nothing moved. Cache each node's world value with a dirty flag.

  • add(parent, local) returns the new node's index. A parent always has a smaller index than its children.
  • setLocal(i, v) changes the local value and marks that node and all its descendants dirty (their cached world values are now wrong).
  • world(i) returns the world value. If the node is not dirty, return the cache. Otherwise compute it from the parent's (cached or recomputed) world value, store it, clear the flag and add one to recomputes.

The tests count recomputes: an unchanged scene must cost nothing, and changing a node must not recompute its ancestors or its siblings.

Starter (Zig):

const std = @import("std");

pub const Scene = struct {
    const max = 8;

    parent: [max]?usize = @splat(null),
    local: [max]i32 = @splat(0),
    cache: [max]i32 = @splat(0),
    dirty: [max]bool = @splat(true),
    n: usize = 0,
    recomputes: u32 = 0,

    pub fn add(self: *Scene, parent: ?usize, local: i32) usize {
        _ = self;
        _ = parent;
        _ = local;
        return 0;
    }

    pub fn setLocal(self: *Scene, i: usize, v: i32) void {
        _ = self;
        _ = i;
        _ = v;
    }

    pub fn world(self: *Scene, i: usize) i32 {
        _ = self;
        _ = i;
        return 0;
    }
};

Answer key

1. Dirty flag: lazy world transforms back ↑

Hint: Because a parent always has a smaller index than its children, one forward pass after setLocal is enough: for j in i+1..n, if the parent of j is dirty then mark j dirty. world(i) is recursive: base = parent ? world(parent) : 0.

Dirty Flag is cache invalidation with a boolean. The costs are (1) you must set the flag on every path that changes the input (miss one and you get stale data, the classic bug) and (2) you must decide when to clean: lazily on read, like here, or in a batch at a known point in the frame. Engines use it everywhere: transform hierarchies, bounding boxes, navmesh and lighting rebuilds, UI layout, "needs save" markers.

2. Quick check back ↑

B. Moving the parent did not mark its descendants dirty, so their cached world transforms were reused

A dirty flag only works if every change to an input invalidates every dependent cache, including the children.

3. Quick check back ↑

B. Mark dirty on writes (cheap) and recompute lazily once, on the read

Writes only set a boolean; the expensive work happens once when the value is actually needed.

4. Spot the stale-cache bugs back ↑

Hint: Look for the writers of items. One forgets the flag, one clears it by mistake.

  • Line 10: remove_at changes the inputs but never sets _dirty, so the total keeps counting the removed item.
  • Line 14: Loading new items must invalidate the cache (_dirty = true); setting it to false claims the old total is still valid for the new data.

5. Check 1 back ↑

B. A code path changes the inputs without setting the dirty flag; funnel all writes through one function or make the data private so only flag-setting code can modify it

A cache is only correct if every input change invalidates it. One bypassing writer causes stale-until-coincidence bugs.

6. Check 2 back ↑

A. Clean in a batch once per frame at a known point: predictable cost, but you may compute things nobody reads and reads before the clean see stale data

Lazy pays only for what is used but can hitch; batching is predictable but may do wasted work or serve stale reads.
