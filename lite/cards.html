Answer key

1. Card back ↑

What is STAR+?
Situation, Task, Action (in “I”), Result (with a number), plus Reflection: what you learned or changed.

2. Card back ↑

Name the five senior signals interviewers look for.
Scope, handling ambiguity, trade-offs, ownership (operating it), multiplying others.

3. Card back ↑

How should you use AI in an AI-allowed interview?
Follow the policy, think first, treat output as a junior PR, narrate verification (edge cases, tests), and be able to explain every line.

4. Card back ↑

Incident story order?
Detect → mitigate first → diagnose with data → fix & verify → learn (systemic fix, follow-up shipped).

5. Card back ↑

What does a project deep-dive round check?
That you made the key decisions, know their alternatives and costs, can go three levels down, have production numbers, and can say what you would change.

6. Card back ↑

Structure of a project deep dive?
One-minute pitch → the system in one picture → two or three decisions with trade-offs → what went wrong → results with numbers and what you would change.

7. Card back ↑

You reach the edge of what you know in a deep dive. What do you do?
Say so, then reason out loud from what you do know. Never bluff: the interviewer keeps drilling until a bluff shows.

8. Card back ↑

Influence without authority: what must the story contain?
The other side’s constraint, the evidence you brought (prototype, numbers, pilot), how you made yes cheap, and the outcome and relationship afterwards.

9. Card back ↑

How to answer “why are you leaving?”
Toward something: what you want to work on next and why this team has it. One honest sentence about what is missing; no criticism of your employer.

10. Card back ↑

Rules for AI-assisted take-homes?
Disclose how you used AI, commit in small steps, write down decisions and trade-offs, test edge cases, and be ready to extend the code live.

11. Card back ↑

Time plan for a 45-minute design round?
0-5 clarify, 5-10 numbers and API, 10-20 high-level design, 20-38 deep dives, 38-45 operations and wrap-up. Protect the deep dive.

12. Card back ↑

System design framework steps?
Clarify scope → non-functional requirements & numbers → API & data model → high-level design → deep dives → failure, scale, operations.

13. Card back ↑

CAP theorem, usefully?
During a partition choose consistency (reject some requests) or availability (maybe stale answers). Otherwise the trade is latency vs consistency (PACELC). The choice is per operation.

14. Card back ↑

What causes read-your-writes bugs with replicas, and a fix?
Replication lag. Read from the primary for a short window after a write, or use a version/LSN token to read from a caught-up replica.

15. Card back ↑

Cache stampede: what and how to mitigate?
Many requests miss at once when a hot key expires. Mitigate: request coalescing (single flight), jittered TTLs, early refresh, serve-stale-while-revalidate.

16. Card back ↑

Why consistent hashing?
Adding or removing a node moves only ~1/N of keys instead of nearly all with hash mod N. Virtual nodes even out load.

17. Card back ↑

Transactional outbox: purpose?
Write the event to an outbox table in the same DB transaction as the state change; a relay publishes it at-least-once. Avoids lost or phantom events from dual writes.

18. Card back ↑

Little’s Law?
Concurrency = arrival rate × latency. Higher latency means more in-flight requests, which exhausts pools unless you have timeouts and limits.

19. Card back ↑

Amdahl’s Law?
The serial fraction caps speed-up: with 10% serial, max speed-up is 10× regardless of nodes.

20. Card back ↑

Scaling playbook order?
Measure → stateless services → cache/batch/index → async via queues → scale data (replicas, shards) → protect (limits, backpressure, shedding).

21. Card back ↑

Read-your-writes vs monotonic reads?
Read-your-writes: you always see your own changes. Monotonic reads: you never see older data after newer data. Both are weaker and cheaper than linearizable.

22. Card back ↑

Outbox relay: polling vs CDC?
Polling the outbox table is simple but adds latency and DB load. CDC (e.g. Debezium on the WAL) is faster with no polling, but is another system coupled to replication internals. Both are at-least-once.

23. Card back ↑

Order to run a system design interview?
Scope and requirements, numbers, API and data model, high-level design, deep dive on the hardest part, failure/scale/operations. Say assumptions out loud.

24. Card back ↑

Unknown outcome after a timeout calling a bank: what do you do?
Never blindly retry. Query the bank by a deterministic end-to-end reference; create only if absent. Mark the payment unknown and reconcile.

25. Card back ↑

1 million requests per day is how many per second?
About 12 requests per second (1e6 / 86,400). Peak is usually 3-10× the average.

26. Card back ↑

How does an idempotency key work?
Client sends a unique key per logical operation; server stores the result under it and returns it for repeats. Same key + different payload is rejected; concurrent duplicates must not run twice.

27. Card back ↑

Circuit breaker states?
Closed (normal) → open after N failures (fail fast during cooldown) → half-open (one probe; success closes, failure re-opens).

28. Card back ↑

What is a saga?
A sequence of local transactions, each with a compensating action, used when a distributed transaction is not available. Orchestration vs choreography. Compensations must be idempotent.

29. Card back ↑

Why jitter in retries?
Without it, clients retry in sync and create a thundering herd. Use exponential backoff with (full) jitter, a retry budget, and respect Retry-After.

30. Card back ↑

RED vs USE metrics?
RED for services: Rate, Errors, Duration. USE for resources: Utilisation, Saturation, Errors.

31. Card back ↑

Error budget for 99.9% monthly?
About 43 minutes of allowed unavailability per 30 days.

32. Card back ↑

Bulkhead pattern?
Isolate resources (pools/queues) per dependency so one failing dependency cannot starve others.

33. Card back ↑

What is a fencing token?
A number that increases with every lease grant. The protected resource rejects writes carrying a token lower than one it has already accepted, so a paused old lock holder cannot write.

34. Card back ↑

Quorum overlap rule?
R + W > N: every read set overlaps every write set. N=3, W=2, R=2 is typical.

35. Card back ↑

Why are consensus clusters 3 or 5 nodes, not 4?
A majority of 4 is 3, so 4 nodes tolerate one failure, the same as 3. 5 nodes tolerate two.

36. Card back ↑

Raft in two sentences?
Nodes elect a leader for a term by majority vote; the leader appends log entries and commits each once a majority has stored it. A new leader must hold every committed entry.

37. Card back ↑

Lamport clock update rule?
Increment on each local event; on receiving a message set the clock to max(local, received) + 1. If A happened before B then L(A) < L(B), not the reverse.

38. Card back ↑

Why does overload collapse a service?
Unbounded queues make every request old, retries multiply load, and by Little’s law higher latency needs more in-flight capacity. Everything times out together.

39. Card back ↑

Load shedding: what goes first?
Deferrable and background work (refreshes, analytics) before user-facing reads, and reads before money-moving writes. Reject fast with 429/503 and Retry-After.

40. Card back ↑

What is a retry budget?
A cap on retries as a share of traffic (e.g. 10%), applied at one layer only, with backoff and jitter, so retries cannot multiply load during an incident.

41. Card back ↑

Canary vs blue/green vs feature flag?
Canary: gradual traffic share with automated comparison. Blue/green: switch all traffic between two versions. Flag: deploy dark, release per tenant or percentage, kill switch.

42. Card back ↑

Expand/contract migration steps?
Add the new schema, write to both, backfill, switch reads, stop writing the old, remove it. Each step is separately reversible.

43. Card back ↑

What is MCP?
Model Context Protocol: an open protocol where servers expose tools, resources and prompts to AI applications. Treat each server like a dependency: its descriptions and results are prompt input.

44. Card back ↑

Context engineering principles?
Relevant over complete, stable content first (cacheable) and volatile last, compact long histories, keep tool output small, mark untrusted content as data.

45. Card back ↑

How do you protect an LLM feature from model retirement?
Pin versions in config, health checks that call the model, an evaluated fallback model, real provider errors in logs, and deprecation tracking with an owner.

46. Card back ↑

Rules for working with coding agents?
Spec and tests first, small diffs, same review and CI bar as humans, watch for weakened tests, sandboxes and scoped credentials.

47. Card back ↑

What to log for every LLM call?
Feature, model id and version, prompt template version, token counts, latency, cost and outcome (ok, error type, format failure).

48. Card back ↑

Cheapest fixes when LLM output quality is poor, in order?
Better instructions/examples → better context/retrieval → structured output + validation → tools → decompose task → stronger model → fine-tune.

49. Card back ↑

RAG pipeline in one line?
Chunk docs → embed → store vectors; at query time embed query, retrieve top-k similar chunks, put in prompt, answer with citations.

50. Card back ↑

How do you evaluate a RAG system?
Golden question set; measure retrieval (recall@k) separately from generation (faithfulness, correctness); run in CI; spot-check LLM judges.

51. Card back ↑

Prompt injection: core defence?
You cannot prompt it away. Limit blast radius: least-privilege tools, validate tool args server-side, confirm risky writes, break exfiltration channels.

52. Card back ↑

The “lethal trifecta” for agents?
Access to private data + exposure to untrusted content + an outbound/exfiltration channel. Remove at least one.

53. Card back ↑

Common bugs in AI-generated code?
Boundary/off-by-one, hallucinated APIs, floats for money, missing authorisation checks, races/missing awaits, over-engineering, tests that mirror the implementation.

54. Card back ↑

PSD3 vs PSR?
PSD3 is a directive mainly about licensing and supervision; the PSR is a regulation with the conduct rules (APIs, SCA, fraud), directly applicable in every member state.

55. Card back ↑

What does the PSR change for bank APIs?
Mandatory dedicated interfaces with performance parity, a list of prohibited obstacles, a contingency mechanism instead of the fallback interface, and permission dashboards for users.

56. Card back ↑

PSR fraud changes?
Payee name/IBAN verification with a warning before authorisation, bank impersonation fraud treated as unauthorised and refunded, and fraud data sharing under GDPR safeguards.

57. Card back ↑

ASPSP, PSU, TPP, AISP, PISP?
Bank; end user; regulated third party; account-information provider (read); payment-initiation provider (pay by bank).

58. Card back ↑

QWAC vs QSealC?
QWAC: eIDAS cert for mutual TLS (channel identity). QSealC: eIDAS seal cert for signing messages (integrity/non-repudiation).

Why are stacks hard for a solver?
Contacts are coupled. Sequential impulses iterate over all contacts with accumulated impulses and warm starting; more iterations means stiffer stacks.

Raycast vs shape cast?

DDA raycast on a grid?

Move-and-slide steps?

Alpha blend vs additive?
