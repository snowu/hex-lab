Thinking in patterns: sequencing

What a pattern is and costs, then the three that organise time in every game: the game loop, update methods and double buffering.

What a pattern is (and is not)

A pattern is a named solution to a problem that keeps coming back, written down with its trade-offs. The name matters as much as the code: saying "this is an event queue" lets a teammate understand the design in one sentence. It is not a template to stamp on everything. Every pattern has a cost (more indirection, more memory, harder debugging), and the cost is only worth paying when the problem is real.

Before applying any pattern ask three questions:

  1. What exact problem do I have? "The code feels messy" is not one. "Adding a new enemy needs edits in six files" is.
  2. What does the pattern cost here? Indirection makes code harder to follow; caches go stale; queues add latency.
  3. What is the simplest thing that works? A function and a switch beats a framework for three cases. Wait for the third repetition before abstracting ("rule of three").

Patterns in this track are grouped like the book that made them famous: sequencing (this lesson), behaviour (command, state, bytecode, type object), decoupling (observer, event queue, component, service locator) and optimisation (pool, flyweight, dirty flag, spatial partition, data locality). Each lesson ends with a coding drill in Zig and C++ so you build the data structure yourself.

Game loop (recap)

The first lesson of the game loop track covered it: input, update, render, with a fixed timestep for the simulation. The important property for patterns: the loop is the only place that decides when things happen. Everything else is a callback from it. When two systems fight over order, the answer is almost always in how the loop is organised.

Update method

Give every entity an update(dt) and let the loop call it. This is the pattern behind Godot's _process and _physics_process, Unity's Update and Unreal's Tick.

# GDScript: each node has its own update; the engine walks the tree
func _physics_process(delta):
    position += velocity * delta

What it buys you: each object describes its own behaviour in isolation, and the loop does not need to know what objects exist. What to watch for:

  • Order dependence. If A updates before B, A sees B's old state and B sees A's new state. Bugs from this look like "the left enemy is always one frame ahead of the right one".
  • Adding and removing during the loop. An object that spawns a bullet or kills itself while the list is being walked can skip, repeat or crash. Queue spawns and removals and apply them after the pass (Godot: queue_free() and call_deferred exist for this).
  • Too many tiny updates. Ten thousand objects each doing a virtual call and touching different memory is slow. Systems that update arrays of plain data (see the data-locality lesson) fix that.
  • Time. Pass dt, never count frames.

Double buffer

Order dependence has a clean fix when the objects read each other during the update: keep two copies of the state. Everyone reads from the current copy and writes into the next one; when the pass ends, swap them. Now the result does not depend on the update order at all. Conway's Game of Life is the classic example: updating in place corrupts the neighbours that have not been processed yet.

const std = @import("std");

const W = 8;
const H = 8;

/// One Game of Life generation. Reads only from `cur`, writes only to `next`.
fn step(cur: *const [W * H]bool, next: *[W * H]bool) void {
    for (0..H) |y| {
        for (0..W) |x| {
            var n: u8 = 0;
            for ([_]i32{ -1, 0, 1 }) |dy| {
                for ([_]i32{ -1, 0, 1 }) |dx| {
                    if (dx == 0 and dy == 0) continue;
                    const nx = @as(i32, @intCast(x)) + dx;
                    const ny = @as(i32, @intCast(y)) + dy;
                    if (nx < 0 or ny < 0 or nx >= W or ny >= H) continue;
                    if (cur[@as(usize, @intCast(ny)) * W + @as(usize, @intCast(nx))]) n += 1;
                }
            }
            const alive = cur[y * W + x];
            next[y * W + x] = n == 3 or (alive and n == 2);
        }
    }
}

test "a blinker flips between horizontal and vertical, whatever the update order" {
    var a: [W * H]bool = @splat(false);
    var b: [W * H]bool = @splat(false);
    a[3 * W + 2] = true;
    a[3 * W + 3] = true;
    a[3 * W + 4] = true;
    step(&a, &b);
    try std.testing.expect(b[2 * W + 3] and b[3 * W + 3] and b[4 * W + 3]);
    try std.testing.expect(!b[3 * W + 2] and !b[3 * W + 4]);
    step(&b, &a); // swap the roles of the two buffers
    try std.testing.expect(a[3 * W + 2] and a[3 * W + 3] and a[3 * W + 4]);
}

Swapping is just exchanging which buffer plays which role (two pointers, no copying). The same idea is how graphics work: the GPU shows the front buffer while you draw into the back buffer, then they swap, so the player never sees a half-drawn frame. The cost is double the memory and, if the data is large, the time to copy or clear.

Answer key

1. Quick check back ↑

B. Update order: A reads B's old position, B reads A's new one. Read from the previous state and write into a new one (double buffering), or compute all decisions first and move afterwards

In-place updates make results depend on iteration order. Separating "decide from the old state" from "apply the new state" removes the asymmetry.

2. Quick check back ↑

B. Name the problem first, weigh the cost, and prefer the simplest solution until it hurts (about the third repetition)

A pattern is a trade-off, not a virtue. Indirection and caches have real costs; unnecessary ones are the typical beginner mistake.

3. Spot the update-method bugs back ↑

Hint: One is about time, two are about changing a list while walking it.

  • Line 3: e.velocity is added per frame, not per second. Multiply by delta so movement does not depend on the frame rate.
  • Line 5: Erasing from the array being iterated skips the element that slides into the freed slot (or crashes in other languages). Mark the enemy dead and remove it after the loop, or iterate over a copy or backwards.
  • Line 7: Appending to the array being iterated: the new bullet may or may not be visited this frame depending on the engine, and it is a different kind of object stored in the enemy list. Queue spawns and add them after the loop, into the right collection.

4. Check 1 back ↑

C. Queue spawns and removals during the pass and apply them afterwards (Godot queue_free and call_deferred exist for this)

Mutating a list while walking it skips or repeats elements. Deferred add/remove keeps the iteration stable.

5. Check 2 back ↑

A. Keep two buffers: every cell reads from the current copy and writes into the next one, then swap their roles

Double buffering separates deciding from applying, so no cell sees a half-updated neighbour. Swapping is just exchanging roles.
