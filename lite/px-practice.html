Pixel Art · lesson 6 of 6 · 5 min

A practice routine and a reusable editor

Daily drills that build skill quickly, and the design of a pixel editor you can drop into any game project.

Twenty minutes a day beats a weekend a month

  1. Icon of the day (8×8 or 16×16, one palette of 4 to 8 colours): sword, potion, key, mushroom, heart. Timebox it to 15 minutes. Do not undo more than you must.
  2. Copy a sprite pixel by pixel from a game you love, then close it and redraw from memory. You learn how others place pixels, then what you retained.
  3. Ramp study: draw the same sphere three times in three palettes (warm light, cool light, night). Compare with the ramp simulation.
  4. Silhouette thumbnails: draw 10 different monsters as 16×16 black shapes. Keep the three most distinct, give them colour.
  5. Animate a bounce, then a blink, then a walk. Always the same order: bounce first.
  6. Tile a floor with 16 tiles that connect, then build a room from them in the engine.
  7. Once a week, make a small scene (64×64 to 128×128) with background, midground and a character, and post it for feedback.

A reusable editor: spritewright

The editor in the first lesson is a teaching toy. The real tool lives in its own project, spritewright: a dependency-free pixel editor you can use by itself or drop into a game repository.

  • By itself, in a browser. Open the hosted page (snowu.github.io/spritewright): upload a PNG, edit and download it, or pick a project: a GitHub repository (it lists the PNG sprites, you edit, and Propose PR opens a pull request through the GitHub API, forking first if you have no write access) or a folder on your computer (Chromium browsers; Save writes back in place). Nothing to install, nothing added to the game repo.
  • As a dependency of a game repository. From a clone of the game, npx --allow-git=root github:snowu/spritewright --open runs it with nothing installed (npm 12 refuses GitHub packages unless you opt in). To pin it: add allow-git=root to .npmrc, npm i -D github:snowu/spritewright, then npx spritewright init writes a config (it picks the art folders and skips docs and screenshots) and npx spritewright --open serves the editor with save-to-disk. Add "art": "spritewright --open" to package.json so an artist just runs npm run art. It is one file plus a tiny Node server, no build step.
  • As a library. PixelForge.mount(element, options) embeds the editor in your own tool or page, with TypeScript types.

What it does: pencil, eraser, fill, line, rectangles, mirror drawing, "clean lines" mode, a palette panel (recolour a colour everywhere, load a Lospec .hex palette, snap an image to it), flip/rotate/shift/resize, a sprite-sheet animation preview, PNG import and export. Saves are lossless: it reads and writes PNG bytes itself, so even semi-transparent pixels (an alpha value used as a marker) come back unchanged. Its README lists the limits honestly, including that the pull request flow is tested against a mocked GitHub API.

Exercise: spec the PR flow

Before reading the code of the editor, write down in five bullets what should happen when an artist presses “Propose change”: which API calls, in which order (read the base branch ref, create blobs, create a tree, create a commit, create or update a branch ref, open the pull request), what the branch is called, what the PR body contains (before/after images), and what happens on a conflict. Then compare with the editor's implementation.
