Payments & money handling

Minor units, IBAN validation, fair splitting, and the payment status lifecycle.

Neonomics’ docs list payment types such as domestic, SEPA credit, scheduled variants, and batch transfers. After the user completes SCA the payment must be completed promptly because bank authorisations expire fast, and status is polled (or pushed) by payment id.

Money rules (memorise)

  1. Store integer minor units (cents/øre) + ISO 4217 currency. Never floats. Beware currencies with 0 or 3 decimals (JPY, KWD).
  2. Never add amounts of different currencies.
  3. Define a rounding rule (half-up? banker’s?) and use it everywhere.
  4. Use idempotency keys on every payment-creating request (see the Reliability track).
  5. Ledger entries are append-only; fix mistakes with reversing entries.

Payment status lifecycle

Berlin Group / ISO 20022-style statuses include RCVD (received), PDNG (pending), ACTC (technically accepted), ACCP (accepted for customer profile), ACSP (settlement in process), ACSC (settlement completed), ACCC (credit account completed), RJCT (rejected), CANC (cancelled). Banks report these late, duplicated, skipped, or out of order, and your system must still end in a correct state.

Challenge (Python): Merge payment status updates safely

Implement apply_status(current, incoming) returning the new status, with these simplified rules (ranks: RCVD 0, PDNG 1, ACTC 2, ACCP 3, ACSP 4, ACSC 5, ACCC 6):

  • If current is terminal (ACCC, RJCT, CANC) → unchanged.
  • RJCT is accepted unless current rank ≥ 5 (already settled).
  • CANC is accepted only if current rank ≤ 2.
  • Otherwise move forward only: accept incoming if its rank is higher (skipping is fine); ignore same or lower rank (stale or duplicate).
  • Unknown status → raise ValueError('unknown status').

Answer key

1. Floats and rounding in money code back ↑

B. 0.30000000000000004, 1998.9999999999998, 1999, 2 4

Binary floating point cannot represent most decimal fractions exactly, so 19.99 * 100 is 1998.9999999999998. And Python's round() uses banker's rounding (round half to even): round(2.5) is 2 and round(3.5) is 4, which silently shifts money by a cent. Use integer cents or Decimal with an explicit rounding mode.

2. IBAN validation (mod 97) back ↑

Hint: int(ch, 36) turns "0"-"9" and "A"-"Z" into 0–35, which is exactly the IBAN letter mapping. Join them into one string and take int(...) % 97. Use re.fullmatch with [0-9] (the \d class also matches non-ASCII digits).

Reference solution:

import re

LENGTHS = {'NO': 15, 'DE': 22, 'SE': 24, 'DK': 18, 'FI': 18, 'GB': 22}

def is_valid_iban(iban):
    if not isinstance(iban, str):
        return False
    s = iban.replace(' ', '').upper()
    if not re.fullmatch(r'[A-Z]{2}[0-9]{2}[A-Z0-9]{11,30}', s):
        return False
    if LENGTHS.get(s[:2], len(s)) != len(s):
        return False
    rearranged = s[4:] + s[:4]
    digits = ''.join(str(int(ch, 36)) for ch in rearranged)
    return int(digits) % 97 == 1

Validating the checksum proves the IBAN is well-formed, not that the account exists or belongs to the person. That is what an account-verification endpoint is for.

3. Split money without losing a cent back ↑

Hint: Use fractions.Fraction so the shares are exact: Fraction(total) * Fraction(w) / Fraction(sum). int() floors a non-negative Fraction. Then sort indexes by (-remainder, index) and add 1 to the first `leftover` of them.

Reference solution:

from fractions import Fraction

def split_amount(total_minor, weights):
    if not weights or any(w < 0 for w in weights) or sum(weights) <= 0:
        raise ValueError('invalid weights')
    ws = [Fraction(w) for w in weights]
    total_weight = sum(ws)
    exact = [Fraction(total_minor) * w / total_weight for w in ws]
    parts = [int(x) for x in exact]
    leftover = total_minor - sum(parts)
    order = sorted(range(len(parts)), key=lambda i: (-(exact[i] - parts[i]), i))
    for k in range(leftover):
        parts[order[k % len(parts)]] += 1
    return parts

Money is integer minor units plus a currency code. Keep the allocation rule in the spec (for example fees go to the platform) and always test the invariant “parts sum to the total”.

4. Merge payment status updates safely back ↑

Hint: A RANK dict and a TERMINAL set. Handle RJCT and CANC before the generic “higher rank wins” comparison.

Reference solution:

RANK = {'RCVD': 0, 'PDNG': 1, 'ACTC': 2, 'ACCP': 3, 'ACSP': 4, 'ACSC': 5, 'ACCC': 6}
TERMINAL = {'ACCC', 'RJCT', 'CANC'}

def apply_status(current, incoming):
    known = set(RANK) | {'RJCT', 'CANC'}
    if current not in known or incoming not in known:
        raise ValueError('unknown status')
    if current in TERMINAL:
        return current
    if incoming == 'RJCT':
        return current if RANK[current] >= 5 else 'RJCT'
    if incoming == 'CANC':
        return 'CANC' if RANK[current] <= 2 else current
    return incoming if RANK[incoming] > RANK[current] else current

The design principle: status handling must be idempotent and monotonic, so replays, retries and out-of-order webhooks converge to the same state. Store the raw bank statuses too, for audit and debugging.
