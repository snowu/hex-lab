C++ for games

The modern-C++ subset game programmers actually use, and the habits that keep it safe and fast.

Why C++ is still everywhere in games

Unreal, most console SDKs, physics libraries (Box2D, Jolt, PhysX), Godot itself and decades of engine code are C++. You will read it even if you write something else. The goal is to write the small, boring subset that gives control without foot-guns.

Habits that matter

  • Value semantics, contiguous data. Prefer std::vector<Particle> to a vector of pointers. Contiguous memory is what makes loops fast.
  • RAII: resources (memory, files, GPU buffers) are owned by objects whose destructors release them. Use std::unique_ptr for single ownership; avoid raw new/delete in game code. shared_ptr only when ownership is truly shared (and it is rarely).
  • No allocation in the frame loop. reserve() up front, reuse buffers, use pools or arenas.
  • Avoid virtual calls per entity per frame in hot loops: group by type (struct of arrays) or use a std::variant and std::visit. A virtual call is cheap, the cache miss it hides is not.
  • Use enum class and exhaustive switch (with -Wswitch) for state machines.
  • Prefer std::span, std::string_view for non-owning views; they carry a length and avoid copies.
  • const everything you can. Use [[nodiscard]] on functions whose result must be checked.

Foot-guns to know by name

  • Iterator invalidation: push_back or erase on a vector invalidates iterators, references and pointers into it. Erasing in a range-for is the classic crash (see the bug hunt in the performance lesson). Use the erase-remove idiom (std::erase_if in C++20) or swap-remove by index.
  • Dangling references: holding a pointer to an element and then growing the container.
  • Integer pitfalls: unsigned underflow (size() - 1 on an empty vector), signed overflow is undefined, integer division truncates toward zero (the drill on integer scaling).
  • Uninitialised members: always default-initialise (int hp = 0;).
  • Float comparison: compare with a tolerance, never ==.
  • Static initialisation order across translation units. Avoid global objects with constructors.

Tooling you should turn on

g++ -std=c++20 -Wall -Wextra -O1 -g -fsanitize=address,undefined main.cpp -o game
  • AddressSanitizer finds out-of-bounds and use-after-free; UBSan finds undefined behaviour such as signed overflow. The lab's validator compiles every C++ drill with them on.
  • A debugger (gdb, lldb, or the IDE) and a profiler (perf, Tracy). Learn to read a crash backtrace.
  • CMake is the lingua franca for building; for a first project a single CMakeLists.txt with SDL3 or raylib via FetchContent is enough.

Answer key

1. Spot the C++ lifetime bugs back ↑

Hint: Two bugs are the same root cause seen at two places (pointers into a growing vector), one is a plain leak.

  • Line 8: Returning a pointer into a vector that can grow: the next push_back may reallocate and move every element, leaving earlier pointers dangling. Return an index or handle instead.
  • Line 13: a was obtained before the second spawn, which may reallocate the vector. Writing through a afterwards is a use-after-free. This is the consequence of line 8.
  • Line 16: new Bullet is copied into the vector and the original is never deleted: a leak on every call. There is no reason to heap-allocate here (items_.push_back({0,0,0,0})).

2. Quick check back ↑

B. size() - 1 wraps to a huge number and the loop reads out of bounds (and i >= 0 is always true for unsigned)

Unsigned arithmetic wraps. Loop with signed indices, use reverse iterators, or check empty() first.

3. Quick check back ↑

B. A contiguous std::vector<Particle> of plain data updated in one loop

Contiguous plain data is cache friendly. Node-based containers and pointer-per-object designs mean a cache miss per element.

4. Check 1 back ↑

A. Erasing invalidates the iterators being looped over; mark the dead and remove them after the loop, or use erase-remove or swap-remove by index

Iterator invalidation makes in-loop erase undefined behaviour; separating marking from removal keeps iteration valid.

5. Check 2 back ↑

B. std::unique_ptr with RAII, avoiding raw new and delete in game code

Single ownership maps to unique_ptr: the destructor releases the resource on every path with no sharing overhead.
