State, hierarchies and stacks

From a switch statement to state objects, hierarchical machines and the pushdown automaton that remembers where you came from.

Where state machines come from

Behaviour that depends on what the character is currently doing is a state machine, whether you call it that or not. The first version is booleans (is_jumping, is_ducking), which breed impossible combinations ("jumping and ducking and dead"). The input, buffering and state machines lesson showed the enum-and-switch version. This lesson goes further.

Step 1: enum and switch

One variable holds the state; one match/switch handles it. Good up to a handful of states. The compiler can check you handled every state (an exhaustive switch). It starts to hurt when each state needs its own data (how long have I been stunned?) and the function grows to hundreds of lines.

Step 2: state objects (the State pattern)

Each state becomes its own object or node with enter(), exit() and update(dt). The actor holds a pointer to the current state and delegates to it. State-specific data lives inside the state, and adding a state is adding a file.

# GDScript: states as child nodes
class_name State extends Node
func enter(actor): pass
func exit(actor): pass
func update(actor, delta): pass            # return the next State, or null to stay

class_name Stunned extends State
var time_left := 0.6
func update(actor, delta):
    time_left -= delta
    return actor.get_node("States/Idle") if time_left <= 0.0 else null

Rules that keep it clean: transitions happen in one place (the machine, not scattered state = X assignments), exit of the old state always runs before enter of the new one, and a state that is re-entered starts fresh.

Step 3: hierarchical state machines (HFSM)

Many states share behaviour. "Walking", "running" and "idle" are all grounded: they all let you jump and they all fall off ledges the same way. Put the shared behaviour in a parent state (Grounded) and let children inherit it, so you write "if not on floor, go to Falling" once. A child handles an event first; if it ignores it, the parent gets it. This is how you stop the combinatorial explosion of "(every state) × (every shared reaction)".

Step 4: concurrent machines

A character has independent concerns: movement (idle, run, jump) and weapon (holstered, aiming, reloading). One machine for both needs 3 × 3 = 9 states and grows multiplicatively. Two separate machines that run side by side need 3 + 3, and only interact where they must (cannot sprint while reloading).

Step 5: the pushdown automaton

A plain machine has no memory: when "stunned" ends, how does it know to go back to "running" rather than "idle"? Keep a stack of states. push a new state on top (the old one pauses), pop to resume exactly what was underneath. This is how game flow works: main menu, in game, pause menu, options, confirm dialog. Each push/pop runs the lifecycle callbacks enter, pause, unpause, exit, which is where you stop music, freeze physics and release held keys. You build it in the drill.

Behaviour trees: when states get too many

For complex AI, hand-written transitions between 30 states become a web. Behaviour trees (AI track) make the decision logic a hierarchy that is re-evaluated each tick, and are often a better fit than a state machine for deciding what to do, while state machines remain good for managing what you are currently doing (animation, movement modes).

Drill: Pushdown automaton: a stack of states

A state stack remembers what you were doing: the pause menu goes on top of gameplay, a dialogue on top of that, and popping returns to exactly where you were. States are small integers here. Every change is written to an event log so you can see which lifecycle callbacks would run.

  • push(s): if there is a current top, log pause for it. Then log enter for s and put it on top. Returns false (and logs nothing) if the stack already holds 8 states.
  • pop(): log exit for the top and remove it; if a state is now on top, log unpause for it. false if empty.
  • replace(s): log exit for the top, then enter for s, at the same depth (no pause or unpause). false if empty.
  • top() is the current state; events() is the log so far.

Starter (Zig):

const std = @import("std");

pub const Kind = enum { enter, exit, pause, unpause };
pub const Event = struct { kind: Kind, state: u8 };

pub const StateStack = struct {
    stack: [8]u8 = undefined,
    depth: usize = 0,
    log: [64]Event = undefined,
    log_len: usize = 0,

    fn record(self: *StateStack, kind: Kind, state: u8) void {
        self.log[self.log_len] = .{ .kind = kind, .state = state };
        self.log_len += 1;
    }

    pub fn top(self: *const StateStack) ?u8 {
        if (self.depth == 0) return null;
        return self.stack[self.depth - 1];
    }

    pub fn events(self: *const StateStack) []const Event {
        return self.log[0..self.log_len];
    }

    pub fn push(self: *StateStack, s: u8) bool {
        _ = self;
        _ = s;
        return false;
    }

    pub fn pop(self: *StateStack) bool {
        _ = self;
        return false;
    }

    pub fn replace(self: *StateStack, s: u8) bool {
        _ = self;
        _ = s;
        return false;
    }
};

Answer key

1. Pushdown automaton: a stack of states back ↑

Hint: Write a tiny record(kind, state) helper that appends to the log, and implement push/pop/replace as sequences of record calls plus the stack change. Mind the order: pause the old top BEFORE entering the new one, and unpause the new top AFTER exiting the old one.

A plain state machine has no memory ("go back to what I was doing" needs every state to know its predecessor). The pushdown automaton fixes that with a stack and is how most game flow works: main menu → game → pause → options. The lifecycle events (enter/exit/pause/unpause) are the important part: they are where you stop music, freeze the simulation, release held input. Hierarchical state machines are the other extension: states that share behaviour inherit it from a parent state.
