Component, subclass sandbox and service locator

Compose entities from parts, give subclasses a safe toolbox, and reach shared services without global state.

Component: composition over inheritance

The earlier entities lesson introduced the idea; here is the pattern in detail. Instead of one huge GameObject class that handles input, physics, rendering and AI (a "god object"), split it into components, each owning one concern: Health, Mover, SpriteRenderer, PlayerInput. An entity is a container of components. Reuse comes from combining: a crate is Sprite + Collider + Health; an enemy adds AIBrain; a trap is Collider + DamageOnTouch, with no inheritance tree.

The design question is how components talk:

  • Direct reference: AIBrain asks its entity for the Mover component and calls it. Simple; creates coupling between those two component types.
  • Messages/signals: Health emits died, others react (observer lesson). Loosest coupling, hardest to follow.
  • Shared data: components read and write a shared state object (a blackboard). Good when many systems need the same facts (position, target).

A common mistake is a component that needs half the other components to function: that is one component pretending to be several.

Subclass sandbox

Sometimes inheritance is the right tool, if used carefully. In the subclass sandbox pattern a base class provides a protected toolbox of operations (play_sound(), spawn_particles(), move_toward()), and subclasses implement one virtual method (activate()) using only those operations. Superpowers are written as subclasses without ever touching the audio or particle systems directly.

# GDScript: Godot's own Node virtuals (_ready, _process) are this pattern
class_name Power extends Node
func activate(hero): pass                     # subclasses override
func _play(sound): Audio.play(sound)          # the toolbox
func _burst(pos): Particles.burst(pos)

class_name Fireball extends Power
func activate(hero):
    _play("whoosh"); _burst(hero.position)

Benefits: the coupling between 100 powers and the engine is concentrated in the base class, so refactoring the engine changes one file. Costs: the base class tends to grow into a kitchen sink, and deep hierarchies are fragile ("fragile base class"). Keep the hierarchy one level deep, and prefer data (type objects) when subclasses differ only in numbers.

Service locator, dependency injection and autoloads

Code needs shared services (audio, save system, input, random). How does it get them?

  1. Global singleton: Audio.play() from anywhere. Easy, and a trap (next lesson).
  2. Service locator: a small registry that holds the current implementations: Services.audio().play(...). Callers depend on the interface, not a concrete class, and you can swap implementations: a null service that does nothing (tests, headless servers), a logging decorator that wraps the real one for debugging.
  3. Dependency injection: pass what you need into the constructor or setup(). Explicit and easy to test; some plumbing.
const std = @import("std");

/// The interface callers depend on: a pointer to some implementation plus a function.
const Audio = struct {
    ctx: *anyopaque,
    playFn: *const fn (ctx: *anyopaque, id: u32) void,

    fn play(self: Audio, id: u32) void {
        self.playFn(self.ctx, id);
    }
};

/// A real implementation would talk to the sound card; this one counts calls.
const CountingAudio = struct {
    plays: u32 = 0,

    fn playImpl(ctx: *anyopaque, id: u32) void {
        _ = id;
        const self: *CountingAudio = @ptrCast(@alignCast(ctx));
        self.plays += 1;
    }

    fn audio(self: *CountingAudio) Audio {
        return .{ .ctx = self, .playFn = playImpl };
    }
};

/// The null service: does nothing, so callers never check for "no audio".
fn nullPlay(ctx: *anyopaque, id: u32) void {
    _ = ctx;
    _ = id;
}

var null_ctx: u8 = 0; // lives for the whole program, so the null service never holds a dangling pointer

const Locator = struct {
    audio: Audio,

    fn provideNull() Locator {
        return .{ .audio = .{ .ctx = &null_ctx, .playFn = nullPlay } };
    }
};

test "callers use the interface, tests plug in a counter" {
    var counting = CountingAudio{};
    const services = Locator{ .audio = counting.audio() };
    services.audio.play(1);
    services.audio.play(2);
    try std.testing.expectEqual(@as(u32, 2), counting.plays);
    const silent = Locator.provideNull();
    silent.audio.play(3); // no crash, no sound
}

Locators hide dependencies (you cannot see from a function's signature that it needs audio) and must be set up before use. Prefer injection for core logic and a locator for cross-cutting services. In Godot an autoload is a global singleton node: fine for a few thin services (audio bus, settings), a liability for game state.

Answer key

1. Quick check back ↑

B. Health emits a died signal/event and the others subscribe

The component announces what happened and does not know who listens, so it stays reusable (the same Health on a crate with no UI).

2. Quick check back ↑

B. Callers never need to check whether the service exists, and tests or headless builds run with silent, harmless implementations

A null object removes "if audio is not None" branches everywhere and makes automated tests possible without a sound device.

3. Quick check back ↑

B. A type object for the shared stats, and a small number of attack behaviours (components, scripts or a subclass sandbox) chosen by the type

Data for what is data, code only for what really differs: that keeps the number of classes to the number of behaviours, not the number of stat sheets.

4. Check 1 back ↑

B. It is one component pretending to be several and should be merged or split differently, since a component needing half the entity signals a missing concept

Components should own one concern. A part that drags in half the entity is a hidden god object.

5. Check 2 back ↑

D. Injection makes core logic explicit and testable, while a locator suits cross-cutting services; locators hide dependencies and need setup before use, so a thin Godot autoload is fine only for services, never game state

Passing dependencies shows what code needs; a locator with an interface and a null service keeps cross-cutting needs swappable.
