Entities, components and scenes

Inheritance versus composition, Godot’s node tree, and the data-oriented ECS idea behind sparse sets.

The inheritance trap

The first instinct is a class hierarchy: Enemy → FlyingEnemy → ShootingFlyingEnemy. It breaks the day you want a walking enemy that shoots, a flying one that does not, and a boss that is both. You end up with diamond inheritance or copy-paste. The standard fix is composition: build things out of small parts that each do one job (Health, Mover, Shooter, Collider).

Three ways to compose

  1. Scene tree (Godot, Unity prefabs): an object is a tree of nodes. A goblin is a CharacterBody2D with children for the sprite, collision shape, hurtbox and a script. Reuse comes from saving that tree as a scene and instancing it. Communication: call down, signal up. A parent may call methods on its children, but children emit signals and never reach for their parents.
  2. Component objects: an entity is a bag of component objects with behaviour. Easy to read, but each component carries its own update and memory layout is scattered.
  3. ECS (entity-component-system): entities are just ids, components are plain data, and systems are functions that run over all entities with a given set of components. Behaviour lives in systems, data in packed arrays.

Why ECS is fast: data-oriented design

CPUs are fast at walking arrays in order and slow at chasing pointers. A movement system that needs Position and Velocity for 50,000 entities should read two tight arrays, not 50,000 scattered objects. The data structure underneath is usually a sparse set: a dense array of the component values (cheap to iterate) plus a sparse array mapping entity id to its dense slot (cheap lookup). Removal uses swap-remove to keep the dense array gap-free. Build one in the drill.

When is ECS worth it? When you have thousands of similar things (bullets, particles, units, tiles) or need to serialise and rewind the world. For a platformer with fifty entities, Godot's node tree is simpler and fast enough. Pick the tool for the scale you actually have.

Drill: Sparse set: the heart of a fast ECS

Entity-component systems store each component type in a sparse set: O(1) add, remove, lookup, and a densely packed array you can iterate without gaps. Implement one with a fixed capacity (ids are 0 .. capacity-1).

  • sparse[id] is the index of that id in the dense arrays. dense[i] is the id stored at index i, and values[i] its value. Only the first count dense slots are live.
  • add(id, value): returns false if the id is out of range or already present, else stores it at the end.
  • has(id) and get(id) (optional/null when absent). Careful: a stale sparse entry from a removed id must not fool has. Check that sparse[id] < count and dense[sparse[id]] == id.
  • remove(id): swap-remove. Move the last live element into the hole so the array stays packed. Returns whether something was removed.
  • ids() returns the live ids in dense order.

Starter (Zig):

const std = @import("std");

pub fn SparseSet(comptime T: type, comptime capacity: usize) type {
    return struct {
        const Self = @This();

        sparse: [capacity]u32 = @splat(0), // id -> index into dense
        dense: [capacity]u32 = @splat(0), // index -> id
        values: [capacity]T = undefined, // index -> value
        count: usize = 0,

        pub fn has(self: *const Self, id: u32) bool {
            _ = self;
            _ = id;
            return false;
        }

        /// false if id is out of range or already present
        pub fn add(self: *Self, id: u32, value: T) bool {
            _ = self;
            _ = id;
            _ = value;
            return false;
        }

        pub fn get(self: *const Self, id: u32) ?T {
            _ = self;
            _ = id;
            return null;
        }

        /// swap-remove: keep the dense arrays packed
        pub fn remove(self: *Self, id: u32) bool {
            _ = self;
            _ = id;
            return false;
        }

        pub fn ids(self: *const Self) []const u32 {
            return self.dense[0..self.count];
        }
    };
}

Design question: “How would you structure bullets in a bullet-hell with 20,000 on screen?”

  • No node per bullet. Store positions and velocities in flat arrays (struct of arrays) and update them in one tight loop.
  • Render them with one batched draw call (a MultiMesh or a single custom draw) instead of 20,000 sprites.
  • Use a pool/free-list to recycle slots (see the performance lesson), no allocation in the hot path.
  • Collision against the player only: test bullets against a handful of player hitboxes, using a spatial hash if there are many targets.
  • Cull off-screen bullets as you iterate and recycle them.

Answer key

1. Sparse set: the heart of a fast ECS back ↑

Hint: remove: let i = sparse[id], last = count - 1. dense[i] = dense[last], values[i] = values[last], sparse[dense[i]] = i, count -= 1. That also works when i == last.

Bevy, flecs and EnTT build on this idea (Bevy also has archetype tables). Iterating a dense array is cache friendly, and swap-remove is why entity order is never stable. In Zig this is a comptime-generic function that returns a type, which is how its standard containers (ArrayList, HashMap) are built too.

2. Quick check back ↑

B. It keeps removal O(1) and the dense array gap-free, at the cost of not preserving order

Swap-remove is O(1) and leaves no holes to skip while iterating. The price is that iteration order changes, so never rely on it.

3. Quick check back ↑

B. Health emits a signal like health_changed(value) and the UI connects to it

“Call down, signal up”: the Health node should not know the UI exists. A signal keeps both reusable (you can put the same Health on an enemy with no UI).

4. Check 1 back ↑

B. Compose enemies from small parts (Mover, Shooter, Health, Collider) instead of extending the hierarchy

Composition replaces the brittle hierarchy with combinable parts, so new mixes need no new branches.

5. Check 2 back ↑

C. Have Health emit a signal such as health_changed and let the UI connect to it

Call down, signal up: children announce events with signals and never reach for their parents, keeping both reusable.
