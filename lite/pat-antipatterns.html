Singletons, globals and other traps

Why the easy pattern hurts, what to do instead, and the other design smells that kill game codebases.

The singleton trap

A singleton is a class with exactly one instance, reachable from anywhere (Game.instance, an autoload called GameState). It is the most overused pattern in games because it solves "how do I reach X from here?" in one line. The costs show up later:

  • Hidden dependencies. A function's signature no longer says what it touches; any code can read or change the singleton. Reading a function does not tell you what it depends on.
  • Global mutable state. Anything can write to it at any time, so bugs appear far from their cause, and execution order starts to matter.
  • Testing. You cannot test a function without setting up the whole global world, and tests leak state into each other.
  • "Only one" is rarely true. Split screen means two players. Level editors preview a level inside a level. A replay viewer runs a second simulation. The day "there is only one" stops being true, every call site must change.
  • Lifetime and initialisation order. Which singleton starts first? Who tears down last? Static initialisation order across files is a classic C++ bug.

Alternatives

  1. Pass it in. If a function needs the world, take the world as a parameter. Verbose for a week; clear forever.
  2. Keep it in the owner. Most "singletons" are really "the current level's X". Let the level own it and hand references down the tree (Godot: call down, signal up).
  3. Service locator for genuinely cross-cutting services (audio, settings, analytics), with an interface so tests can swap them (component lesson).
  4. Scene-local instead of global: an autoload with a small, stable job (an audio bus, a settings store) is fine. An autoload holding the player, the score, the inventory and the current level is a global state blob.

Other smells

  • God object / "Manager" classes. GameManager that handles input, spawning, score, UI and save. Split by responsibility; a class name ending in Manager is often a missing concept.
  • Inheritance towers. Entity → Character → Enemy → FlyingEnemy → ShootingFlyingEnemy. Prefer composition and type objects.
  • Premature generalisation. A plugin system for the one weapon you have. Build the concrete thing twice, then abstract.
  • Stringly typed everything. Passing "enemy_goblin" around and comparing strings in hot paths. Use enums or interned ids, keep strings at the data boundary.
  • Update order spaghetti. Systems that depend on being updated in a specific order with no comment saying so. Make the order explicit in one place.
  • Deep coupling through signals. Event chains where each handler emits the next: nobody can say what happens when you press jump.
  • Copy-paste scenes. Fifty slightly different enemy scenes instead of one scene and fifty data files.

A refactoring recipe

  1. Find the singleton's callers and group by what they use.
  2. Split the singleton by responsibility into small things that each have one reason to change.
  3. Give each piece an owner (the level, the player) and pass references down where needed.
  4. For what remains global, define a small interface and a way to swap it.
  5. Delete the global. If something breaks, you found a hidden dependency.

Refactoring exercise: break up a GameManager

A GameManager has these responsibilities: reads input, spawns enemies, tracks score, shows the HUD, saves and loads, plays music, handles pause.

  • Group them into 4 to 6 cohesive pieces. (Input → controllers; spawning → a Spawner owned by the level; score → a ScoreKeeper that listens to events; HUD → UI node that listens; save/load → a SaveService behind an interface; audio → Audio service; pause → a state in a pushdown stack.)
  • Which of these needs to be global at all? (Probably only audio and settings.)
  • Draw who owns whom and which direction messages flow.
  • Pick one responsibility and write the test you could not write before.

Answer key

Hint: All three are the same disease: reaching into global state instead of being given what you need.

  • Line 8: Writing Game.score directly from the coin couples the coin to the global state, and anything can change score from anywhere. The coin should emit collected and the scoring code react (observer).
  • Line 9: The coin also reaches through the global into the player's internals and edits hp. The player should expose heal(), or the coin should emit and a Health component react. With two players (split screen) this also heals the wrong one.
  • Line 14: target = Game.player assumes exactly one player that already exists when the enemy is ready (initialisation order) and is the same forever (respawn replaces it). Inject the target when the enemy is spawned.
