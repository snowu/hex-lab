Raycasts, shape casts and spatial queries

Asking the world questions: what is in front of me, can I see it, what is inside this area, did the bullet hit.

Queries are different from simulation

Simulation moves bodies and resolves contacts. A query asks a question about the current state without changing it: is there a wall between the guard and the player? what is under the mouse? what is inside this explosion? can I step forward without falling? Game code makes far more queries than people expect: AI line of sight, hitscan weapons, ground checks, interaction prompts, camera collision, placement previews.

Rays

A ray is an origin plus a direction. The result you almost always want is the closest hit: the distance along the ray (t), the point (origin + dir * t), the surface normal (for decals and bounce) and which object was hit. Always give a maximum distance and a layer mask so the query ignores things it should not see (your own body, triggers, other team).

Ray against a box: the slab method

An axis-aligned box is the intersection of two "slabs" (the space between two parallel lines on each axis). Find where the ray enters and leaves each slab; the ray hits the box if the latest entry is before the earliest exit.

const std = @import("std");

const Box = struct { x: f32, y: f32, w: f32, h: f32 };

/// Distance along the ray where it first enters the box, or null. The direction does not have to be normalised (t is in units of the direction).
fn rayBox(ox: f32, oy: f32, dx: f32, dy: f32, b: Box) ?f32 {
    var t_min: f32 = 0; // ignore hits behind the origin
    var t_max: f32 = std.math.inf(f32);
    const axes = [2][4]f32{ .{ ox, dx, b.x, b.x + b.w }, .{ oy, dy, b.y, b.y + b.h } };
    for (axes) |a| {
        const o = a[0];
        const d = a[1];
        if (d == 0) {
            if (o < a[2] or o > a[3]) return null; // parallel to the slab and outside it
        } else {
            var t1 = (a[2] - o) / d;
            var t2 = (a[3] - o) / d;
            if (t1 > t2) std.mem.swap(f32, &t1, &t2);
            t_min = @max(t_min, t1);
            t_max = @min(t_max, t2);
            if (t_min > t_max) return null;
        }
    }
    return t_min;
}

test "ray against a box" {
    const box = Box{ .x = 4, .y = 2, .w = 2, .h = 2 };
    try std.testing.expectEqual(@as(?f32, 4), rayBox(0, 3, 1, 0, box)); // straight in from the left
    try std.testing.expectEqual(@as(?f32, null), rayBox(0, 0, 1, 0, box)); // passes below
    try std.testing.expectEqual(@as(?f32, null), rayBox(10, 3, 1, 0, box)); // box is behind the origin
    try std.testing.expectEqual(@as(?f32, 0), rayBox(5, 3, 1, 0, box)); // starting inside
    try std.testing.expectApproxEqAbs(@as(f32, 2), rayBox(0, 0, 2, 1, box).?, 1e-5); // diagonal: enters the left edge at (4, 2)
}

Rays on a grid: DDA

On a tile map, step from cell border to cell border instead of testing shapes (the next drill and simulation). It visits exactly the cells the ray crosses: ideal for line of sight in tile games, shadow casting, and Wolfenstein-style rendering.

Shape casts

A ray is infinitely thin: it slips through a gap smaller than a character. For things with width (a thrown axe, a character about to walk) sweep the shape along the movement and find the first impact (time of impact). Engines implement it by inflating the obstacle by the shape's size (Minkowski sum) and raycasting against that. Use it for character movement, thick projectiles and camera collision.

Layers and masks

Every query takes a mask of layers to consider. Set a sensible default and name your layers (walls, enemies, player, projectiles, triggers, pickups). Most "my raycast hits itself" and "my bullet hits the pickup" bugs are mask bugs. Starting a ray inside the shooter's own collider is the classic: exclude the shooter or start just past its edge.

Performance

  • Queries use the broadphase (a grid or tree), so cost is roughly logarithmic in the number of objects, but not free: hundreds per frame is fine, thousands needs care.
  • Share and cache: if ten enemies ask "can I see the player" each frame, stagger checks across frames (enemy i checks on frame i mod 5).
  • Prefer cheap first: a distance check before a raycast; a field-of-view dot product before line of sight.

Hitscan, projectiles and fairness

A hitscan weapon is one raycast in the frame you shoot: instant, cheap, exact. Projectiles are bodies that move and collide over several frames (travel time, drop, dodgeable). Online, hitscan needs lag compensation (networking track). Choose by the gameplay you want, not by cost.

Drill: Raycast on a grid (DDA)

Hitscan weapons, line of sight and "what is under the cursor" all need a raycast. On a tile grid the fast, exact method is the DDA (digital differential analyzer, Amanatides and Woo): instead of sampling along the ray, jump from one cell border to the next.

The grid is a list of rows; a cell is 1×1; '#' is a wall; the position (ox, oy) is in cell units (so (0.5, 0.5) is the middle of the top-left cell, x grows right, y grows down). (dx, dy) is the direction (any length except zero). Return the first wall cell the ray enters and the distance along the ray at which it enters it, or nothing if the ray leaves the grid or travels more than max_dist without hitting one. If the origin is already inside a wall, that is a hit at distance 0. An origin outside the grid has no hit.

Starter (Zig):

const std = @import("std");

pub const Hit = struct { col: usize, row: usize, dist: f64 };

/// grid rows of '.' and '#', cells are 1x1, y grows down. Returns the first wall cell entered by the ray.
pub fn raycast(grid: []const []const u8, ox: f64, oy: f64, dx: f64, dy: f64, max_dist: f64) ?Hit {
    _ = grid;
    _ = ox;
    _ = oy;
    _ = dx;
    _ = dy;
    _ = max_dist;
    return null;
}

Answer key

1. Raycast on a grid (DDA) back ↑

Hint: Normalise the direction. cell = floor(origin). For each axis keep tMax = distance along the ray to the next border on that axis, and tDelta = distance between borders (1/|d|, or infinity when d is 0). Loop: step on the axis with the smaller tMax (the distance you report is that tMax BEFORE you add tDelta), check bounds, check the new cell. Beware exact corner crossings in your own tests: both axes tie.

The DDA visits exactly the cells the ray passes through, so the cost is proportional to the distance, not to the number of samples. The same loop draws lines on a grid, does shadow casting, and (with a height per cell) renders the classic Wolfenstein-style 3D view. In 3D engines the equivalent is a ray through a BVH or the physics broadphase. For rays against shapes (circles, boxes) use analytic tests instead, and for a thick "projectile" use a shape cast, as in the collision lesson.

2. Quick check back ↑

B. Exclude the guard's own collider (or its layer) from the query, or start the ray outside its shape

A ray that starts inside a shape immediately hits it. Exclusions and masks are part of every query.

3. Quick check back ↑

B. A shape cast (a small box or circle the width of the character's feet) instead of a single ray

A ray has zero width and can slip through seams; a swept shape covers the character's footprint.

4. Quick check back ↑

B. Check a cheap distance and field-of-view test first, and stagger the raycasts across frames

Cull with cheap tests and spread the expensive ones. Reaction time of a few frames is invisible for AI.

5. Check 1 back ↑

A. When the latest slab entry is before the earliest slab exit, with hits behind the origin ignored

The box is the intersection of its slabs. Overlapping entry-exit intervals mean the ray passes through all of them.

6. Check 2 back ↑

B. The gameplay you want: instant exact shots versus travel time, drop and dodgeability, plus online lag compensation for hitscan

Both are cheap enough. Fairness, feel and networking decide, not performance alone.
