Procedural generation

Seeds, deterministic randomness, noise, cellular automata caves and the validation step everyone forgets.

Seeds and determinism

Procedural content is a function of a seed: same seed, same world. That gives you shareable seeds, daily challenges, replays, and bugs you can reproduce. It only works if your random numbers are yours: a generator with explicit state that you create from the seed, not a global one that any system can advance. If a particle effect calls random() in the middle of level generation, every level after it changes. Keep one stream per concern (layout, loot, cosmetics). Implement a small LCG in the first drill to see exactly what state means.

Common techniques

  • Random walk / drunkard's walk: a digger wanders and carves floor. Cheap, organic caves and corridors.
  • Cellular automata: random noise, then repeatedly apply a neighbour-counting rule. Creates cave-like blobs (second drill and the simulation).
  • Room and corridor / BSP: split space into rooms recursively and connect them. Classic dungeons.
  • Noise (Perlin, simplex, value noise): smooth randomness for terrain heights, biomes, clouds. Layer several scales (octaves) for detail.
  • Wave Function Collapse: choose tiles so every neighbour pair is compatible, propagate constraints, collapse the lowest-entropy cell. Great for consistent local style.
  • Grammars and templates: assemble hand-made chunks (Spelunky's level chunks) so quality stays high.

The part that makes it playable

Randomness makes content; design makes it fair. Always add a validation and repair step:

  • Is the start connected to the exit? (Flood-fill. The simulation highlights disconnected pockets in amber.)
  • Are there enough resources, and not too many enemies at the spawn?
  • Reject-and-retry with the next seed, or repair by carving a tunnel.
  • Constrain the randomness. Pure noise is boring; authored rules plus randomness is what produces memorable levels.

Drill: A seeded random number generator

Procedural levels, replays and "daily seeds" need a deterministic RNG you control. Implement a linear congruential generator. The state update is state = (1103515245 * state + 12345) mod 2^31, starting from seed mod 2^31.

  • next_int(n): update the state once, return (state >> 16) % n. The low bits of an LCG are weak, so use the high ones.
  • next_float(): update the state once, return state / 2^31 as a double.

Starter (Zig):

const std = @import("std");

pub const Rng = struct {
    state: u64,

    pub fn init(seed: u64) Rng {
        _ = seed;
        return .{ .state = 0 };
    }

    pub fn nextInt(self: *Rng, n: u32) u32 {
        _ = self;
        _ = n;
        return 0;
    }

    pub fn nextFloat(self: *Rng) f64 {
        _ = self;
        return 0;
    }
};

Simulation: Cellular automata caves

Random noise is smoothed with the rule “become a wall if 5 or more of the 8 neighbours are walls”. Press smooth a few times.

Try this in the full app:

  • Start with ~45% walls and press smooth 4 to 5 times: caves emerge from static.
  • Raise the fill to 55%: more solid, more disconnected pockets (amber).
  • Lower it to 35%: huge open areas, almost no structure.
  • Press keep largest cave to apply the usual repair: delete everything unreachable.
  • Press new seed and compare; same parameters, different map.

Drill: Cave generation: one smoothing step

Cellular-automata caves start from random noise and repeatedly apply one rule. Write smooth: the map is a grid of '#' (wall) and '.' (floor). A cell of the next generation is a wall if 5 or more of its 8 neighbours are walls, otherwise floor. Cells outside the map count as walls. Read only from the old generation. Try the same rule in the cave simulation above.

Zig: the map is a flat w * h byte slice, write the result into dst. C++: rows as strings, return the new grid.

Starter (Zig):

const std = @import("std");

/// src and dst are w*h bytes, row-major. '#' wall, '.' floor.
pub fn smooth(src: []const u8, w: usize, h: usize, dst: []u8) void {
    _ = w;
    _ = h;
    @memcpy(dst, src);
}

Answer key

1. A seeded random number generator back ↑

Hint: Use 64-bit integers: 1103515245 * (2^31 - 1) is about 2.4e18, which fits in u64 / uint64_t without overflow, so you can take the modulo afterwards.

Never use a global random for gameplay: you cannot replay it, and any extra call (a particle spawn!) shifts every later result. Keep separate streams per concern (loot, level generation, cosmetic effects). Godot has RandomNumberGenerator with a seed; PCG and xoshiro are far better generators than this LCG, which is for teaching. Zig ships std.Random.DefaultPrng (xoshiro) and C++ has .

2. Cave generation: one smoothing step back ↑

Hint: For every cell loop dr, dc over -1..1 except (0,0). A neighbour outside the grid counts as a wall. Compare the count with 5. Never write into the grid you are reading from. Note a 2x2 map: every cell has 5 outside neighbours, so all four become walls.

Typical recipe: fill about 45% walls, run 4 or 5 smoothing steps, then flood-fill to find the caves and either keep the biggest or tunnel between them. Other generators: random-walk "drunkard" digging, BSP rooms, Wave Function Collapse for tile consistency.

B. The effect advances the shared random stream, shifting every later number used by generation

Use separate RNG instances per system so cosmetic randomness cannot disturb gameplay randomness.

The rule makes caves, not guarantees. Validate reachability and difficulty.
