Object pool, flyweight and data locality

Three optimisation patterns that all come from the same fact: memory access, not arithmetic, is the bottleneck.

Why memory layout matters

A modern CPU can do a few billion operations a second, but fetching a value from main memory takes the time of hundreds of operations. To hide that, it loads memory in cache lines (typically 64 bytes) and keeps recent ones in fast caches. Code that walks memory in order is fast; code that jumps around (following pointers to scattered objects) pays the full delay on every step. Many game optimisations are about keeping the data the loop needs together.

Data locality: array of structs vs struct of arrays

Suppose each particle has position, velocity, colour, lifetime and a few flags (64 bytes) and the update loop only needs position and velocity (16 bytes). With an array of structs (AoS) each cache line contains a quarter of one useful particle's data and the rest is dead weight. With a struct of arrays (SoA) the positions are contiguous and the loop reads only what it needs. ECS (see the architecture lessons) is this idea applied to the whole game.

const std = @import("std");

// AoS: one record per particle. Convenient, but the update drags colour and flags through the cache.
const ParticleAos = struct { x: f32, y: f32, vx: f32, vy: f32, r: u8, g: u8, b: u8, alive: bool, life: f32 };

// SoA: one array per field. The movement loop touches only x, y, vx, vy.
const Particles = struct {
    x: [256]f32 = undefined,
    y: [256]f32 = undefined,
    vx: [256]f32 = undefined,
    vy: [256]f32 = undefined,
    count: usize = 0,

    fn update(self: *Particles, dt: f32) void {
        for (0..self.count) |i| {
            self.x[i] += self.vx[i] * dt;
            self.y[i] += self.vy[i] * dt;
        }
    }
};

test "the SoA update touches contiguous arrays" {
    var p = Particles{};
    p.count = 2;
    p.x[0] = 0;
    p.y[0] = 0;
    p.vx[0] = 10;
    p.vy[0] = -4;
    p.x[1] = 5;
    p.y[1] = 5;
    p.vx[1] = 0;
    p.vy[1] = 0;
    p.update(0.5);
    try std.testing.expectEqual(@as(f32, 5), p.x[0]);
    try std.testing.expectEqual(@as(f32, -2), p.y[0]);
    try std.testing.expectEqual(@as(f32, 5), p.x[1]);
    _ = ParticleAos;
}

Rules of thumb: measure first. SoA wins when loops touch few fields of many objects; AoS wins when you usually touch all the fields of one object (a single character). Hot/cold splitting (keep rarely used data in a separate structure) is a middle path.

Object pool

Creating and destroying objects constantly (bullets, particles, enemies) costs allocator time, fragments memory and, in garbage-collected languages, causes pauses. A pool allocates all instances up front, hands them out and takes them back. A free list threaded through the unused slots makes both operations O(1) (you build it in the drill). Decisions to make explicitly:

  • Exhausted: refuse the request (a skipped bullet is nearly always better than a hitch), recycle the oldest, or grow in chunks.
  • Reset: a recycled object must be fully re-initialised, or it keeps old state ("zombie bullet with the last owner's damage"). Have one reset function and call it on acquire.
  • Stale references: if something still holds a pointer to a recycled object, it now points at a different bullet. Hand out handles (index plus a generation counter incremented on release) instead of raw pointers; a stale handle is detected because its generation no longer matches.

In Godot, pools matter mostly for scenes that are expensive to instantiate; for plain data, arrays of structs (SoA) are the more effective way.

Flyweight

If 10,000 trees each store their own copy of the mesh, the texture and the species stats, memory explodes. A flyweight splits an object into shared, immutable data (the tree type: one copy) and per-instance data (position, age: tiny). Every instance holds a reference or index to the shared part. Tile maps are the everyday example: the map stores a small integer per cell, and the integer indexes a table of tile definitions (texture, solidity, cost). The related type object pattern is the next lesson.

Drill: Object pool with an O(1) free list

An object pool allocates all objects up front and hands them out and takes them back. A naive pool scans for a free slot (O(n)). A free list threads the unused slots together so both operations are O(1): free_head is the first free slot and next_free[i] is the slot after i in the list. init is given and links every slot (0 → 1 → 2 → ... → capacity, where capacity means "end of list").

  • acquire(): take the head of the free list, mark it in use, return its index. Nothing if the pool is exhausted.
  • release(index): put the slot at the front of the free list (so the most recently released slot is reused first). Returns false for an out-of-range index or a slot that is already free (a double release must not corrupt the list).
  • freeCount() / get(index) as in the starter.

Starter (Zig):

const std = @import("std");

pub fn Pool(comptime T: type, comptime capacity: usize) type {
    return struct {
        const Self = @This();

        items: [capacity]T = undefined,
        next_free: [capacity]usize = undefined, // the free list is threaded through the unused slots
        in_use: [capacity]bool = @splat(false),
        free_head: usize = 0, // first free slot; capacity means "none"
        free_count: usize = capacity,

        pub fn init() Self {
            var s = Self{};
            for (0..capacity) |i| s.next_free[i] = i + 1;
            return s;
        }

        pub fn freeCount(self: *const Self) usize {
            return self.free_count;
        }

        pub fn get(self: *Self, index: usize) *T {
            return &self.items[index];
        }

        /// the index of a free slot, or null if the pool is exhausted
        pub fn acquire(self: *Self) ?usize {
            _ = self;
            return null;
        }

        /// false for an out-of-range index or a slot that is already free
        pub fn release(self: *Self, index: usize) bool {
            _ = self;
            _ = index;
            return false;
        }
    };
}

Answer key

1. Object pool with an O(1) free list back ↑

Hint: acquire: if free_head == capacity return null; i = free_head; free_head = next_free[i]; in_use[i] = true; free_count -= 1. release: reject invalid or already-free slots; in_use[index] = false; next_free[index] = free_head; free_head = index; free_count += 1.

Pools avoid allocator cost, fragmentation and garbage-collector pauses for things that spawn and die constantly (bullets, particles, enemies). The free list is the same trick malloc implementations use. Design decisions to state out loud: what happens when the pool is empty (drop the request, recycle the oldest, grow in chunks), and how stale handles are detected. Index + generation counters ("handles") catch the use-after-release bug: a bullet that was recycled must not be hit by an old reference.

2. Quick check back ↑

B. Store positions and velocities in their own contiguous arrays (struct of arrays) so the loop reads only what it needs

The cost is cache misses from moving unneeded bytes. Contiguous hot data fixes it.

3. Quick check back ↑

B. Handles that carry a generation counter, so a stale handle no longer matches

Index + generation: when a slot is recycled its generation changes, and any old handle fails validation instead of silently pointing at the new object.

4. Spot the object pool bugs (C++) back ↑

Hint: One is incomplete reset, two are about the vector growing.

  • Line 6: A recycled bullet only gets x and y reset: vx, vy and damage keep the previous bullet's values. Re-initialise the whole object (a reset() or assigning a fresh Bullet{}).
  • Line 11: The pool is supposed to be fixed-size, but when full it quietly grows with push_back, defeating the purpose and (on a vector) reallocating, which invalidates every pointer handed out earlier. Return nothing when exhausted.
  • Line 12: Returning a pointer to the vector's back element: any later growth moves all elements, leaving earlier pointers dangling. Use stable storage (fixed array) or hand out indices/handles.

5. Check 1 back ↑

B. Have one reset function that fully re-initialises the object and call it on every acquire from the pool

Pooled objects must be completely re-initialised on acquire. Partial resets leak the last user into the next one.

6. Check 2 back ↑

A. Split each tree into shared immutable data (the tree type, one copy) plus tiny per-instance data (position, age) referencing it, like a tile map storing small ids into a table

The flyweight pattern shares one copy of the heavy definition across many light instances.
