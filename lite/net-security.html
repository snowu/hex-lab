Cheating, trust and hostile input

The client is in the player's hands: validate everything on the server, leak nothing you do not need to, and treat every packet as an attack.

The golden rule

The client is controlled by the player. Anything the client does or reports can be faked: memory can be edited, packets forged, the program replaced. So a networked game must be designed so that a hacked client can only ask, never tell. The server decides what is true.

Typical cheats and the design that stops them

CheatDesign response
Speed hack / teleport (send a position)Clients send inputs, the server simulates movement. Or, if clients send positions, the server validates against the maximum speed and rejects impossible moves (snippet below).
Aimbot, auto-fireCannot be fully prevented client-side. Server-side statistics and behavioural detection, rate limits on fire, review tools. Be honest about the limits.
Wallhack / map hackDo not send information the player should not have (enemies behind walls, hidden cards, the other team's resources). Fog-of-war on the server.
Item or currency duplication, impossible purchasesThe server owns inventory and balances and checks every transaction (idempotent operations, transactions with ids).
Replay or forged packetsSequence numbers, session tokens, authenticated and encrypted transport; reject out-of-window sequences.
Modified game files / valuesNever trust a stat the client sends (damage, health, cooldown). The server holds the numbers.
Random outcomes chosen by the clientRoll on the server (loot, crits). A client that picks its own roll always gets the best one.

Validate on the server

For each request ask: is the sender who they claim to be? Is the action allowed in the current state (is it their turn, do they have the item, is the cooldown over)? Is the argument in range (position within the map, speed under the maximum, count between 1 and 99)? How often may they do this (rate limit per player and per action)? Reject and (rarely) log, never crash and never "try to make sense of it".

const std = @import("std");

const Move = struct { seq: u32, x: f32, y: f32 };

const Player = struct {
    x: f32 = 0,
    y: f32 = 0,
    last_seq: u32 = 0,
    rejected: u32 = 0,
};

const MAX_SPEED: f32 = 300; // units per second, from the game rules: the server's number, not the client's
const MAP: f32 = 1000;

/// Accept a client-reported position only if it is physically possible since the last accepted one.
fn acceptMove(p: *Player, m: Move, dt: f32) bool {
    if (m.seq <= p.last_seq) return reject(p); // replayed or reordered packet
    if (std.math.isNan(m.x) or std.math.isNan(m.y) or std.math.isInf(m.x) or std.math.isInf(m.y)) return reject(p); // hostile floats
    if (m.x < 0 or m.y < 0 or m.x > MAP or m.y > MAP) return reject(p); // outside the world
    const dx = m.x - p.x;
    const dy = m.y - p.y;
    const max_step = MAX_SPEED * dt * 1.1; // a little slack for timing jitter
    if (dx * dx + dy * dy > max_step * max_step) return reject(p); // teleport or speed hack
    p.x = m.x;
    p.y = m.y;
    p.last_seq = m.seq;
    return true;
}

fn reject(p: *Player) bool {
    p.rejected += 1;
    return false;
}

test "plausible moves are accepted, impossible ones are not, and hostile numbers are survived" {
    var p = Player{ .x = 100, .y = 100 };
    try std.testing.expect(acceptMove(&p, .{ .seq = 1, .x = 104, .y = 100 }, 1.0 / 60.0)); // 4 units in 1/60 s is 240 u/s
    try std.testing.expect(!acceptMove(&p, .{ .seq = 2, .x = 400, .y = 100 }, 1.0 / 60.0)); // teleport
    try std.testing.expect(!acceptMove(&p, .{ .seq = 1, .x = 105, .y = 100 }, 1.0 / 60.0)); // replayed sequence
    try std.testing.expect(!acceptMove(&p, .{ .seq = 3, .x = std.math.nan(f32), .y = 0 }, 1.0 / 60.0));
    try std.testing.expect(!acceptMove(&p, .{ .seq = 4, .x = -5, .y = 100 }, 1.0 / 60.0));
    try std.testing.expectEqual(@as(f32, 104), p.x); // state only moved for the accepted move
    try std.testing.expectEqual(@as(u32, 4), p.rejected);
}

Hostile bytes

Treat every incoming packet like a file from a stranger (the same rule as the save-file lesson): check the length before reading, never trust a count or index inside it, cap allocations, and parse with code that fails safely. Memory-unsafe parsers (C and C++) are where most real remote-code-execution bugs come from; bounds-checked code and fuzzing the parser with random and mutated packets finds them early.

Denial of service

  • Rate limit by connection and by action; drop clients that flood.
  • Make the handshake cheap for the server and expensive for the attacker (stateless cookies so spoofed connection requests allocate nothing).
  • Cap per-connection memory and message size. Bound everything that grows with player input.
  • Do not let a small request trigger a large response (amplification).

Accounts, privacy and safety

  • Use established authentication (platform tokens, OAuth), never roll your own password storage; send secrets only over encrypted channels (TLS, DTLS).
  • Collect the minimum personal data, and know the rules that apply to you (GDPR, children's privacy laws). Chat and names need moderation tools: reporting, mutes, filters.
  • Log enough to investigate abuse, without logging secrets.

Anti-cheat: be realistic

Client-side anti-cheat is an arms race and invasive; server authority and good design remove entire classes of cheating cheaply. Decide per game: a co-op game with friends needs little; a ranked competitive game needs authoritative servers, statistical detection, report tools and a ban process. Never put a secret in the client and assume it stays secret.
